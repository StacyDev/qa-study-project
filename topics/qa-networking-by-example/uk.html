Network Debugging Tutorial

A complete reference for debugging communication failures between two computers — from physical layer to application layer.

How to use this tutorial: use the sidebar to navigate by topic. Start with Network type tree to understand which type of network you are dealing with — that determines which debugging path to follow. The VLAN misconfiguration case study is a detailed worked example of a real switch-level failure.

What this covers

Two computers cannot communicate. This tutorial walks through every possible reason — from a loose cable to a VLAN misconfiguration to a TLS certificate mismatch — organised by the OSI model and by the type of network the computers are on.

First question to always ask before debugging: do you have access to all devices in the path — both hosts, the switch, the router? The answer changes which checks are possible and which require escalation.

The core principle

Always debug bottom up — start at the physical layer and move up. A problem at Layer 1 makes every higher layer appear broken. Jumping to application logs before confirming the cable is seated is wasted effort.

The second principle: know which device to run each check on. Running ss -tuln on Host A tells you nothing about whether Host B's service is listening. Every command in this tutorial is labelled with the correct host.

Network Type Tree

All communication types classified by the path the data takes. Click any type in the sidebar to go to its debugging guide.

How to identify which type you have

Are both hosts on the same machine? → Type 1 (loopback).

Two machines, one cable, no switch? → Type 2 (direct cable).

Same building, same subnet, connected via switch? → Type 3 (switched local).

Same building, different subnets or different floors? → Type 4 (routed local).

Communicating via an application like Slack, email, or a web app? → Type 6 (central server).

Using a VPN client? → Type 7.

Video or voice call? → Type 8 (P2P with relay).

Connecting directly to another machine's public IP? → Type 5.

Switch Tables Explained

A common misconception is that a switch only has one table — the CAM table. In reality a managed switch maintains several tables, each responsible for a different aspect of frame forwarding.

Why this matters for debugging: when communication fails at Layer 2, the problem may be in any one of these tables — not necessarily the CAM table. Knowing which table does what tells you where to look.

The tables and their roles

CAM table — Content Addressable Memory ▶

What it stores: MAC address → VLAN → port number.

How it is built: passively through MAC learning. When any frame arrives on a port, the switch reads the source MAC address from the Ethernet frame header and writes: this MAC was seen on this port in this VLAN. There is no manual configuration — the table builds itself from observed traffic.

How long entries last: each entry has a timer — typically 300 seconds. Every time the switch sees a frame from that MAC the timer resets. If 300 seconds pass with no frames from that MAC, the entry is removed. This is called ageing out.

What it is used for: every time the switch receives a frame, it looks up the destination MAC in the CAM table. If found, the frame goes to that specific port. If not found, the switch floods the frame to all ports in the same VLAN.

show mac address-table ← Cisco command to inspect CAM table clear mac address-table dynamic ← force clear all learned entries
VLAN table — port-to-VLAN assignments ▶

What it stores: which VLANs exist, and which physical ports belong to each VLAN.

How it is built: manually configured by a network administrator. This is the table that was misconfigured in the VLAN case study — the admin changed a port's VLAN assignment by mistake.

What it is used for: when a frame arrives on a port, the switch looks up that port in the VLAN table to determine which VLAN the frame belongs to. When delivering a frame, the switch checks that the destination port is in the same VLAN as the source. If not, the frame is dropped.

The relationship with the CAM table: the VLAN column in the CAM table records which VLAN a MAC was observed in. The CAM table does not actively sync with the VLAN table. If the VLAN table changes, the CAM table still holds its old cached values until they age out — which is exactly what creates the silent drop window in a VLAN misconfiguration.

show vlan brief ← shows all VLANs and their member ports show interface FastEthernet 0/2 ← shows which VLAN port 2 is assigned to
STP table — Spanning Tree Protocol ▶

What it stores: the state of each port — forwarding, blocking, or listening — to prevent loops when multiple switches are connected to each other.

Why it exists: if two switches are connected by two cables for redundancy, frames could loop forever between them. STP detects this and blocks one of the paths. Only one active path exists at a time; if it fails, STP activates the blocked path.

Debugging relevance: a port in STP blocking state will not forward any traffic. This looks exactly like a disconnected cable from the host's perspective — NIC LED is green, but no frames get through. STP convergence after a topology change can also cause a 30–50 second outage while it recalculates the active path.

show spanning-tree ← shows port states per VLAN
ARP table — IP to MAC mapping (Layer 3 switches only) ▶

What it stores: IP address → MAC address mappings, exactly like the ARP table on a host.

Only on Layer 3 switches: a basic Layer 2 switch does not have an ARP table — it only operates on MAC addresses. A Layer 3 switch can route traffic between VLANs and therefore needs to resolve IP addresses to MACs, which requires an ARP table.

show ip arp ← on a Layer 3 switch
Routing table (Layer 3 switches only) ▶

What it stores: network prefixes and the next hop to reach them — identical in function to a router's routing table.

Only on Layer 3 switches: a Layer 2 switch has no routing table. A Layer 3 switch can route between VLANs internally without needing a separate router device.

show ip route ← routing table on a Layer 3 switch

VLANs vs Subnets

Two concepts that are often confused because they solve similar problems at different OSI layers.

Why VLANs exist at all

The question is: why not keep everything on one flat network on a single switch?

Reason 1 — Security ▶

On a flat network every host can send frames directly to every other host at Layer 2 — no router, no firewall in between. A compromised laptop in the guest WiFi can send ARP requests to the finance server on the same switch. With VLANs, the guest network is VLAN 30, finance is VLAN 10. They cannot exchange frames directly. Any traffic between them must pass through a router where firewall rules can inspect and block it. The switch hardware enforces the separation before the packet even reaches a firewall.

Reason 2 — Broadcast control ▶

Every device on a network receives all broadcast traffic — ARP requests, DHCP requests, network discovery protocols. On a flat network with 500 devices, every broadcast goes to all 500 hosts. Each host must process it, even to decide it is irrelevant. VLANs create separate broadcast domains — a broadcast on VLAN 10 never reaches VLAN 20. As networks grow, this becomes critical for performance.

Reason 3 — Flexibility without physical changes ▶

Without VLANs, moving a host to a different logical group requires physically moving its cable to a different switch. With VLANs, you change one line of configuration on the switch port — the cable stays exactly where it is. This is also why a VLAN misconfiguration is so dangerous — the physical layer looks perfectly healthy while the logical separation has changed.

In practice they are almost always paired one-to-one: VLAN 10 gets subnet 192.168.10.0/24, VLAN 20 gets 192.168.20.0/24. This is why a VLAN misconfiguration also creates an IP problem — the host's IP belongs to the VLAN 10 subnet but the switch has moved it to VLAN 20. The root cause is Layer 2. The IP mismatch is a Layer 3 consequence.

Can one VLAN have two subnets?

Technically possible. Practically a misconfiguration. Here is what happens:

Scenario: VLAN 10 contains two hosts:
— Host A: 192.168.10.5 /24
— Host B: 192.168.20.5 /24

At Layer 2: works fine. The switch sees both on VLAN 10, learns their MACs, delivers frames between them.

At Layer 3: Host A looks at Host B's IP (192.168.20.5) and computes it is not in its own subnet (192.168.10.x). So Host A sends it to its default gateway instead of directly. The gateway receives it and may not know how to route it back to the same VLAN — creating a routing loop or a dead end.

ARP also breaks: Host A will never send an ARP request directly to Host B because it believes Host B is on a remote network. It ARPs for the gateway instead. Host B never receives the ARP, never replies, and communication never starts.
Correct design: one VLAN per subnet, one subnet per VLAN — always. If you need a second group of hosts on a different subnet, create a second VLAN for them. This keeps Layer 2 and Layer 3 boundaries aligned and makes debugging straightforward.

Type 1 — Loopback

Two processes on the same machine communicating through the virtual loopback interface. No physical hardware involved.

5-minute triage strategy

Branch: YES — you have access to the machine

1. No physical checks — loopback is a virtual interface. Skip directly to software.

2. Check the application is running: ps aux | grep <service>. If the process is not in the list — start it. Nothing else matters if the process is dead.

3. Check the port is listening: ss -tuln. The port must be listed and bound to 127.0.0.1 or 0.0.0.0 — not a specific external IP which would make it unreachable on loopback.

4. Test the connection: telnet 127.0.0.1 <port>. Connected = working. Refused = nothing listening. Timeout = firewall rule blocking loopback traffic.

5. If all above pass and it still fails — check application logs. The service may be running and listening but rejecting connections due to a configuration error or version mismatch.

Branch: NO — no access to the machine
You cannot debug loopback remotely. The problem is entirely inside a machine you cannot reach. Escalate to whoever manages that machine.
Process A→ 127.0.0.1 loopback (virtual)→ Process B

The loopback interface (127.0.0.1 for IPv4, ::1 for IPv6) is a virtual network interface built into the OS. Traffic sent to 127.0.0.1 never leaves the machine — it goes through the OS network stack and loops back. No cable, no switch, no NIC hardware involved at all.

Common in: a web server on port 8080 talking to a database on port 5432 on the same machine. Nginx proxying to an app server. Redis cache on localhost. Microservices running on one machine during development.

Physical checks

None. There is no physical hardware in this path. Skip directly to software checks.

Type 2 — Direct Cable

Two machines connected by a single Ethernet cable with no switch, no router, and nothing else in between.

5-minute triage strategy

Branch A: access to both hosts

1. Physical first — NIC LEDs on both machines must be lit. Press cable firmly on both ends. If no LED — fix physical before anything else.

2. Check interface state: ip link show on both. Must show UP with carrier. NO-CARRIER means no physical signal despite the cable being present.

3. Check IP addresses on both: ip addr show. Both must have IPs in the same subnet. No IP means DHCP was expected but there is no DHCP server — assign static IPs manually.

4. Run ping from Host A: ping <B-IP>. If ping succeeds — L1 through L3 confirmed. Move to L4: check listening ports and firewall.

5. If ping fails — check ARP: arp -a on Host A. If Host B's MAC is missing, the problem is at L2 — cable, NIC, or IP subnet mismatch.

6. If ping succeeds but application fails — check service running on Host B, port listening (ss -tuln), firewall rules (iptables -L), then application logs.

Branch B: own host only
Check your own NIC LED and ip link show. Verify your static IP is configured correctly. Run ping <B-IP> — if no reply you cannot confirm whether the problem is your side, the cable, or Host B. You can only confirm your own configuration is correct and report that Host B is unreachable. Escalate for access to Host B.
Host A→ Ethernet cable (direct)→ Host B
Used for: emergency server access when no switch is available, fast file transfer between two machines, initial server setup, minimal test environments.

What is a network interface

When a NIC (Network Interface Card) is installed in a computer, the operating system creates a named software object for it. That named object is called the network interface. All configuration — IP address, MTU, up/down state — is applied to the interface, not directly to the hardware.

On Linux the interface is typically named eth0, eth1, or enp3s0 — the exact name depends on the OS version and NIC model. On Windows it appears as Ethernet, Ethernet 2, or Local Area Connection — visible in Network Adapter settings.

When you run ip link show or Get-NetAdapter, two separate conditions must both be true:

UP — the OS has activated the interface. An interface can be physically connected but administratively disabled by the OS — ip link set eth0 down puts it in this state. The output will say DOWN even if a cable is plugged in.

Carrier detected — the NIC is receiving an electrical signal from the other end of the cable. No carrier means no physical signal — the cable is unplugged, broken, or the other device is off. In ip link show output this appears as NO-CARRIER when the cable is disconnected even if the interface is UP.

Both must be true before any frame can leave the machine. If either is missing — fix it before touching any higher layer.

Cable type

An Ethernet cable contains 8 wires twisted into 4 pairs. Some pairs transmit data and some receive. When two computers are connected directly, both are the same type of device — both try to transmit on the same wire pair, which causes a collision. Historically this required a crossover cable — a cable where the transmit wires on one end are physically connected to the receive wires on the other end.

However, any NIC manufactured in roughly the last 15 years supports a feature called auto-MDI/X (Medium Dependent Interface Crossover). The NIC automatically detects what it is connected to and electronically swaps the pairs internally if needed. A standard straight-through Ethernet cable — the kind used everywhere in offices — works perfectly. Grab any Ethernet cable from a drawer. It will work.

The only time you need a crossover cable is if you are connecting very old hardware — pre-2000s era network cards that do not support auto-MDI/X.

Critical differences vs a switched network

No DHCP server — there is no router or switch to assign IP addresses automatically. Both machines must have static IP addresses configured manually in the same subnet before anything works.

No switch CAM table to check — skip all CAM table checks entirely. ARP still happens — Host A resolves Host B's MAC address by sending a broadcast directly down the cable and Host B replies — but there is no switch in the path to relay or log it.

No switch port LEDs — the only LEDs to check are the NIC ports on both machines themselves.

How ARP works on a direct cable connection

ARP (Address Resolution Protocol) works exactly the same as on a switched network. When Host A wants to send to 192.168.0.2 it sends an ARP broadcast — "who has 192.168.0.2, tell 192.168.0.1?" That broadcast goes out the NIC, travels down the cable, and Host B receives it directly. Host B replies with its MAC address. Host A writes that MAC into its ARP cache and communication can begin. No switch, no CAM table involved — but ARP is still required.

Static IP setup — Linux terminal

# On Host A: ip addr add 192.168.0.1/24 dev eth0 ip link set eth0 up # On Host B: ip addr add 192.168.0.2/24 dev eth0 ip link set eth0 up # Test from Host A: ping 192.168.0.2

Static IP setup — Windows graphical interface

No terminal required. On Windows you can configure a static IP entirely through the GUI:

Settings → Network & Internet → Ethernet → Change adapter options → right-click the adapter → Properties → Internet Protocol Version 4 (TCP/IPv4) → Properties → Use the following IP address

Enter the IP address (e.g. 192.168.0.1), subnet mask (255.255.255.0 for /24), and leave default gateway blank — there is no gateway in a direct cable setup. Leave DNS server blank or enter 8.8.8.8 — it makes no difference for direct communication by IP address.

Do you need to edit the hosts file? No. The hosts file (/etc/hosts on Linux, C:\Windows\System32\drivers\etc\hosts on Windows) maps hostnames to IP addresses locally, bypassing DNS. It is only relevant if you want to use a hostname like hostb instead of typing the IP address. If you communicate by IP address directly, the hosts file is never involved. No other preconditions are needed — no special drivers, no registry edits, nothing else.

How to assign IP addresses — two valid options

There is no router or DHCP server in a direct cable setup. Both machines must have IP addresses before any communication is possible. There are exactly two ways to achieve this:

Option 1 — Manual static IP (recommended) ▶

You assign an IP address to each machine yourself. This is the most reliable approach because you are fully in control of every value. Three things must be correct:

IP address — each machine gets a unique address. Example: Host A gets 192.168.0.1 and Host B gets 192.168.0.2. They must not be the same.

Subnet mask — must be identical on both machines. Use 255.255.255.0 (also written as /24). This tells each machine which part of the address identifies the network and which identifies the host. If the subnet masks differ even by one bit, the machines compute different network boundaries and one may conclude the other is unreachable.

IP address group — both addresses must belong to the same network range. With a /24 subnet mask, the first three octets must match. 192.168.0.1 and 192.168.0.2 are in the same group. 192.168.0.1 and 192.168.1.2 are not — they are on different networks and cannot communicate directly.

Default gateway — leave blank. There is no router in this setup. A gateway is only needed when traffic must leave the local network.

This is the correct approach for a direct cable connection. Static setup: 30 seconds. No software dependencies. No risk of address conflicts.
Option 2 — Link-local automatic addressing ▶

When a network interface is active but the OS finds no DHCP server and no static IP has been configured, the OS automatically assigns itself an address in the range 169.254.0.0 – 169.254.255.255. This is called link-local addressing. On Windows it is called APIPA (Automatic Private IP Addressing). On Linux it is handled by the network manager.

The timing: the OS waits a few seconds after the cable is plugged in to see if a DHCP server responds. When none does, it picks a random address in the 169.254.x.x range, sends ARP requests to check no other device on the cable is already using that address, and assigns it to itself. Both machines do this independently.

Potential issues:

Different subnets — both machines pick addresses in the 169.254.x.x range and use a /16 subnet mask (255.255.0.0), so they are on the same network. This specific risk is less likely with link-local than with other auto-assignment schemes — but it can still occur if one machine has a stale static IP left over from a previous configuration while the other uses link-local.

IP address duplication — both machines independently pick a random address and there is a small but real chance they pick the same one. The ARP probe step reduces this risk but does not eliminate it entirely under all conditions. If both end up with the same IP, neither can communicate.

Unpredictability — you do not know in advance what IP address each machine assigned itself. You must check with ip addr show or ipconfig /all on each machine after the link comes up to find out what addresses were assigned before you can use them.

Link-local works but requires checking the assigned addresses on both machines before attempting any communication. For anything beyond a quick test, static IP assignment is more reliable.
What about a portable DHCP server? Some guides mention running DHCP server software on one of the machines to automatically assign an address to the other. In a direct cable connection this is redundant. DHCP works by broadcasting a discovery message — the other machine receives it directly down the cable. But for DHCP server software to respond, it must already be installed, configured, and running on that machine before the cable is connected. This requires more setup than simply typing two static IP addresses. The result is identical but the effort is greater. For a direct cable connection, static IP or link-local are the only two options worth considering.

How to actually initiate communication — practical examples

Once both machines have IP addresses in the same subnet, you need to actively start sending traffic. The cable being connected is not enough — one side must initiate. Here is what happens under the hood in every case, and the practical ways to trigger it.

What always happens invisibly before any communication:
1. Host A checks — is Host B's IP in my subnet? Yes → send directly, no router needed.
2. Host A checks its ARP cache — do I know the MAC for that IP? If not → send ARP broadcast down the cable.
3. Host B receives the ARP request and replies with its MAC address.
4. Host A now has the MAC, builds an Ethernet frame, sends it down the cable.
5. Host B receives the frame and passes it up to the application.

The user never sees these steps. They happen automatically the moment you initiate any of the methods below.
Terminal — ping (first test, always do this first) ▶

Open a terminal on Host A and run ping 192.168.0.2. The OS sends ICMP echo packets to Host B and prints a reply for each one received. This is the standard first check — it confirms the cable, addresses, and IP routing all work before trying anything more complex. If ping fails, nothing else will work either.

ping 192.168.0.2 # Linux and Windows — works on both
Terminal — file transfer with netcat ▶

Netcat is a simple tool that opens a raw TCP connection and passes data through it. No server software required — just the command on each end.

On Host B first — set it to listen on a port and write whatever arrives into a file:

nc -l 9999 > received_file.txt

Then on Host A — connect to that port and stream a file into it:

nc 192.168.0.2 9999 < file_to_send.txt

The file travels down the cable. When Host A finishes sending, the connection closes and Host B's file is complete. No login, no setup, no shared folder configuration required.

Terminal — SSH remote access ▶

If Host B has SSH server software running (on Linux: sshd, on Windows: OpenSSH Server which can be enabled in Optional Features), you can open a full remote terminal session from Host A:

ssh username@192.168.0.2

After entering the password you get a terminal running on Host B. Every command you type executes on Host B. You can copy files, run programs, edit configuration — all from Host A without touching Host B physically.

Windows File Explorer — shared folder (SMB) ▶

This is the graphical approach — no terminal needed. SMB (Server Message Block) is the Windows file sharing protocol. It runs over TCP port 445.

On Host B — share a folder: right-click any folder → Properties → Sharing tab → Share → choose who can access it → Share.

On Host A — access it: open File Explorer → click the address bar at the top → type \\192.168.0.2 → press Enter.

Windows sends a connection request to Host B over SMB. If Host B has sharing enabled and the firewall allows port 445, Host A sees Host B's shared folders appear in File Explorer exactly like a local drive. You can drag and drop files in either direction.

The OS handles all ARP resolution, TCP connection establishment, and SMB negotiation completely invisibly. From the user's perspective it looks like opening a folder on your own machine.

Windows Firewall on Host B must allow incoming connections on port 445. If file sharing was never enabled, the firewall may block it. Go to Windows Defender Firewall → Allow an app through → File and Printer Sharing → enable for Private networks.
Browser — accessing a web server on Host B ▶

If Host B is running a web server — for example during development of a web application — you can access it from Host A's browser without any special setup beyond having the IPs configured.

On Host A open any browser and type in the address bar:

http://192.168.0.2 # port 80 (default HTTP) http://192.168.0.2:8080 # if server runs on a different port

The browser builds an HTTP request, sends it to Host B's IP, and displays whatever the web server on Host B returns. This is exactly how developers test a web application running on a colleague's machine or a local test server before it is deployed.

Alternatives when no Ethernet interface is available

If neither machine has an Ethernet port, direct communication is still possible through other physical interfaces. In all cases below, once the link is established the OS presents it as a standard network interface — from Layer 3 upward the debugging process is identical to Ethernet.

WiFi Direct (WiFi P2P) ▶

Both machines connect directly over WiFi without any router or access point. One machine acts as a software access point, the other connects to it. Modern operating systems support this natively — Windows calls it a mobile hotspot or WiFi Direct. The underlying protocol is still TCP/IP so everything works exactly like a cable connection including ARP, IP addressing, and all the same debugging steps from Layer 3 upward.

Bluetooth ▶

Designed for short range — typically up to 10 metres. Supports a network profile called PAN (Personal Area Network) which allows TCP/IP communication between two devices over Bluetooth. Slow compared to WiFi or Ethernet but functional for small file transfers or messaging. Less common on desktop computers but standard on laptops.

USB network adapter / USB tethering ▶

When two computers are connected with a USB data transfer cable (not a standard USB cable — a special networking cable), the OS creates a virtual network interface over USB. The two machines then communicate exactly like an Ethernet connection — TCP/IP, ARP, static IPs. Also works when one machine shares its internet connection to another via USB tethering.

Thunderbolt / USB-C networking ▶

Modern MacBooks and some Windows laptops support IP networking directly over a Thunderbolt or USB-C cable. The OS creates a virtual Ethernet interface over the Thunderbolt connection. Apple calls this Thunderbolt Bridge. Extremely fast — limited only by Thunderbolt bandwidth, which far exceeds Gigabit Ethernet.

Serial / legacy (historical context) ▶

Before Ethernet was common, two computers could communicate via serial ports (RS-232) using a null modem cable. Very slow by modern standards. Not relevant in practice today but occasionally appears in embedded systems or industrial equipment.

Key point for debugging all alternatives: regardless of the physical medium — cable, WiFi, Bluetooth, USB — once the link is established the OS presents it as a network interface. You still check ip link show or Get-NetAdapter, still configure IP addresses in the same subnet, still use ping, still check ARP. The physical medium only affects Layer 1 checks — instead of looking at an Ethernet LED you check WiFi signal strength or Bluetooth connection status. Layer 3 and above is identical.

Type 3 — Switched Local Network

Two hosts on the same subnet, connected through a switch. The most common local network configuration.

5-minute triage strategy

Branch A: both hosts + switch access — full path

1. Physical first — NIC LEDs on both hosts and switch port LEDs for both ports. Cable seated. If any light is off — fix physical before continuing.

2. Ping sanity test immediately: ping <B-IP> from Host A. If ping succeeds — L1, L2, L3 all confirmed. Skip to step 5. If ping fails — continue step by step.

3. If ping failed — check VLAN and CAM table on the switch: show vlan brief and show mac address-table. Are both hosts in the same VLAN? Is Host B's MAC mapped to the correct port? A VLAN mismatch silently drops frames — nothing on the host side reveals this.

4. Check IP configuration on both hosts: ip addr show. Same subnet? Same prefix length? Run traceroute <B-IP> — Host B should appear at hop 1. If it appears via the gateway, the subnet mask is wrong.

5. Once ping succeeds — check service on Host B: ss -tuln for listening ports, telnet <B-IP> <port> from Host A. Connected = L4 open. Refused = not listening. Timeout = firewall on Host B.

6. If port reachable but application fails — check process running on Host B, check firewall rules (iptables -L -n -v), check TLS if encrypted, check application logs (journalctl -u <service> -f).

Branch B: both hosts, no switch access
Follow the same steps but skip the switch checks entirely. You cannot verify VLAN or CAM table. If ping fails and all host-side configuration looks correct, a VLAN misconfiguration on the switch is a possible cause you cannot confirm — escalate to whoever manages the switch and describe what you observed: physical looks healthy, IP configuration correct, ping fails, no ARP response.
Branch C: own host only
Check your NIC, your IP address, and your subnet mask. Run ping — if no reply you cannot determine whether the problem is your side, the cable, the switch, or Host B. Run telnet <B-IP> <port> — a refused or timeout result tells you the network path is partially working or blocked. Report your findings and escalate.
Host A→ Switch (CAM + VLAN tables)→ Host B

The switch learns each host's MAC address via MAC learning and forwards frames using its CAM table. The router is not involved in delivering frames between hosts on the same subnet — though it may be the DHCP server that assigns their IP addresses.

A detailed worked example of how a single admin typo silently breaks communication between two hosts on a switched network.

Why this is hard to find: nothing physically changed. All LEDs are green. The NIC on Host B shows UP. Ping times out — which looks identical to Host B being powered off. You cannot find this from the hosts alone. You need access to the switch.

Host A and Host B are both on VLAN 10. The switch has learned both MACs. Communication works normally.

How the CAM table was built: passively. When Host B sent any frame, the switch read the source MAC and wrote BB:BB → VLAN 10 → Port 2. There is no manual configuration. The switch learns from observed traffic only.

Admin makes the change — with a typo

The admin needs to move Host C (port 3) from VLAN 20 to VLAN 10. But types port 2 instead of port 3.

Intended command:
interface FastEthernet 0/3
switchport access vlan 10
Actual command typed:
interface FastEthernet 0/2 ← typed 2 instead of 3
switchport access vlan 20

This changes the VLAN table entry for port 2 from VLAN 10 to VLAN 20. Host B's cable did not move. The NIC LED is still green. This is a pure software change — only the VLAN table was updated. The CAM table was not touched.
Two tables — now contradicting each other:
VLAN table: port 2 → VLAN 20 (just changed)
CAM table: BB:BB → VLAN 10 → Port 2 (still cached, not yet updated)

The switch will use the CAM table to find the destination port, then check the VLAN table when delivering — and that is where the drop happens.

The switch floods to all ports in VLAN 10. Port 2 is no longer in VLAN 10 so it is excluded from the flood. Host B never receives the frame, never replies, and the CAM entry is never rebuilt. Permanently broken until the port configuration is corrected.

Final result — broken, hard to find

What looks healthy: NIC LED on port 2 is green. Host B's ip link show shows UP. Cable is intact. Host B can ping 127.0.0.1.
What is actually broken: ping <B-IP> from Host A times out. ip neigh show on Host A shows BB:BB as FAILED. Host B's port is in VLAN 20 but its IP belongs to the VLAN 10 subnet — double failure at L2 and L3, root cause is L2.
Why the IP matters even though the switch is L2: the switch does not look at IPs. But Host B's IP (e.g. 192.168.10.5) was assigned for the VLAN 10 subnet. Now that port 2 is in VLAN 20, that subnet no longer matches the VLAN. The L2 failure (wrong VLAN) causes a L3 consequence (wrong subnet). Fix the VLAN — the IP issue resolves automatically.
How to find and fix it — requires switch access:
show mac address-table — BB:BB missing from VLAN 10
show interface FastEthernet 0/2 — reveals port 2 is in VLAN 20

Fix:
interface FastEthernet 0/2
switchport access vlan 10

Communication restores within seconds of Host B sending any frame.

Host B has no idea its port was moved. It sends a frame normally. Here is what happens to the CAM table.

This makes things worse. Before Host B sent anything, its entry was stale but still under VLAN 10. After Host B sends, the entry moves to VLAN 20. Host A looks up BB:BB under VLAN 10 — finds nothing at all. Not even a stale entry to attempt delivery against.
Can Host C reach Host B now? The switch delivers the frame to port 2 (BB:BB is now under VLAN 20). Host B receives it at L2. But Host B's IP (192.168.10.x) is from the VLAN 10 subnet and Host C's IP is from the VLAN 20 subnet — communication still fails at L3. Frame arrives, Host B discards it because the source IP is from a foreign network.

Key questions answered

Which table was actually misconfigured — CAM or VLAN? ▶

The VLAN table was misconfigured. The admin changed the port's VLAN assignment. The CAM table was not misconfigured — it held a cached entry that became wrong the moment the VLAN table changed underneath it. The CAM table is a victim of the misconfiguration, not its cause.

Why does the CAM table have a VLAN column if the switch operates at L2? ▶

Because the same MAC address could theoretically appear on different VLANs on different ports. The VLAN column scopes each CAM entry to a specific VLAN context. It is not a full copy of the VLAN table — it just records which VLAN the MAC was last seen in. When the VLAN table changes, the cached VLAN in the CAM entry becomes stale and contradicts current reality.

Does the CAM table automatically sync with the VLAN table? ▶

No. The CAM table only updates passively through MAC learning. There is no automatic sync triggered when the VLAN table changes. This is what creates the 300-second window where the two tables contradict each other. To force an immediate update: clear mac address-table dynamic on the switch.

Why can this only be found from the switch — not from the hosts? ▶

From Host A the symptom is a timeout on ping — identical to Host B being off, a firewall blocking traffic, or a broken cable. Host A has no visibility into the switch's VLAN configuration. From Host B everything looks fine. The only way to find this is to inspect the switch management interface. This is why "do you have access to all devices?" is always the first question in a debugging scenario.

Type 4 — Routed Local Network

Two hosts in the same building on different subnets. Traffic must cross an internal router.

5-minute triage strategy

Branch A: full access to both hosts and router

1. Physical checks on both hosts — LEDs, interface state.

2. Ping sanity test: ping <B-IP>. If ping succeeds — routing is working. Go to L4.

3. If ping fails — ping the gateway first: ping <gateway-IP>. If gateway does not reply — Host A cannot even leave its own subnet. Fix local config first.

4. Run traceroute <B-IP>. If it stops at the router — the router's firewall is blocking inter-subnet traffic. Check router ACL (access control list) rules.

5. Verify routing table on Host A: ip route show. A route for Host B's subnet must exist via the internal router.

6. Once ping succeeds — check port and application on Host B as per Type 3 steps.

Branches B and C: limited or no router access
You can still run traceroute to see where the path breaks. If it stops at the router IP, you have identified the problem location even without router access. Report: "traceroute stops at router X.X.X.X — inter-subnet routing or firewall blocking suspected." Escalate to the network team with this specific observation.
Host A→ Switch A→ Internal router→ Switch B→ Host B

Common in large offices with VLAN segmentation between departments. Host A on 10.1.0.x and Host B on 10.2.0.x cannot reach each other via ARP — ARP does not cross subnet boundaries. All traffic must go through the internal router.

Extra failure points vs Type 3: the internal router must have routes for both subnets. Its firewall may block inter-subnet traffic. ARP only works within a subnet — the router handles delivery between subnets.

Type 5 — Direct Internet P2P

Host A connects directly to Host B's public IP over the internet. Requires port forwarding on Host B's router.

5-minute triage strategy

Branch A: you control Host B

1. Confirm both sides have internet: ping 8.8.8.8 from both machines.

2. Find Host B's public IP: curl ifconfig.me on Host B. This is the address Host A needs to connect to.

3. Verify port forwarding is configured on Host B's router — incoming traffic on your port must be forwarded to Host B's private IP. Without this, NAT blocks all inbound connections.

4. Test from Host A: telnet <B-public-IP> <port>. Connected = working. Timeout = port forwarding missing or ISP blocking that port.

5. Check Host B's firewall allows inbound on that port. Check service is running and listening on Host B.

Branch B: you do not control Host B
Confirm your internet works. Ping Host B's public IP — if no reply, either B is down, its firewall blocks ICMP, or NAT blocks inbound. Run traceroute to see where the path breaks. You cannot configure port forwarding or check Host B's firewall — report your observations and escalate.

Type 6 — Via Central Server

Both hosts connect outward to the same server. Neither connects to the other directly.

5-minute triage strategy

Branch A: your own server

1. Confirm internet: ping 8.8.8.8 and gateway.

2. DNS resolution: nslookup <server-hostname>. Must return an IP. Failure = DNS broken.

3. Port reachable: telnet <server> 443. Timeout = outbound port 443 blocked by your firewall or ISP.

4. Full test: curl -v https://<server>. Then check server-side logs for the actual error.

5. Check TLS: openssl s_client -connect <server>:443. Certificate expired or hostname mismatch fails here.

Branch B: third-party server (Slack, Teams, etc.)
Check the service status page first — status.slack.com, status.atlassian.com, etc. If the service is down, stop debugging locally. If the status page shows all green, check your own internet connectivity, DNS, and whether port 443 outbound is blocked. Run traceroute <server> — if the path stops at an internal IP, a corporate proxy is intercepting traffic.

Type 7 — VPN Tunnel

An encrypted tunnel through the internet that makes remote hosts appear to be on the same local network.

5-minute triage strategy

Branch A: you manage the VPN server

1. Confirm internet without VPN: ping 8.8.8.8 with VPN disconnected. Must pass first.

2. Check VPN server port is reachable: nc -zvu <vpn-server> 1194. Corporate firewalls frequently block VPN ports.

3. Connect VPN. Ping the VPN gateway's virtual IP. Reply = tunnel established.

4. Check routing table: ip route show — private range must route via VPN interface.

5. Ping Host B's VPN IP. If fails — routing inside the tunnel is broken. Check VPN server config and pushed routes.

Branch B: client side only
Confirm your internet works. Connect the VPN client. If it connects but tunnel is broken — ping the gateway virtual IP. If that fails, the VPN server is not routing. Escalate to whoever manages the VPN server with: "client connects, gateway ping fails, route to private network not working."

Type 8 — P2P with Relay Fallback

Tries direct connection first. Falls back to a relay server if NAT or corporate firewalls block the direct path.

5-minute triage strategy

Branch A: connection works but quality is poor — relay fallback suspected

1. Open browser DevTools during an active call. Look at WebRTC stats — a "relay" candidate type confirms the call is going through a TURN relay server instead of connecting directly. This adds significant latency.

2. Check whether STUN port is reachable: nc -zvu <stun-server> 3478. If blocked, direct connection negotiation cannot happen at all.

3. Test from a different network (mobile hotspot vs corporate WiFi). Works better on home network = corporate firewall blocking UDP media ports. Escalate to network team to open required UDP port ranges.

Branch B: no connection at all
Confirm basic internet works. Check whether the relay server itself is reachable: telnet <relay-server> 443. Check the application's status page — the relay infrastructure may be down. If all connectivity checks pass, the problem is likely in the application's authentication or session negotiation.

TCP vs UDP and Port Ranges

Understanding the transport protocol tells you which commands to use and how to interpret results.

TCP — Transmission Control Protocol

Connection-oriented: a three-way handshake must complete before any data flows. Host A sends SYN → Host B replies SYN-ACK → Host A sends ACK → connection ESTABLISHED.

Guaranteed delivery: every packet is acknowledged. No acknowledgement = automatic retransmission.

Testable directly: because a connection must be established, telnet and nc give a clear result.

Handshake failure meanings:
SYN sent, no SYN-ACK → nothing listening on that port, or firewall drops SYN. Check ss -tuln and iptables on Host B.
SYN-ACK received, connection still fails → Host A's firewall dropping the returning SYN-ACK. Check firewall on Host A.
ESTABLISHED but drops immediately → application on Host B accepted then closed. Check app logs on Host B.
Refused vs timeout — memorise this distinction:
Connection refused = Host B actively rejected it. Nothing is listening on that port. The OS returned an error immediately.
Timeout / no response = a firewall is silently dropping the packet. The packet may never reach the service. These two outcomes point to completely different problems.

UDP — User Datagram Protocol

Connectionless: data sent immediately, no handshake. Sender does not know if it arrived.

No guaranteed delivery: packets can be lost silently. No automatic retransmission.

Harder to test: telnet does not work for UDP — it only tests TCP. Use nc -u <IP> <port> or check application logs.

Used for: DNS (port 53), DHCP (67/68), video streaming, VoIP, online gaming — where speed matters more than perfect delivery.

OSI Model — Reference

The OSI (Open Systems Interconnection) model is a conceptual framework that divides network communication into 7 distinct layers. Each layer has a specific job and communicates only with the layers directly above and below it. The model is used universally to describe, design, and debug network systems.

OSI vs TCP/IP: the OSI model has 7 layers and is the theoretical standard. The TCP/IP model has 4 layers and is what the internet actually uses. The rightmost column shows how the OSI layers map onto TCP/IP. Layers 5, 6, and 7 in OSI all collapse into one "Application" layer in TCP/IP.

Notes on specific protocols and devices

DHCP — why it is L7 even though it assigns IP addresses ▶

DHCP (Dynamic Host Configuration Protocol) assigns IP addresses, which feels like an L3 concern. But DHCP is classified as an application layer (L7) protocol because of how it works mechanically: it is a request-response protocol running over UDP (L4), it uses port numbers (67 for server, 68 for client), and it has its own message format with fields, options, and acknowledgements — all characteristics of an application layer protocol.

The fact that its output (an IP address) is used at L3 does not change its own classification. DNS is the same — it resolves hostnames to IPs (an L3 concept) but is itself an L7 protocol because it runs as a request-response application over UDP/TCP.

ARP — the bridge between L2 and L3 ▶

ARP (Address Resolution Protocol) translates IP addresses (L3) into MAC addresses (L2) so that frames can be built and delivered. It is technically defined as operating between L2 and L3 — sometimes called L2.5. ARP does not use IP itself; it is sent directly inside an Ethernet frame with a special EtherType value. It cannot cross routers — ARP operates only within a local subnet.

Firewall — which layer? ▶

Firewalls exist at multiple layers depending on their type. A basic packet filter firewall operates at L3 (IP addresses) and L4 (port numbers). A stateful firewall also tracks TCP connection state at L4. An application firewall (WAF — Web Application Firewall) operates at L7 and can inspect HTTP content. A single firewall device may enforce rules across all these layers simultaneously.

Switch — Layer 2 vs Layer 3 ▶

A basic switch operates at L2 — it forwards frames using MAC addresses and its CAM table. It has no awareness of IP addresses. A Layer 3 switch can also route packets between subnets using IP addresses, doing the job of a router internally. The same physical device can perform both functions, but they are two separate operations at two separate layers.

NIC — which layer? ▶

A NIC (Network Interface Card) spans both L1 and L2. At L1 it handles the physical transmission and reception of electrical signals or radio waves. At L2 it has a burned-in MAC address and handles frame assembly and disassembly. The driver software that controls the NIC bridges both layers and presents a single network interface to the OS.
