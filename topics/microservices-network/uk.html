00 What is microservice networking CONCEPT
In a microservices architecture, each service is a separate process — often a separate container or VM. Services must communicate over a network to do anything useful. Unlike a monolith where function calls are in-process, every service-to-service call crosses a network boundary and can fail for network reasons.

Key concepts

ConceptWhat it meansWhy it matters for QA
Service discoveryMechanism by which Service A finds Service B's address at runtime. Can be internal DNS, environment variables, or a service registry.If discovery is broken, services can't find each other — looks like a network failure but is a configuration issue.
Internal DNSDNS resolver available only inside the container network or cluster. Resolves service names like payment-service to their current IP.Works only inside the network. Calling a service name from your host machine will fail — it doesn't exist in external DNS.
Health check endpointAn endpoint (/health, /ping) the service exposes to report whether it is alive and ready to handle traffic.Used by load balancers and orchestrators to route traffic. A service can be running but unhealthy — still receives no traffic.
Circuit breakerA pattern that stops routing calls to a service that keeps failing, to prevent cascading failures across the system.A tripped circuit breaker returns errors immediately without attempting the network call — looks like the service is down.
API GatewayA single entry point that receives external requests and routes them to the correct internal service.Gateway errors (502, 504) usually mean the gateway itself is healthy but can't reach the upstream service.
Service meshInfrastructure layer (Istio, Linkerd) that proxies all service-to-service traffic via sidecars. Adds observability, retries, and mTLS.If a service mesh is misconfigured, it silently drops traffic. Check sidecar proxy logs, not just the app logs.

How services find each other

INTERNAL DNS (Docker / Kubernetes)
Service name resolves to its current IP automatically. http://payment-service/charge — no IP needed. Most common in container environments. Breaks if the service name doesn't exist, the service is in a different namespace, or the container is outside the network.
ENVIRONMENT VARIABLES
Address injected at startup: PAYMENT_HOST=192.168.1.5, PAYMENT_PORT=8080. Simple and explicit. Breaks when IPs change and the variable isn't updated — service silently calls the wrong host.
SERVICE REGISTRY (Consul, Eureka)
Services register themselves on startup; callers query the registry to get the current address. More dynamic than env vars. Breaks if the service fails to register, or the registry itself is unreachable.
HARDCODED CONFIG
Explicit IP or hostname in a config file. Easy to set up, fragile in practice. Common in early-stage projects. Breaks on any IP change, redeployment to a different host, or environment switch.
CRITICAL DISTINCTION — NETWORK ERROR vs APPLICATION ERROR

TCP connection never established (ECONNREFUSED, ETIMEDOUT, ENOTFOUND) → the problem is in the network layer — DNS, routing, firewall, service not running, wrong port.

TCP connection established, error response received (4xx, 5xx) → the network is working. The problem is in the application layer — wrong credentials, missing data, app-level bug, or the app failing to reach its own dependency.

01 Setup types overview CONCEPT
Microservices can run in several different configurations depending on the development or testing stage. Each setup has its own networking model, common failure modes, and debug toolset.
SetupWhere services runHow they communicateService discoveryTypical use
Docker ComposeAll containers on one machineDocker bridge network — internal DNS by service nameDocker internal DNS (service-name)Local development, local integration testing
Separate hostsDifferent VMs or physical machinesDirect TCP over the network (IP:port) or via a reverse proxyHardcoded IP/hostname, /etc/hosts, or external DNSStaging, simple production, legacy setups
Kubernetes clusterPods distributed across nodesClusterIP + Kubernetes internal DNSKubernetes DNS (svc.namespace.svc.cluster.local)Production, cloud staging environments
HybridMix — some local, some on remote stagingVPN, SSH tunnel, or port-forward for cross-boundary callsCombination: local Docker DNS + remote service URLsDev testing against a shared staging environment

Can microservices run on completely separate hosts?

Yes — this is the multi-host setup. Each service runs on its own VM or physical server, connected over a network. This was common before containers became standard and still appears in staging environments, cloud VMs, or when services have different hardware requirements. The main challenges compared to Docker/Kubernetes: no automatic service discovery, firewall rules must be configured manually, and services must bind to 0.0.0.0 (not 127.0.0.1) to accept connections from other hosts.

02 Docker Compose — local setup DOCKER
Docker Compose is the most common local microservices setup. All containers share a virtual bridge network created by Compose. Each service is reachable by its name in docker-compose.yml — no IPs needed. Internal DNS works only inside containers; calling service names from your host machine will fail.

How Docker networking works

DOCKER COMPOSE NETWORK MODEL
1
DOCKER COMPOSE STARTS
Creates a shared bridge network named <project>_default. All services in the file are attached to this network unless configured otherwise.
2
SERVICE NAME = HOSTNAME
Each service gets a hostname matching its name in the YAML. payment-service in the YAML → http://payment-service:8080 is reachable from any other container on the same network.
3
HOST MACHINE ACCESS
From your host machine (outside Docker), service names don't resolve. You must use localhost:mapped-port. Mapped ports are declared in the ports: section of the YAML.
Example: ports: "8080:80" → accessible on your host as localhost:8080

Common issues and fixes

SymptomRoot causeFix
ENOTFOUND service-nameServices are on different Docker networks, or the calling service is running outside DockerCheck networks: in docker-compose.yml — all services must share the same network. If calling from your host, use localhost:mapped-port instead.
ECONNREFUSED service-name:portThe target service is not running, has crashed, or is listening on a different portdocker ps to confirm it's up. docker logs <container> for crash reason. Verify the internal port in the service's own config matches what you're calling.
Service A can't reach B, but B is runningB started but is not yet ready (still initializing), or A cached a failed DNS result before B was upAdd depends_on with condition: service_healthy in docker-compose.yml. Or restart A after B is fully up.
Works locally when calling localhost, fails in containerlocalhost inside a container refers to the container itself, not your host machineUse the service name instead of localhost. To reach your host from a container: host.docker.internal (Docker Desktop) or the host's bridge IP.
Intermittent timeouts between servicesThe target container is restarting (crash loop) or is under memory pressure and GC-pausingdocker stats to check resource usage. docker logs <container> --follow to watch for restarts.

Debug commands

DOCKER COMPOSE — ESSENTIAL DEBUG COMMANDS
# Are all containers running?
docker ps
docker compose ps

# Read logs from a specific service
docker compose logs payment-service
docker compose logs --follow --tail=50 payment-service

# Test DNS resolution from inside a container
docker exec -it <container-name> nslookup payment-service

# Test HTTP connectivity from inside a container
docker exec -it <container-name> curl http://payment-service:8080/health

# Inspect the shared network — see all containers and their IPs
docker network ls
docker network inspect <project>_default

# Open a shell inside a container to debug interactively
docker exec -it <container-name> sh
QA TEST ANGLES — DOCKER COMPOSE
① Verify /health endpoint of every service returns 200 before running integration tests — don't assume a running container is a healthy one.
② Test with one service deliberately stopped — the calling service should return a clear error, not hang indefinitely (timeout should be configured).
③ Check depends_on ordering — start services in wrong order and verify the stack recovers or fails with a clear message.
④ Test port conflicts: try starting the stack when another process is using a mapped port — Compose should fail with a clear error, not silently use a different port.
03 Separate hosts — services on different machines MULTI-HOST
In a multi-host setup, each service (or group of services) runs on a separate VM or physical server. There is no automatic service discovery — services must be configured with the explicit addresses of their dependencies. Each machine is a separate network entity with its own firewall rules.

Critical: service binding address

MOST COMMON MULTI-HOST FAILURE

A service listening on 127.0.0.1:8080 is only reachable from the same machine. To accept connections from other hosts, the service must bind to 0.0.0.0:8080 (all interfaces) or the specific network interface IP.

This is invisible from a running process perspective — the service appears healthy but is unreachable from any other host.

CHECK WHAT THE SERVICE IS BOUND TO
# Linux — check listening sockets
ss -tuln | grep 8080
# 0.0.0.0:8080  → reachable from any host on the network ✓
# 127.0.0.1:8080 → only reachable locally — THIS blocks multi-host access ✗

# Windows
netstat -ano | findstr 8080

Common issues and fixes

SymptomRoot causeFix
ETIMEDOUT connecting to other hostFirewall on the target machine is blocking the port (silently drops packets)From the calling host: Test-NetConnection -ComputerName <IP> -Port <N> / nc -zv <IP> <port>. Check firewall rules on the target: iptables -L INPUT -n -v.
ECONNREFUSED connecting to other hostService not running on the target, or bound to 127.0.0.1 onlySSH into target, check ss -tuln. If bound to 127.0.0.1, update the service's bind config.
DNS name doesn't resolveNo DNS entry for the hostname; hosts file not configuredAdd a temporary entry to /etc/hosts (Linux) or C:\Windows\System32\drivers\etc\hosts (Windows) on the calling machine. Or use the IP directly to confirm connectivity first.
Works from the server itself, fails from another hostService bound to 127.0.0.1 or firewall blocking the portCheck binding (see above). Check firewall.
SSL/TLS certificate errorsCertificate was issued for localhost or a different hostnameThe cert's CN/SAN must match the hostname being called. Check with openssl s_client -connect <host>:<port>.
Connection works but is very slowDNS reverse lookup on every connection, or routing goes through an unexpected pathUse traceroute / tracert to check the actual path. Disable DNS reverse lookup if not needed.

Firewall and connectivity checks

CONNECTIVITY CHECK FROM CALLING HOST
# Windows — test TCP port reachability
Test-NetConnection -ComputerName 192.168.1.50 -Port 8080

# Linux — test TCP port
nc -zv 192.168.1.50 8080
# or
telnet 192.168.1.50 8080

# Trace the route to the target
traceroute 192.168.1.50    # Linux
tracert 192.168.1.50       # Windows
FIREWALL INSPECTION ON TARGET HOST (Linux)
# List all input rules
iptables -L INPUT -n -v

# Check if a specific port is allowed
iptables -L INPUT -n -v | grep 8080
QA TEST ANGLES — MULTI-HOST
① From the calling host, test the target port directly before running any application tests — confirm basic TCP connectivity first.
② Verify the service is bound to the correct interface: ss -tuln must show 0.0.0.0:port, not 127.0.0.1:port.
③ Test from both directions — can A reach B AND can B reach A? Firewall rules are often asymmetric.
④ Verify DNS resolves to the correct IP on the calling host: nslookup <hostname> — stale /etc/hosts entries or DNS cache can point to old IPs after a server move.
04 Kubernetes cluster KUBERNETES
In Kubernetes, services communicate via ClusterIP — a stable virtual IP assigned to each Service object. Kubernetes internal DNS resolves service names automatically. Services are not reachable from outside the cluster unless explicitly exposed. Pods are ephemeral — their IPs change on restart; always call the Service name, never the Pod IP.

Kubernetes DNS — how service names resolve

FormExampleWorks from
Short namepayment-serviceSame namespace only
Namespace-qualifiedpayment-service.paymentsAny namespace in the cluster
Full DNS namepayment-service.payments.svc.cluster.localAny namespace in the cluster

Service types — what is reachable from where

TypeReachable fromUse case
ClusterIPInside the cluster onlyDefault. Service-to-service calls within the cluster.
NodePortAny machine that can reach a cluster nodeExposing a service for external testing without a load balancer.
LoadBalancerInternet (via cloud provider load balancer)Production external exposure.
ExternalNameInside the cluster → resolves to external DNSAliasing an external service so internal code uses a consistent name.

Common issues and fixes

SymptomRoot causeFix
ENOTFOUND service-name from inside a podWrong namespace — short name only works within the same namespaceUse the namespace-qualified name: service-name.namespace. Check kubectl get svc -n <namespace>.
Service exists, DNS resolves, but no responseService has no healthy endpoints — pods are not running or don't match the selectorkubectl get endpoints <service> -n <ns> — must not be empty. Check pod labels match service selector.
Intermittent failures (not 100%)One pod is unhealthy but still in the endpoints list (readiness probe not configured or slow)kubectl describe pod <pod> — check Events and readiness probe status. Configure a proper readiness probe.
Works inside the cluster, not reachable from outsideService type is ClusterIP — only accessible inside the clusterUse kubectl port-forward svc/<name> <local-port>:<service-port> for local testing. Change to NodePort/LoadBalancer for persistent external access.
Sudden failures after a new deploymentNew pods receive traffic before they are ready (no readiness probe)Add a readinessProbe to the deployment. Traffic is only sent to pods that pass the probe.
Connection silently blocked between specific servicesNetworkPolicy is restricting traffic between namespaces or pod selectorskubectl get networkpolicies -n <ns>. NetworkPolicy defaults to block-all if any policy exists in the namespace.
Service mesh sidecar errors (Istio/Linkerd)mTLS misconfiguration, sidecar not injected, policy mismatchCheck sidecar logs: kubectl logs <pod> -c istio-proxy. Verify PeerAuthentication and DestinationRule policies.

Debug commands

KUBERNETES — ESSENTIAL DEBUG COMMANDS
# Are all pods running and ready?
kubectl get pods -n <namespace>
kubectl describe pod <pod-name> -n <namespace>   # look at Events section

# Does the service exist and have healthy endpoints?
kubectl get svc -n <namespace>
kubectl get endpoints <service-name> -n <namespace>  # empty = no healthy pods

# Test DNS resolution from inside a pod
kubectl exec -it <pod> -n <namespace> -- nslookup <service-name>
kubectl exec -it <pod> -n <namespace> -- nslookup <service-name>.<namespace>.svc.cluster.local

# Test HTTP connectivity from inside a pod
kubectl exec -it <pod> -n <namespace> -- curl http://<service-name>/health

# Expose a ClusterIP service to your local machine for testing
kubectl port-forward svc/<service-name> 8080:80 -n <namespace>

# Stream pod logs
kubectl logs -f <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous   # logs from crashed container

# Check network policies
kubectl get networkpolicies -n <namespace>
kubectl describe networkpolicy <policy-name> -n <namespace>
QA TEST ANGLES — KUBERNETES
① Always check kubectl get endpoints before concluding a service is broken — an empty endpoints list means no pod is passing its readiness probe, not a network problem.
② Test cross-namespace calls explicitly — a service name that works within a namespace fails silently from another namespace without the fully-qualified name.
③ Verify readiness probes are configured: deploy a version that takes 30s to start — traffic should not hit it until it's ready.
④ Test NetworkPolicy if present: deploy a pod in a restricted namespace and confirm it can reach only the allowed services and nothing else.
⑤ After a rollout, check that the old pods are fully terminated before considering the deploy complete — traffic can still hit terminating pods.
05 Hybrid — local service + remote staging HYBRID
A hybrid setup runs one or two services locally (for active development) while the rest of the stack lives on a shared staging environment. The challenge is bridging two networks: your local machine and the remote cluster, in both directions.

Direction 1 — your local service calling remote services

APPROACH

Point your local service's environment variables at the remote service URLs directly. Most staging environments expose services via an ingress or load balancer with real URLs. No tunneling needed for outbound calls.

EXAMPLE — OVERRIDE CONFIG FOR LOCAL DEV
# .env.local — override staging URLs
PAYMENT_SERVICE_URL=https://payment.staging.company.com
AUTH_SERVICE_URL=https://auth.staging.company.com

Direction 2 — remote services calling your local service (callbacks, webhooks)

This is the harder direction. Remote services can't reach localhost. Options:

ToolHow it worksBest for
kubectl port-forwardTunnels a remote Kubernetes service port to your local machine. One-directional: local → remote.Calling remote services from local. Does not solve remote → local callbacks.
ngrok / localtunnelCreates a public URL that tunnels to your localhost port. Remote services call the ngrok URL; traffic forwards to your machine.Webhook testing, OAuth callbacks, any scenario where the remote service must initiate the call.
SSH reverse tunnelssh -R 8080:localhost:8080 user@staging-server — exposes your local port on the remote server.When you have SSH access to the staging server and need it to call back.
Mock / stub the local serviceDeploy a stub of your service to staging instead of trying to bridge networks.When the callback logic is simple and can be stubbed.

Common issues

SymptomCauseFix
Local service can't reach stagingStaging is in a private network with no public endpointConnect VPN, or use kubectl port-forward to expose the service locally.
Works on your machine, fails when deployedHardcoded localhost URLs in config that don't exist in the clusterReplace all localhost references with service names or env vars. Never hardcode localhost in shared config.
Authentication fails between environmentsDifferent secrets, tokens, or signing keys per environmentCheck environment-specific secrets. Confirm the token issued in one env is not being used in another.
Remote callbacks failYour local machine has no public IP; remote service can't initiate the connectionUse ngrok: ngrok http 8080 — gives you a public URL that forwards to your local port.
QA TEST ANGLES — HYBRID
① Verify all env vars are pointing at the correct environment before testing — it's easy to accidentally run tests against production URLs in a hybrid config.
② Test the full request flow end-to-end with tracing or logging enabled to confirm which environment each service is in and that responses are from the expected source.
③ For webhook/callback scenarios: use ngrok and inspect its dashboard to see the exact request the remote service sends — useful for verifying payload format.
06 Symptoms reference — how to tell it's a network issue DIAGNOSIS
The error message on the calling service tells you what happened at the TCP level. Learn to read these errors as precise diagnostic signals rather than generic "connection failed" messages.

TCP-level errors

ErrorMeaningWhere to look
ECONNREFUSEDTCP connection actively rejected by the target. The target host is reachable, but nothing is listening on that port — or a firewall sent a RST.Is the service running? Is it listening on the right port and right interface (0.0.0.0 not 127.0.0.1)?
ETIMEDOUT / request hangsNo response at all. Either the host is unreachable, or a firewall is silently dropping the packets.Can you ping the host? Can you reach the port (nc -zv, Test-NetConnection)? Check firewall rules.
ECONNRESETConnection was established but then forcibly closed mid-flight. The remote end sent a RST.Proxy timeout, load balancer killing idle connections, app crashing during request, TLS mismatch.
ENOTFOUND <hostname> / getaddrinfo failedDNS resolution failed — the hostname does not exist in the DNS this service is using.Is the service name correct? Is the service in the right namespace (K8s)? Is the container on the right Docker network?
DEPTH_ZERO_SELF_SIGNED_CERT / TLS errorsTLS certificate is self-signed, expired, or the hostname doesn't match the cert's CN/SAN.Check cert with openssl s_client -connect host:port. Verify cert matches the hostname being called.

HTTP-level errors from a proxy or gateway

StatusMeaningWhere to look
502 Bad GatewayThe proxy/gateway received an invalid response from the upstream service, or the upstream was unreachable.Check the upstream service's logs and health. The proxy itself is healthy — its upstream is not.
503 Service UnavailableNo healthy upstream instances available. All instances failed health checks, or the service is at capacity.kubectl get endpoints (K8s) or check load balancer backend health. Scale up or fix failing pods.
504 Gateway TimeoutThe proxy reached the upstream but got no response within the timeout. The upstream is alive but too slow or hanging.Check upstream service logs for slow queries, locks, or high CPU. Increase timeout if the operation is legitimately slow.

Behavioral patterns that indicate network problems

PatternWhat it suggests
Consistent ~30 second timeoutDefault TCP timeout — the host exists but the port is silently dropped by a firewall. Not a slow service — the packet never arrived.
Works calling localhost, fails calling service nameService discovery / DNS is broken. The service is healthy but not findable by name.
Intermittent failures (not 100%, retries fix it)Load balancer routing traffic to an unhealthy pod. One instance is bad; others work. Check pod health.
A → B works, B → A failsAsymmetric firewall rule or NetworkPolicy. Rules were only configured in one direction.
Works in local Docker, fails in KubernetesNamespace mismatch, NetworkPolicy blocking, or service not exposed correctly. K8s networking is stricter than Docker by default.
Works from one service, fails from another calling the same dependencyNetworkPolicy allows traffic from the first service's pod selector but not the second's. Or the second service has wrong env vars (different URL).
Failures only appear under loadConnection pool exhausted, too many concurrent connections hitting a limit, or one pod overwhelmed while others are fine.
07 Debug workflow WORKFLOW
A structured approach to diagnosing microservice network failures. Start with quick checks that rule out entire categories of problems before reaching for advanced tooling.

Step 1 — Identify which call is failing

Determine the exact service-to-service call that fails. Check the logs of the calling service — it reports what happened at the TCP level. The called service may show nothing because the connection never arrived.

KEY PRINCIPLE

Read logs on the service that is making the call, not the one being called. The error message is on the caller's side. The called service sees nothing if the packet never arrived.

Step 2 — Pre-flight: rule out architectural mismatches

  • Does the app require internet? Does this environment have internet access?
  • Is the target service actually running? (docker ps, kubectl get pods, systemctl status)
  • Is the target service healthy? Call its /health endpoint directly.
  • Are credentials / tokens correct for this environment?

Step 3 — Triage the network layer

NETWORK TRIAGE — SPLIT THE STACK WITH TWO CHECKS
A
TOP CHECK — Can you reach the service?
From inside the calling container/pod, curl http://service-name/health. If it responds (any HTTP status), L1–L6 are working. The problem is at the application layer. If it fails with ENOTFOUND → DNS problem. If ECONNREFUSED → service not running or wrong port. If ETIMEDOUT → firewall/routing.
B
MIDDLE CHECK — Does ping succeed?
ping <service-name-or-IP>. Success confirms L1–L3 are healthy. If ping succeeds but curl fails → problem is at L4 (port, firewall rule) or L7 (app). If ping fails → problem is at L1–L3 (routing, DNS, physical).

Step 4 — Drill down by setup type

SetupDNS checkPort checkLogs
Docker Composedocker exec <c> nslookup service-namedocker exec <c> curl http://service-name:port/healthdocker compose logs service-name
Separate hostsnslookup <hostname> on the calling machinenc -zv <IP> <port> / Test-NetConnectionSSH into target, check app logs and ss -tuln
Kuberneteskubectl exec <pod> -- nslookup service.namespacekubectl exec <pod> -- curl http://service/healthkubectl logs <pod> + kubectl get endpoints
HybridVerify env var URLs are correct for the environmentcurl <staging-url>/health from your local machineCheck both local service logs and remote staging logs

Step 5 — If still stuck

  • Distributed tracing (Jaeger, Zipkin, AWS X-Ray) — pull the trace for the failing request. Shows exactly which hop failed and at what latency.
  • Packet capture — tcpdump -i eth0 port 8080 on the target. If you see the SYN but no SYN-ACK, the service is not listening. If you see no packets at all, the traffic never arrived (routing/firewall).
  • Service mesh dashboard (Kiali for Istio) — shows real-time traffic flow, error rates, and latency per service pair.
