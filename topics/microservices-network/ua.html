00 Що таке мережа мікросервісів КОНЦЕПЦІЯ
В архітектурі мікросервісів кожен сервіс — це окремий процес, часто окремий контейнер або VM. Сервіси повинні спілкуватися через мережу, щоб виконувати корисну роботу. На відміну від моноліту, де функціональні виклики відбуваються всередині процесу, кожен виклик між сервісами перетинає мережеву межу і може зазнати збою з мережевих причин.

Ключові концепції

КонцепціяЩо означаєЧому важливо для QA
Виявлення сервісівМеханізм, за допомогою якого Сервіс A знаходить адресу Сервісу B під час виконання. Може бути внутрішній DNS, змінні середовища або реєстр сервісів.Якщо виявлення зламано, сервіси не можуть знайти один одного — виглядає як мережевий збій, але є проблемою конфігурації.
Внутрішній DNSDNS-резолвер, доступний лише всередині контейнерної мережі або кластера. Розв'язує імена сервісів на кшталт payment-service до їхнього поточного IP.Працює лише всередині мережі. Виклик імені сервісу з вашої хост-машини завершиться невдачею — воно не існує в зовнішньому DNS.
Ендпоінт перевірки стануЕндпоінт (/health, /ping), який сервіс відкриває, щоб повідомити, чи він живий і готовий обробляти трафік.Використовується балансувальниками навантаження та оркестраторами для маршрутизації трафіку. Сервіс може бути запущений, але нездоровим — він все одно не отримає трафік.
Circuit BreakerПатерн, який припиняє маршрутизацію викликів до сервісу, що постійно збоїть, щоб запобігти каскадним збоям.Спрацьований circuit breaker негайно повертає помилки без спроби мережевого виклику — виглядає як неробочий сервіс.
API GatewayЄдина точка входу, що приймає зовнішні запити та маршрутизує їх до правильного внутрішнього сервісу.Помилки шлюзу (502, 504) зазвичай означають, що сам шлюз здоровий, але не може дістатися до upstream-сервісу.
Service MeshІнфраструктурний шар (Istio, Linkerd), що проксує весь трафік між сервісами через sidecar-и. Додає спостережуваність, повторні спроби та mTLS.Якщо service mesh неправильно налаштований, він мовчки відкидає трафік. Перевіряйте логи sidecar-проксі, а не лише логи застосунку.

Як сервіси знаходять один одного

ВНУТРІШНІЙ DNS (Docker / Kubernetes)
Ім'я сервісу автоматично розв'язується до його поточного IP. http://payment-service/charge — IP не потрібен. Найпоширеніше в контейнерних середовищах. Ламається, якщо ім'я сервісу не існує, сервіс знаходиться в іншому просторі імен або контейнер знаходиться поза мережею.
ЗМІННІ СЕРЕДОВИЩА
Адреса впроваджується при запуску: PAYMENT_HOST=192.168.1.5, PAYMENT_PORT=8080. Простий та явний спосіб. Ламається при зміні IP, якщо змінна не оновлена — сервіс мовчки звертається до неправильного хоста.
РЕЄСТР СЕРВІСІВ (Consul, Eureka)
Сервіси реєструють себе при запуску; клієнти запитують реєстр для отримання поточної адреси. Динамічніше ніж змінні середовища. Ламається, якщо сервіс не зміг зареєструватися, або якщо сам реєстр недоступний.
ЖОРСТКО ЗАКОДОВАНА КОНФІГУРАЦІЯ
Явний IP або hostname у конфіг-файлі. Просто налаштувати, але нестабільно на практиці. Поширено на ранніх етапах проекту. Ламається при будь-якій зміні IP, перерозгортанні на іншому хості або перемиканні середовища.
КРИТИЧНА ВІДМІННІСТЬ — МЕРЕЖЕВА ПОМИЛКА vs ПОМИЛКА ЗАСТОСУНКУ

TCP-з'єднання ніколи не встановлено (ECONNREFUSED, ETIMEDOUT, ENOTFOUND) → проблема в мережевому шарі — DNS, маршрутизація, брандмауер, сервіс не запущений, неправильний порт.

TCP-з'єднання встановлено, отримано помилкову відповідь (4xx, 5xx) → мережа працює. Проблема в шарі застосунку — невірні облікові дані, відсутні дані, помилка на рівні коду або застосунок не може дістатися до власних залежностей.

Мікросервіси можуть працювати в кількох різних конфігураціях залежно від етапу розробки або тестування. Кожна конфігурація має власну мережеву модель, типові режими збоїв та набір інструментів для відлагодження.

Чи можуть мікросервіси працювати на повністю окремих хостах?

Так — це конфігурація з кількома хостами. Кожен сервіс працює на власній VM або фізичному сервері, з'єднаних через мережу. Це було поширеним до стандартизації контейнерів і досі зустрічається в staging-середовищах, хмарних VM або коли сервіси мають різні апаратні вимоги. Основні складнощі порівняно з Docker/Kubernetes: немає автоматичного виявлення сервісів, правила брандмауера необхідно налаштовувати вручну, і сервіси повинні прив'язуватися до 0.0.0.0 (а не 127.0.0.1), щоб приймати з'єднання з інших хостів.

02 Docker Compose — локальна конфігурація DOCKER
Docker Compose — найпоширеніша локальна конфігурація мікросервісів. Всі контейнери спільно використовують віртуальну bridge-мережу, створену Compose. Кожен сервіс доступний за своїм іменем з docker-compose.yml — IP-адреси не потрібні. Внутрішній DNS працює лише всередині контейнерів; виклик імен сервісів з вашої хост-машини завершиться невдачею.

Як працює мережа Docker

МЕРЕЖЕВА МОДЕЛЬ DOCKER COMPOSE
1
DOCKER COMPOSE ЗАПУСКАЄТЬСЯ
Створює спільну bridge-мережу з іменем <проект>_default. Всі сервіси у файлі підключаються до цієї мережі, якщо не налаштовано інакше.
2
ІМ'Я СЕРВІСУ = HOSTNAME
Кожен сервіс отримує hostname, що відповідає його імені у YAML. payment-service у YAML → http://payment-service:8080 доступний з будь-якого іншого контейнера в тій самій мережі.
3
ДОСТУП З ХОСТ-МАШИНИ
З вашої хост-машини (поза Docker) імена сервісів не розв'язуються. Необхідно використовувати localhost:зіставлений-порт. Зіставлені порти оголошуються у секції ports: YAML.
Приклад: ports: "8080:80" → доступно на вашому хості як localhost:8080

Типові проблеми та рішення

СимптомПершопричинаРішення
ENOTFOUND service-nameСервіси знаходяться в різних мережах Docker, або сервіс, що викликає, запущений поза DockerПеревірте networks: у docker-compose.yml — всі сервіси повинні спільно використовувати одну мережу. При виклику з хоста використовуйте localhost:зіставлений-порт.
ECONNREFUSED service-name:portЦільовий сервіс не запущений, аварійно завершився або слухає на іншому портуdocker ps для підтвердження запуску. docker logs <контейнер> для причини збою. Перевірте, що внутрішній порт у конфіг сервісу збігається з тим, що ви викликаєте.
Сервіс A не може дістатися до B, але B запущенийB запустився, але ще не готовий (ще ініціалізується), або A закешував невдалий DNS-результат до того, як B запустивсяДодайте depends_on з condition: service_healthy у docker-compose.yml. Або перезапустіть A після повного запуску B.

Переривчасті тайм-аути між сервісамиЦільовий контейнер перезапускається (crash loop) або перебуває під тиском пам'яті та робить паузи GCdocker stats для перевірки використання ресурсів. docker logs <контейнер> --follow для спостереження за перезапусками.

КУТИ ТЕСТУВАННЯ QA — DOCKER COMPOSE
① Перевірте, що ендпоінт /health кожного сервісу повертає 200 перед запуском інтеграційних тестів — не припускайте, що запущений контейнер є здоровим.
② Протестуйте з одним навмисно зупиненим сервісом — сервіс, що викликає, повинен повернути чітку помилку, а не завмирати безмежно (таймаут повинен бути налаштований).
③ Перевірте порядок depends_on — запустіть сервіси у неправильному порядку і переконайтеся, що стек відновлюється або завершується з чітким повідомленням.
④ Протестуйте конфлікти портів: спробуйте запустити стек, коли інший процес вже використовує зіставлений порт — Compose повинен завершитися з чіткою помилкою, а не мовчки використовувати інший порт.
03 Окремі хости — сервіси на різних машинах МУЛЬТИХОСТ
У конфігурації з кількома хостами кожен сервіс (або група сервісів) працює на окремій VM або фізичному сервері. Автоматичного виявлення сервісів немає — сервіси повинні бути налаштовані з явними адресами своїх залежностей. Кожна машина є окремою мережевою сутністю з власними правилами брандмауера.

Критично: адреса прив'язки сервісу

НАЙПОШИРЕНІШИЙ ЗБІЙ ПРИ МУЛЬТИХОСТІ

Сервіс, що слухає на 127.0.0.1:8080, доступний лише з тієї самої машини. Щоб приймати з'єднання з інших хостів, сервіс повинен прив'язатися до 0.0.0.0:8080 (всі інтерфейси) або до конкретного IP мережевого інтерфейсу.

Це непомітно з точки зору запущеного процесу — сервіс виглядає здоровим, але є недоступним з будь-якого іншого хоста.

ПЕРЕВІРКА АДРЕСИ ПРИВ'ЯЗКИ СЕРВІСУ
# Linux — перевірка сокетів, що слухають
ss -tuln | grep 8080
# 0.0.0.0:8080  → доступний з будь-якого хоста в мережі ✓
# 127.0.0.1:8080 → доступний лише локально — ЦЕ блокує мультихост-доступ ✗

# Windows
netstat -ano | findstr 8080

Типові проблеми та рішення

СимптомПершопричинаРішення

Перевірки брандмауера та підключення

ПЕРЕВІРКА ПІДКЛЮЧЕННЯ З ХОСТА, ЩО ВИКЛИКАЄ
# Windows — перевірка доступності TCP-порту
Test-NetConnection -ComputerName 192.168.1.50 -Port 8080

# Linux — перевірка TCP-порту
nc -zv 192.168.1.50 8080
# або
telnet 192.168.1.50 8080

# Трасування маршруту до цілі
traceroute 192.168.1.50    # Linux
tracert 192.168.1.50       # Windows
ПЕРЕВІРКА БРАНДМАУЕРА НА ЦІЛЬОВОМУ ХОСТІ (Linux)
# Перелік всіх правил вхідного трафіку
iptables -L INPUT -n -v

# Перевірка дозволу конкретного порту
iptables -L INPUT -n -v | grep 8080
КУТИ ТЕСТУВАННЯ QA — МУЛЬТИХОСТ
① З хоста, що викликає, протестуйте цільовий порт напряму перед запуском будь-яких тестів застосунку — спочатку підтвердіть базове TCP-підключення.
② Перевірте, що сервіс прив'язаний до правильного інтерфейсу: ss -tuln повинен показувати 0.0.0.0:порт, а не 127.0.0.1:порт.
③ Протестуйте в обох напрямках — чи може A дістатися до B І чи може B дістатися до A? Правила брандмауера часто асиметричні.
④ Перевірте, що DNS розв'язується до правильного IP на хості, що викликає: nslookup <hostname> — застарілі записи /etc/hosts або кеш DNS можуть вказувати на старі IP після переміщення сервера.
04 Кластер Kubernetes KUBERNETES
У Kubernetes сервіси спілкуються через ClusterIP — стабільний віртуальний IP, призначений кожному об'єкту Service. Внутрішній DNS Kubernetes розв'язує імена сервісів автоматично. Сервіси недоступні ззовні кластера, якщо це не налаштовано явно. Поди — ефемерні: їхні IP змінюються при перезапуску; завжди викликайте ім'я Service, ніколи — IP пода.

① Завжди перевіряйте kubectl get endpoints перед висновком про несправність сервісу — порожній список ендпоінтів означає, що жоден под не проходить пробу готовності, а не мережеву проблему.
② Явно тестуйте виклики між просторами імен — ім'я сервісу, що працює всередині простору імен, мовчки збоїть з іншого без повного імені.
③ Перевірте налаштування проб готовності: розгорніть версію, що запускається 30с — трафік не повинен потрапляти до неї, доки вона не готова.
④ Протестуйте NetworkPolicy: розгорніть под в обмеженому просторі імен та переконайтеся, що він може досягти лише дозволених сервісів.
⑤ Після розгортання перевірте, що старі поди повністю завершились перед висновком про успішність — трафік може ще потрапляти до подів, що завершуються.
05 Гібридний — локальний сервіс + remote staging ГІБРИДНИЙ
Гібридна конфігурація запускає один або два сервіси локально (для активної розробки), тоді як решта стека знаходиться у спільному staging-середовищі. Складність полягає у з'єднанні двох мереж: вашої локальної машини та remote-кластера — в обох напрямках.

Напрям 1 — ваш локальний сервіс викликає remote-сервіси

ПІДХІД

Вкажіть змінні середовища вашого локального сервісу напряму на URL remote-сервісів. Більшість staging-середовищ відкривають сервіси через ingress або балансувальник навантаження з реальними URL. Тунелювання не потрібне для вихідних викликів.

ПРИКЛАД — ПЕРЕВИЗНАЧЕННЯ КОНФІГУРАЦІЇ ДЛЯ ЛОКАЛЬНОЇ РОЗРОБКИ
# .env.local — перевизначення URL staging
PAYMENT_SERVICE_URL=https://payment.staging.company.com
AUTH_SERVICE_URL=https://auth.staging.company.com

Напрям 2 — remote-сервіси викликають ваш локальний сервіс (callbacks, webhooks)

Це складніший напрям. Remote-сервіси не можуть дістатися до localhost. Варіанти:

ІнструментЯк працюєНайкраще для
kubectl port-forwardТунелює порт remote Kubernetes-сервісу до вашої локальної машини. Односпрямований: локальний → remote.Виклик remote-сервісів з локального. Не вирішує callback'и remote → локальний.
ngrok / localtunnelСтворює публічний URL, що тунелює до вашого localhost-порту. Remote-сервіси викликають ngrok URL; трафік пересилається на вашу машину.Тестування webhook'ів, OAuth callbacks, будь-який сценарій де remote-сервіс повинен ініціювати виклик.
SSH зворотний тунельssh -R 8080:localhost:8080 user@staging-server — відкриває ваш локальний порт на remote-сервері.Коли є SSH-доступ до staging-сервера і потрібен callback.
Мок / стаб локального сервісуРозгортання заглушки вашого сервісу на staging замість спроби з'єднати мережі.Коли логіка callback проста та може бути застаблена.

КУТИ ТЕСТУВАННЯ QA — ГІБРИДНИЙ
① Перевірте, що всі змінні середовища вказують на правильне середовище перед тестуванням — легко випадково запустити тести проти URL продакшена у гібридній конфігурації.
② Протестуйте повний потік запиту наскрізно з увімкненим трасуванням або логуванням — переконайтеся, яке середовище використовує кожен сервіс і що відповіді надходять з очікуваного джерела.
③ Для сценаріїв webhook/callback: використовуйте ngrok та перевіряйте його дашборд, щоб побачити точний запит, який надсилає remote-сервіс — корисно для перевірки формату payload.
06 Довідник симптомів — як зрозуміти, що проблема в мережі ДІАГНОСТИКА
Повідомлення про помилку на сервісі, що викликає, розповідає вам, що сталося на рівні TCP. Навчіться читати ці помилки як точні діагностичні сигнали, а не як загальне «з'єднання не вдалося».

Помилки рівня TCP

ПомилкаЗначенняДе шукати
ECONNREFUSEDTCP-з'єднання активно відхилено ціллю. Цільовий хост доступний, але на цьому порту нічого не слухає — або брандмауер надіслав RST.Чи запущений сервіс? Чи він слухає на правильному порту та правильному інтерфейсі (0.0.0.0, а не 127.0.0.1)?
ETIMEDOUT / запит зависВідповіді немає взагалі. Або хост недоступний, або брандмауер мовчки відкидає пакети.Чи можна пінгувати хост? Чи можна дістатися до порту (nc -zv, Test-NetConnection)? Перевірте правила брандмауера.
ECONNRESETЗ'єднання встановлено, але потім примусово закрито в процесі. Інша сторона надіслала RST.Тайм-аут проксі, балансувальник навантаження вбиває неактивні з'єднання, застосунок аварійно завершується під час запиту, невідповідність TLS.
ENOTFOUND <hostname> / getaddrinfo failedDNS-розв'язання не вдалося — hostname не існує в DNS, що використовує цей сервіс.Чи правильне ім'я сервісу? Чи знаходиться сервіс у правильному просторі імен (K8s)? Чи знаходиться контейнер у правильній мережі Docker?
DEPTH_ZERO_SELF_SIGNED_CERT / TLS-помилкиTLS-сертифікат є самопідписаним, застарілим або hostname не відповідає CN/SAN сертифіката.Перевірте сертифікат: openssl s_client -connect хост:порт. Переконайтеся, що сертифікат відповідає hostname, що викликається.

СтатусЗначенняДе шукати

Поведінкові патерни, що вказують на мережеві проблеми

ПатернЩо свідчить
Стабільний тайм-аут ~30 секундТиповий TCP-тайм-аут — хост існує, але порт мовчки відкидається брандмауером. Не повільний сервіс — пакет ніколи не прибув.
Працює при виклику localhost, не працює з іменем сервісуВиявлення сервісів / DNS зламано. Сервіс здоровий, але не знаходиться за іменем.
Переривчасті збої (не 100%, повторні спроби виправляють)Балансувальник навантаження маршрутизує трафік до нездорового пода. Один екземпляр несправний; інші працюють.
A → B працює, B → A не працюєАсиметричне правило брандмауера або NetworkPolicy. Правила налаштовані лише в одному напрямку.
Працює в локальному Docker, не працює в KubernetesНевідповідність простору імен, блокування NetworkPolicy або сервіс неправильно відкритий. K8s за замовчуванням суворіший за Docker.

07 Процес відлагодження ПРОЦЕС
Структурований підхід до діагностики мережевих збоїв мікросервісів. Починайте зі швидких перевірок, що виключають цілі категорії проблем, перш ніж використовувати складні інструменти.

Крок 1 — Визначте, який виклик завершується невдачею

Визначте точний виклик між сервісами, що збоїть. Перевірте логи сервісу, що викликає — він повідомляє, що сталося на рівні TCP. Сервіс, що викликається, може нічого не показувати, бо з'єднання ніколи не надійшло.

КЛЮЧОВИЙ ПРИНЦИП

Читайте логи сервісу, що здійснює виклик, а не того, що викликається. Повідомлення про помилку знаходиться на стороні викликача. Сервіс, що викликається, нічого не бачить, якщо пакет ніколи не прибув.

Крок 2 — Попередня перевірка: виключіть архітектурні невідповідності

  • Чи потребує застосунок інтернету? Чи є доступ до інтернету в цьому середовищі?
  • Чи справді запущений цільовий сервіс? (docker ps, kubectl get pods, systemctl status)
  • Чи здоровий цільовий сервіс? Викличте його ендпоінт /health напряму.
  • Чи правильні облікові дані / токени для цього середовища?

Крок 3 — Тріаж мережевого шару

ТРІАЖ МЕРЕЖІ — РОЗДІЛІТЬ СТЕК ДВОМА ПЕРЕВІРКАМИ
A
ПЕРЕВІРКА ВЕРХНЬОГО РІВНЯ — Чи можна дістатися до сервісу?
Зсередини контейнера/пода, що викликає: curl http://service-name/health. Якщо відповідає (будь-який HTTP-статус) — L1–L6 працюють. Проблема на рівні застосунку. ENOTFOUND → DNS-проблема. ECONNREFUSED → сервіс не запущений або неправильний порт. ETIMEDOUT → брандмауер/маршрутизація.
B
СЕРЕДНЯ ПЕРЕВІРКА — Ping проходить?
ping <ім'я-сервісу-або-IP>. Успіх підтверджує здоров'я L1–L3. Ping проходить, curl — ні → проблема на L4 (порт, правило брандмауера) або L7 (застосунок). Ping не проходить → проблема на L1–L3 (маршрутизація, DNS, фізичне).

Крок 5 — Якщо все ще незрозуміло

  • Розподілене трасування (Jaeger, Zipkin, AWS X-Ray) — отримайте трасування для запиту, що збоїть. Показує точно, який перехід завершився невдачею і з якою затримкою.
  • Захоплення пакетів — tcpdump -i eth0 port 8080 на цілі. Якщо бачите SYN, але немає SYN-ACK — сервіс не слухає. Якщо пакетів немає взагалі — трафік ніколи не прибув (маршрутизація/брандмауер).
  • Дашборд service mesh (Kiali для Istio) — показує потік трафіку в реальному часі, рівень помилок та затримку для кожної пари сервісів.
