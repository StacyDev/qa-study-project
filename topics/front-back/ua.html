ВАЖЛИВО — ПЕРЕТИН З БАЛАНСУВАЛЬНИКОМ
Nginx може одночасно бути і зворотнім проксі, і балансувальником. У хмарних середовищах (AWS ALB, GCP HTTPS LB) обидві ролі об'єднано в один керований сервіс. Логічне розмежування залишається — вони вирішують різні задачі, навіть якщо один процес реалізує обидві.
КУТИ ТЕСТУВАННЯ QA — ЗВОРОТНІЙ ПРОКСІ
① Редирект HTTP → HTTPS: надіслати чистий HTTP-запит → очікується 301 або 302 на https://. Перевірити, що Location у редиректі не є відкритим редиректом.
② TLS-сертифікат: перевірити дійсність, що не прострочений, відповідає домену (включно з піддоменами для wildcard). Автоматизувати перевірку терміну дії в моніторингу.
③ Відхилення старих версій TLS: спробувати TLS 1.0 / 1.1 рукостискання → очікується відмова у з'єднанні. Ручна перевірка: openssl s_client -tls1 -connect host:443
④ X-Forwarded-For: перевірити, що заголовок доходить до прикладного шару з реальним IP клієнта, а не IP проксі.
⑤ Заголовки безпеки відповіді: HSTS, X-Frame-Options, Content-Security-Policy, X-Content-Type-Options — наявність та коректні значення у всіх відповідях.
⑥ Стискання: запит з Accept-Encoding: gzip → відповідь має містити Content-Encoding: gzip і стиснуте тіло.

02 Балансувальник навантаження КОМПОНЕНТ
↑ діаграма
Отримує вже розшифрований HTTP-трафік від зворотнього проксі. Розподіляє запити між кількома запущеними екземплярами наступного компонента (кластер API-шлюзу). Постійно перевіряє стан екземплярів і автоматично виключає непрацездатні з ротації.
ЧОМУ ДО API-ШЛЮЗУ

API-шлюз — stateless-сервіс, який може і повинен працювати як кілька екземплярів. Балансувальник це забезпечує: розподіляє трафік по кластеру шлюзів, тому якщо один екземпляр впаде, трафік перенаправляється в межах одного інтервалу health check. Без балансувальника єдиний екземпляр шлюзу є єдиною точкою відмови.

Рівень 4 проти рівня 7

ТипПрацює на рівніРішення про маршрутизаціюМоже аналізувати HTTP?
Балансувальник L4TCP / UDP (транспортний рівень)Тільки IP-адреса та портНі — трафік непрозорий
Балансувальник L7HTTP (прикладний рівень)URL-шлях, заголовки, cookies, content-typeТак — повна видимість запиту

В архітектурах мікросервісів стандартом є балансувальник L7. Він може маршрутизувати /api/orders/* до кластеру замовлень, а /api/payments/* до кластеру платежів — але на практиці ця маршрутизація за шляхом зазвичай виконується API-шлюзом, що стоїть за ним.

Алгоритми розподілу

КРУГОВА ЧЕРГА (ROUND-ROBIN)
Запити розподіляються послідовно: Екземпляр 1, 2, 3, 1… Простий, не потребує стану. За замовчуванням для більшості балансувальників. Слабкість: ігнорує поточне навантаження — повільний екземпляр отримує стільки ж запитів, як і швидкий.
МІНІМУМ З'ЄДНАНЬ
Наступний запит іде до екземпляра з найменшою кількістю відкритих з'єднань. Краще за кругову чергу для запитів різної тривалості. Вимагає відстеження кількості з'єднань балансувальником.
ХЕШ ЗА IP
IP клієнта хешується для визначення, який екземпляр обробляє всі запити від цього клієнта — sticky-сесії без cookies. Ризик: один популярний IP (напр., за NAT) може перевантажити один екземпляр.
КРУГОВА З ВАГАМИ
Екземплярам призначаються ваги (напр., 4-ядерний отримує вагу 4, 2-ядерний — 2). Пропорційний розподіл. Використовується для поступового переключення трафіку при деплоях (canary / blue-green).

Перевірка стану (Health checks)

ЦИКЛ ПЕРЕВІРКИ СТАНУ
1
БАЛАНСУВАЛЬНИК → ЕКЗЕМПЛЯР (періодично)
Балансувальник надсилає HTTP GET на спеціальний ендпоінт кожного екземпляра з налаштованим інтервалом (наприклад, кожні 5 секунд).
GET /health HTTP/1.1 → 200 OK {"status":"healthy"}
2а
ЕКЗЕМПЛЯР НЕ ПРОЙШОВ ПЕРЕВІРКУ
Після N послідовних невдач (напр., 2–3) балансувальник позначає екземпляр непрацездатним і виключає з ротації. Нові запити туди не надходять.
Запити, що вже виконуються, можуть бути оброблені залежно від налаштувань drain.
2б
ЕКЗЕМПЛЯР ВІДНОВИВСЯ
Після N послідовних успішних перевірок балансувальник повертає екземпляр до пулу.
КУТИ ТЕСТУВАННЯ QA — БАЛАНСУВАЛЬНИК
① Розподіл трафіку: надіслати ~50 запитів і перевірити логи доступу по екземплярах — трафік має бути розподілений (при round-robin — приблизно рівномірно).
② Ендпоінт перевірки стану: GET /health → 200 з коректним тілом. Протестувати поведінку при недоступній залежності (БД) — чи відображає /health цей стан?
③ Перемикання при відмові: зупинити один екземпляр під час трафіку → переконатися, що запити продовжуються без помилок 5xx. Виміряти час від відмови до перемаршрутизації.
④ Sticky-сесії: якщо налаштовано IP hash або cookie, перевірити, що той самий клієнт стабільно потрапляє на той самий екземпляр.
⑤ X-Forwarded-For: підтвердити наявність заголовка з реальним IP клієнта (не перезаписаний IP балансувальника).

03 API-шлюз КОМПОНЕНТ
↑ діаграма
Єдина примусова точка входу для всього API-трафіку мікросервісів. Отримує запити від балансувальника і застосовує набір політик — автентифікація, ліміти запитів, маршрутизація — до того, як запит потрапить до мікросервісу. Сервіси за шлюзом довіряють, що ці політики вже застосовані.
ЧОМУ ДО МІКРОСЕРВІСІВ

Без шлюзу кожен мікросервіс мусить самостійно реалізовувати автентифікацію, ліміти запитів і логування — продубльована логіка в десятках сервісів, кожен зі своїми неузгодженостями. Шлюз централізує всі наскрізні задачі в одному місці. Відхилений запит (прострочений токен, перевищений ліміт) зупиняється тут і ніколи не навантажує бекенд.

ФункціяЩо перевіряєВідповідь при помилці
АвтентифікаціяПеревіряє токен (підпис JWT + термін дії, OAuth2 introspection, пошук API-ключа). Визначає ідентичність.401 Unauthorized
АвторизаціяПеревіряє ролі/скоупи клієнта для запитуваного маршруту.403 Forbidden

Маршрутизація запитівЗіставляє вхідний шлях і метод з відповідним мікросервісом.404 або 502
Трансформація запитуПерезаписує заголовки, шлях, query-параметри перед передачею. Може вставляти user ID з токена в заголовок.—
Логування та трасуванняКожен запит логується централізовано. Correlation ID вставляється для розподіленого трасування.—

КУТИ ТЕСТУВАННЯ QA — API-ШЛЮЗ
① Відсутній токен → 401. Прострочений токен → 401. Пошкоджений токен (змінений payload) → 401.
② Дійсний токен, але недостатня роль/скоуп для маршруту → 403. Дійсний токен, правильна роль → 200.
③ Ліміт запитів: швидко надіслати N+1 запитів → (N+1)-й запит повертає 429 із заголовком Retry-After. Перевірити коректне скидання вікна після налаштованого інтервалу.
④ Правильна маршрутизація: GET /api/orders/* потрапляє до сервісу замовлень. GET /api/payments/* — до сервісу платежів. POST і GET на один шлях маршрутизуються незалежно.
⑤ Вставка токена: перевірити, що заголовок X-User-Id, вставлений шлюзом, містить правильне значення із поля sub токена.
⑥ Версіонування API: якщо реалізовано, /v1/ і /v2/ маршрутизуються до правильних версій сервісів незалежно.
⑦ Затримка шлюзу: виміряти p95/p99 часу відповіді — шлюз додає оверхед. Встановити базовий показник і сповіщати при деградації.

04 Мікросервіси КОМПОНЕНТ
↑ діаграма
Окремі сервіси, кожен з яких відповідає за свою бізнес-домен. Реалізують бізнес-логіку, читають і пишуть до власних виділених баз даних, спілкуються з іншими сервісами через внутрішні виклики. Прямий доступ з публічного інтернету неможливий — весь зовнішній трафік надходить через API-шлюз, де вже пройшов перевірку.
ЧОМУ ЗА ШЛЮЗОМ

Сервіси реалізують чисту доменну логіку. Вони довіряють, що запити, які до них надходять, вже автентифіковані шлюзом. Такий поділ спрощує сервіси — їм не потрібно реалізовувати логіку безпекового периметру. Виклики між сервісами обходять шлюз повністю і йдуть напряму через внутрішню мережу — це правильно, оскільки такі виклики відбуваються в довіреному контексті.

Ізоляція домену

Кожен мікросервіс повністю «володіє» своїм доменом — включно з власною базою даних. Сервіс замовлень не має прямого доступу до бази платежів і навпаки. Дані передаються через API-виклики або події, а не через спільну базу. Ця ізоляція обмежує зону ураження: помилка в замовленнях не може пошкодити дані платежів.

Патерни внутрішньої комунікації

СИНХРОННИЙ — REST
Сервіс A викликає HTTP-ендпоінт сервісу B і чекає відповіді. Простий і зрозумілий. Зв'язаність: якщо сервіс B недоступний, запит сервісу A одразу відмовляє.
СИНХРОННИЙ — gRPC
Бінарний протокол поверх HTTP/2. Швидший за REST для внутрішніх викликів. Використовує Protocol Buffers для визначення схем. Поширений для високонавантажених міжсервісних викликів.
АСИНХРОННИЙ — ЧЕРГА ПОВІДОМЛЕНЬ
Сервіс A публікує подію (Kafka, RabbitMQ). Сервіс B споживає, коли готовий. Розв'язаність: сервіс A не чекає; тимчасова недоступність B не призводить до втрати даних.
ПАТЕРН «АВТОМАТИЧНИЙ ВИМИКАЧ» (CIRCUIT BREAKER)

Коли сервіс A залежить від сервісу B через REST, автоматичний вимикач відстежує частоту відмов. Якщо B відмовляє повторно, вимикач «відкривається» і A одразу повертає fallback-відповідь замість очікування тайм-ауту. Це запобігає каскадним відмовам по всій системі. Для QA: симулювати недоступність B і перевірити, що A повертає налаштований fallback, а не тайм-аут на 500.

КУТИ ТЕСТУВАННЯ QA — МІКРОСЕРВІСИ
① Мережева ізоляція: спробувати TCP-з'єднання до внутрішнього порту сервісу ззовні VPC/приватної мережі → тайм-аут або відмова у з'єднанні, не HTTP-відповідь.
② Інтеграційні тести: сервіс A викликає сервіс B → перевірити коректну відповідь, коректну обробку помилок при 4xx або 5xx від B.
③ Автоматичний вимикач: зупинити сервіс B під час запитів, що залежать від нього → перевірити, що A повертає налаштований fallback у межах тайм-ауту відкритого вимикача, а не каскад помилок 500.
④ Consumer-driven contract тести (Pact): очікування сервісу A щодо API сервісу B закодовані як контракт. Запустити контракт проти B незалежно. Виявляє зламні зміни API до інтеграції.
⑤ Ізоляція бази даних: перевірити, що сервіс A не може запитувати базу даних сервісу B напряму (тільки через API B).
⑥ Асинхронний потік: опублікувати подію в чергу → перевірити, що споживаючий сервіс її обробляє та виробляє очікуваний побічний ефект (у межах SLA за часом).

Піраміда тестів для мікросервісних архітектур

ЮНІТ-ТЕСТИ (більшість)
Тестують бізнес-логіку одного сервісу в ізоляції. Всі зовнішні залежності мокуються. Швидкі, дешеві, не потребують інфраструктури.
КОНТРАКТ І ІНТЕГРАЦІЯ (середина)
Тестують комунікацію між двома суміжними сервісами. Consumer-driven контракти (Pact) перевіряють сумісність інтерфейсів без розгортання повного стеку.
НАСКРІЗНІ ТЕСТИ (мінімум)
Повний стек з реальною інфраструктурою. Тільки критичні користувацькі сценарії — дорогі, повільні, нестабільні. Покривають повний шлях від клієнта до бази даних і назад.

06 Типові помилки СПІВБЕСІДА
↑ діаграма
Це найпоширеніші хибні твердження на співбесідах щодо цих компонентів. Сказати будь-яке з них — це миттєвий червоний прапор для ролі Senior QA або backend-інженера.
✗
Стверджувати, що балансувальник навантаження та зворотній проксі — одне й те саме.
Вони вирішують різні задачі. Зворотній проксі відповідає за транспорт (TLS, кешування, статичні файли, маскування IP). Балансувальник — за доступність (розподіл, health checks, перемикання при відмові). Nginx може робити обидва одночасно, але це не робить їх одним концептом.
✗
Казати, що API-шлюз — «просто маршрутизатор».
Маршрутизація — лише одна з багатьох функцій. API-шлюз також забезпечує автентифікацію, авторизацію, ліміти запитів, трансформацію запитів/відповідей і централізоване логування. Назвати його «просто маршрутизатором» — означає не розуміти архітектурну причину його існування.
✗
Казати, що TLS завершується на балансувальнику навантаження.
У шаруватій архітектурі TLS завершується на зворотньому проксі — до балансувальника. Балансувальник отримує чистий HTTP. (Виняток: у деяких спрощених хмарних розгортаннях керований балансувальник також виконує роль зворотнього проксі. Ключовий момент — TLS завершується на першому серверному компоненті.)
✗
Казати, що до мікросервісів можна звернутися напряму «у разі крайньої необхідності».
Це анулює модель безпеки. Якщо у мікросервісів є будь-який шлях прямого доступу, цей шлях буде використаний, неправильно налаштований і зрештою скомпрометований. Правило абсолютне: жодного публічного маршруту до внутрішніх сервісів. Надзвичайні ситуації вирішуються через шлюз або внутрішній адмін-інструментарій у приватній мережі.
✗
Казати, що «шлюз перевіряє автентифікацію, тому сервісам перевірка не потрібна».
Сервіси все одно мають перевіряти, що заголовок X-User-Id (або аналогічний), вставлений шлюзом, присутній і відповідає запитуваному ресурсу (перевірка власника). Ніколи не варто вважати, що запит прийшов через шлюз лише тому, що він у внутрішній мережі. Принцип глибокого захисту (defense in depth) залишається актуальним.

Правильна ментальна модель — чотири шари, одна задача кожен

ШАР 1: ЗВОРОТНІЙ ПРОКСІ
Вирішує транспортні задачі: TLS, стискання, кешування, статичні файли. Задача: «Як зашифрований трафік з інтернету стає чистим внутрішнім HTTP?»
ШАР 2: БАЛАНСУВАЛЬНИК
Вирішує задачі доступності: розподіл, перемикання при відмові, health checks. Задача: «Як один URL обслуговує трафік з кількох запущених екземплярів?»
ШАР 3: API-ШЛЮЗ
Вирішує задачі API-політик: автентифікація, ліміти, маршрутизація, логування. Задача: «Як наскрізні API-задачі виконуються без дублювання коду в кожному сервісі?»
ШАР 4: МІКРОСЕРВІСИ
Вирішують задачі бізнес-логіки: доменна обробка, управління даними. Задача: «Як складний застосунок будується як незалежно розгортувані, доменно-орієнтовані модулі?»
✓
Зворотній проксі завершує TLS — перший серверний компонент, публічна IP, сертифікати тут.
✓
Балансувальник розподіляє по екземплярах шлюзу — шлюз працює як кластер, балансувальник розподіляє до нього.
✓
API-шлюз — виконавець політик — кожен зовнішній запит проходить через єдину точку перевірки автентифікації та лімітів до потрапляння в бізнес-логіку.
✓
Виклики між сервісами обходять шлюз — йдуть напряму по внутрішній мережі. Це правильно і навмисно.
✓
Кожен шар тестується незалежно — TLS на проксі, розподіл на балансувальнику, автентифікація на шлюзі, бізнес-логіка на сервісі — без розгортання повного стеку для кожного тесту.

07 Нормалізація запиту КОМПОНЕНТ
↑ діаграма
Нормалізація — це приведення вхідного запиту до стандартного, очищеного вигляду перед передачею далі по ланцюгу. Зворотній проксі виконує це першим, ще до того як запит потрапляє до балансувальника чи сервісів.
ЧОМУ ЗАПИТ МОЖЕ БУТИ «НЕЧИСТИМ»

Браузер надсилає акуратні запити — але браузер не єдиний клієнт. curl, мобільні застосунки, сторонні інтеграції і зловмисники формують запити вручну, без жодних гарантій коректності. Нормалізація захищає від решти клієнтів, а не від браузера.

Що саме нормалізується

ЩоПрикладНавіщо
URL і шляхи//api//orders → /api/orders; /api/./orders/../orders → /api/orders; подвійне кодування %252F розкривається тутОбхід фільтрів через аномальні шляхи — поширена техніка атаки
Заголовки від клієнтаКлієнт надіслав X-User-Id: admin → проксі видаляєБез видалення будь-який клієнт може підмінити ідентифікатор і обманути сервіс

ЧОМУ ЦЕ ВАЖЛИВО ДЛЯ QA

Якщо нормалізація не відбувається або відбувається неправильно, бекенд отримує брудний або потенційно небезпечний запит. Класичний приклад — path traversal: GET /api/orders/../../etc/passwd. Браузер такого не надішле, але зловмисник — так. Якщо URL не нормалізується до передачі на сервіс, запит може обійти роутинг і дістатись до файлів або ендпоінтів, які не мали бути доступні.

КУТИ ТЕСТУВАННЯ QA — НОРМАЛІЗАЦІЯ ЗАПИТУ
① Path traversal: GET /api/orders/../../etc/passwd → очікується 400 або 404, не вміст файлу
② Подвійне кодування: /api%2Forders і /api%252Forders → коректно оброблені або відхилені
③ Підмінений заголовок: запит з X-User-Id: 999 → сервіс отримує ID з токена, не з цього заголовка
④ Hop-by-hop: заголовок Connection не з'являється в логах бекенду

08 Проксі та шлюзи — термінологія ТЕРМІНОЛОГІЯ
↑ діаграма
Всі чотири стоять "посередині" з'єднання — саме тому вони здаються однаковими. Різниця в тому, кому вони служать і в якому напрямку.

Проксі (forward proxy, прямий проксі)

Стоїть між клієнтом та інтернетом. Клієнт знає про нього і навмисно направляє трафік через нього. Сервер-отримувач бачить IP проксі, а не IP клієнта.

Клієнт → Проксі → Інтернет → Сервер

Використовується для: корпоративної фільтрації інтернету, анонімізації, обходу гео-блокувань. Сервер не підозрює про існування проксі.

Зворотній проксі (reverse proxy)

Стоїть між інтернетом та вашими серверами. Клієнт не підозрює про його існування — він просто бачить одну адресу. Весь трафік спочатку потрапляє на зворотній проксі.

Клієнт → Зворотній проксі → Ваші сервери

Використовується для: завершення TLS, кешування, стискання, приховування внутрішніх IP. Клієнт не знає що є щось за ним.

Слово "зворотній" означає лише те, що проксі знаходиться на стороні сервера, а не клієнта.

Шлюз (gateway)

Загальний мережевий термін — будь-який компонент що транслює між двома різними системами або протоколами. Не специфічний для HTTP. Шлюз може з'єднувати різні мережі, протоколи або формати даних.

Зворотній проксі технічно є різновидом шлюзу — але сам по собі термін "шлюз" надто широкий щоб щось означати без контексту.

API-шлюз (API Gateway)

Зворотній проксі з вбудованими API-специфічними функціями. Стоїть перед мікросервісами.

Клієнт → API-шлюз → Мікросервіс А
                  → Мікросервіс Б
                  → Мікросервіс В

Додає поверх того що робить звичайний зворотній проксі: примусова автентифікація, ліміти запитів на клієнта, маршрутизація між кількома сервісами, валідація токенів, трансформація запитів і відповідей.

ПЛУТАНИНА ЗАЗВИЧАЙ ВИНИКАЄ ЧЕРЕЗ ТЕ

Що API-шлюз є зворотнім проксі — він просто робить більше. А вендори іноді називають свій зворотній проксі "шлюзом" з маркетингових міркувань (AWS API Gateway, Kong Gateway). Базова концепція завжди одна: щось стоїть посередині, перехоплює і обробляє запити.
