00 Request flow overview CONCEPT
A client request doesn't go straight to a microservice. It passes through a chain of infrastructure components, each solving a specific problem before handing off to the next. The order matters — each component depends on what the previous one already handled. Click any component in the diagram to jump to its section.
REQUEST FLOW — CLICK ANY COMPONENT
WHY THIS ORDER — THE ONE-LINE RULE

Each component solves a problem before handing off to the next. The reverse proxy handles transport (TLS, compression). The load balancer handles availability (distribution). The API gateway handles API-level policy (auth, rate limiting). Microservices handle business logic. Reversing any two components breaks this separation.

The three zones

PUBLIC ZONE
The open internet. The client lives here. Only the reverse proxy has a public IP address — everything else is invisible to the client.
EDGE / DMZ
Semi-trusted zone. Reverse proxy and load balancer sit here. Receives external traffic, terminates TLS, distributes to internal components.
INTERNAL NETWORK
Trusted zone. API gateway and microservices live here. Traffic is already decrypted and distributed. No direct public access possible.

SECURITY BOUNDARY TEST — ALWAYS RUN THIS

Try reaching an internal service's IP and port directly from outside the VPC or private network. You should get a timeout or connection refused — not a 200 or 401. Getting a response means the network perimeter is misconfigured. This is a critical finding in any security-focused test pass.

01 Reverse Proxy COMPONENT
↑ diagram
The first server-side component a client request reaches. Sits in front of all other infrastructure. Its core job: terminate the TLS connection, normalize the request, and forward clean HTTP internally. Clients communicate only with the reverse proxy — they never see backend IPs.
WHY BEFORE THE LOAD BALANCER

TLS termination is centralised here so all downstream components work with plain, already-decrypted HTTP. If TLS were terminated after the load balancer, every LB instance would need certificates, doubling operational complexity. One certificate lives here. Everything else is simpler because of it.

Core functions

FunctionWhat it doesWhy it matters for QA
TLS/SSL terminationDecrypts HTTPS. Downstream gets plain HTTP.Test certificate validity and expiry. Confirm TLS 1.0/1.1 is rejected.
HTTP → HTTPS redirect301 or 302 redirect for plain HTTP requests.Verify every HTTP endpoint redirects. Check redirect is not open redirect.
Static file servingReturns HTML, CSS, images directly — never hits backend.Cache headers: Cache-Control, ETag, Last-Modified present and correct.
Response compressionGzip or Brotli encoding of response bodies.Content-Encoding header present. Payload smaller than uncompressed baseline.
IP maskingReplaces client IP with X-Forwarded-For header downstream.Verify X-Forwarded-For contains the real client IP, not proxy IP.
Security headersAdds HSTS, X-Frame-Options, CSP, etc. on the way out.Verify headers present on all responses. Check HSTS max-age value.

Step-by-step flow

REVERSE PROXY REQUEST FLOW
1
CLIENT → REVERSE PROXY
Client sends HTTPS request. TCP connection established; TLS handshake happens at the proxy.
GET /api/orders HTTP/1.1 Host: api.example.com (TLS-encrypted transport)
2
REVERSE PROXY (internal)
Decrypts the request. Serves from cache if available. Otherwise adds X-Forwarded-For header with client IP and forwards as plain HTTP.
X-Forwarded-For: 203.0.113.42 X-Real-IP: 203.0.113.42
3
REVERSE PROXY → LOAD BALANCER
Forwards the decrypted request on the internal network. Backend never sees the original TLS session.
The load balancer IP is private — not routable from the internet.
4
REVERSE PROXY → CLIENT (response)
Receives response from backend, adds security headers, optionally compresses, re-encrypts for the TLS connection back to client.
Strict-Transport-Security: max-age=31536000; includeSubDomains Content-Encoding: gzip

Common implementations

EXAMPLES
Nginx Traefik HAProxy Caddy Apache httpd AWS CloudFront
NOTE — OVERLAP WITH LOAD BALANCER
Nginx can act as both a reverse proxy and a load balancer simultaneously. In cloud environments (AWS ALB, GCP HTTPS LB) both roles are merged into one managed service. The logical separation still holds — they solve different problems, even if the same binary implements both.
QA TEST ANGLES — REVERSE PROXY
① HTTP → HTTPS redirect: send plain HTTP request → expect 301 or 302 to https://. Check the redirect Location header is not an open redirect.
② TLS certificate: verify certificate is valid, not expired, matches the domain (including subdomains if wildcard). Automate expiry check in monitoring.
③ Rejected TLS versions: attempt TLS 1.0 / 1.1 handshake → expect connection refused or alert. Use openssl s_client -tls1 for manual check.
④ X-Forwarded-For: check the header reaches the application layer with the real client IP — not the proxy's IP.
⑤ Security response headers: HSTS, X-Frame-Options, Content-Security-Policy, X-Content-Type-Options — verify presence and correct values on all responses.
⑥ Compression: request with Accept-Encoding: gzip → response must include Content-Encoding: gzip and compressed body.

02 Load Balancer COMPONENT
↑ diagram
Receives already-decrypted HTTP traffic from the reverse proxy. Distributes requests across multiple running instances of the next component (the API gateway cluster). Continuously monitors instance health and removes unhealthy nodes from the rotation automatically.
WHY BEFORE THE API GATEWAY

The API gateway is stateless and can run as multiple instances. The load balancer enables this: it distributes across the gateway cluster, so if one gateway instance crashes, traffic is rerouted within one health-check interval. Without the LB, a single gateway instance is a single point of failure — the entire API is down if it crashes.

Layer 4 vs Layer 7

TypeOperates atRouting decisions based onCan inspect HTTP?
L4 Load BalancerTCP / UDP (transport layer)IP address and port onlyNo — traffic is opaque bytes
L7 Load BalancerHTTP (application layer)URL path, headers, cookies, content-typeYes — full request visibility

In microservice architectures, an L7 load balancer is the norm. It can route /api/orders/* to the Orders cluster and /api/payments/* to the Payments cluster — but in practice this path-based routing is usually handled by the API gateway sitting behind it.

Distribution algorithms

ROUND-ROBIN
Requests distributed in sequence: Instance 1, Instance 2, Instance 3, Instance 1… Simple, no state required. Default for most LBs. Weakness: ignores current load — a slow instance gets the same share as a fast one.
LEAST CONNECTIONS
Next request goes to the instance with the fewest open connections. Better than round-robin for variable-duration requests (e.g. file uploads mixed with fast reads). Requires the LB to track connection counts.
IP HASH
Client IP is hashed to determine which instance handles all requests from that client — sticky sessions without cookies. Risk: one popular IP (e.g. behind a NAT) can overload one instance.
WEIGHTED ROUND-ROBIN
Instances given weights (e.g. a 4-core instance gets weight 4, a 2-core gets weight 2). Proportional distribution. Used for gradual traffic shifts during deployments (canary / blue-green).

Health checks

HEALTH CHECK CYCLE
1
LOAD BALANCER → INSTANCE (periodic)
LB sends HTTP GET to a designated health endpoint on each backend instance at a configured interval (e.g. every 5 seconds).
GET /health HTTP/1.1 → 200 OK {"status":"healthy"}
2a
INSTANCE FAILS HEALTH CHECK
After N consecutive failures (e.g. 2–3), the LB marks the instance unhealthy and removes it from the rotation. No new requests are sent to it.
Existing in-flight requests may still be processed depending on drain settings.
2b
INSTANCE RECOVERS
After N consecutive successful health checks, the LB re-adds the instance to the pool.
QA TEST ANGLES — LOAD BALANCER
① Traffic distribution: send ~50 requests and check access logs per instance — traffic should be spread (with round-robin, roughly equal).
② Health check endpoint: GET /health → must return 200 with a valid body. Test what happens when a dependency (DB) is down — does /health reflect that?
③ Instance failover: stop one instance while sending traffic → monitor that requests continue without 5xx errors. Measure time from failure to re-routing.
④ Sticky sessions: if IP hash or cookie-based stickiness is configured, verify the same client consistently hits the same instance.
⑤ X-Forwarded-For: confirm the header is present and contains the real client IP (not overwritten by the LB's IP).

03 API Gateway COMPONENT
↑ diagram
The single enforced entry point for all microservice API traffic. Receives requests distributed by the load balancer and applies a set of policies — authentication, rate limiting, routing — before the request ever reaches a microservice. Services behind the gateway trust that these policies have already been enforced.
WHY BEFORE MICROSERVICES

Without a gateway, every microservice must independently implement authentication, rate limiting, and logging — duplicated logic across dozens of services, each with its own inconsistencies. The gateway centralises all cross-cutting concerns in one place. A rejected request (expired token, rate limit hit) dies here and never consumes backend compute.

Core functions

FunctionWhat it enforcesFailure response
AuthenticationValidates token (JWT signature + expiry, OAuth2 introspection, API key lookup). Identifies the caller.401 Unauthorized
AuthorizationChecks caller's roles/scopes against the requested route.403 Forbidden
Rate limitingCounts requests per client/IP within a time window. Blocks excess traffic.429 Too Many Requests + Retry-After header
Request routingMaps incoming path + method to the correct downstream microservice.404 or 502
Request transformationRewrites headers, path, query params before forwarding. Can inject user ID from token into headers.—
Response transformationShapes or filters upstream response before returning to client.—
Logging & tracingEvery request logged centrally. Correlation IDs injected for distributed tracing.—

Request flow through the gateway

API GATEWAY POLICY PIPELINE
1
LOAD BALANCER → GATEWAY INSTANCE
Request arrives on the gateway. Auth header extracted.
GET /api/orders/123 Authorization: Bearer eyJhbGci...
2
GATEWAY — AUTH VALIDATION
Token signature verified against the public key (JWT RS256) or HMAC secret. Expiry (exp claim) checked. If invalid or expired → stop here.
→ 401 { "error": "token_expired" }
3
GATEWAY — RATE LIMIT CHECK
Checks request count for this client within the current window (e.g. 100 req/min). Counter incremented. If over limit → stop here.
→ 429 Retry-After: 47
4
GATEWAY — ROUTING
Path matched against routing table. User ID injected from token payload into a header for the downstream service.
/api/orders/* → orders-service:8080 X-User-Id: user_abc123 (injected from token)
5
GATEWAY → MICROSERVICE
Validated, rate-checked, routed request forwarded to the correct service. Service processes it and returns response.
The microservice trusts all arriving requests are already authenticated.

QA TEST ANGLES — API GATEWAY
① Missing token → 401. Expired token → 401. Malformed token (tampered payload) → 401.
② Valid token, insufficient role/scope for this route → 403. Valid token, correct role → 200.
③ Rate limit: send N+1 requests rapidly → (N+1)th request returns 429 with Retry-After header. Verify the window resets correctly after the configured interval.
④ Correct routing: GET /api/orders/* arrives at Orders service. GET /api/payments/* arrives at Payments service. POST vs GET on the same path should route correctly.
⑤ Token injection: verify the X-User-Id (or equivalent) header injected by the gateway contains the correct value from the token sub claim.
⑥ API versioning: if implemented, /v1/ and /v2/ route to the correct service versions independently.
⑦ Gateway latency: measure p95/p99 response times — the gateway adds overhead. Establish a baseline and alert on regressions.

04 Microservices COMPONENT
↑ diagram
Individual services, each owning a single business domain. Process business logic, read and write to their own dedicated databases, and communicate with other services via internal calls. Never directly reachable from the public internet — all external traffic arrives pre-validated via the API gateway.
WHY BEHIND THE GATEWAY

Services implement pure domain logic. They trust that arriving requests have already been authenticated by the gateway. This separation keeps services simple — they don't need to implement security perimeter logic. Service-to-service calls bypass the gateway entirely and travel directly over the internal network, which is correct — those calls originate from a trusted context.

Domain isolation

Each microservice owns its domain completely — including its own database. The Orders service has no direct access to the Payments database and vice versa. Data is exchanged via API calls or events, not by sharing a database. This isolation limits blast radius: a bug in Orders cannot corrupt Payments data.

ServiceOwnsCommunicates via
Auth serviceUser credentials, tokens, sessionsCalled by gateway to validate tokens; issues tokens on login
Orders serviceOrder records, order statusREST API; publishes OrderCreated events to queue
Payments servicePayment records, transaction stateREST API; subscribes to OrderCreated events
Notification serviceNotification templates, delivery stateSubscribes to events from Orders and Payments

Internal communication patterns

SYNCHRONOUS — REST
Service A calls Service B's HTTP endpoint and waits for a response. Simple and familiar. Coupling: if Service B is down, Service A's request fails immediately.
SYNCHRONOUS — gRPC
Binary protocol over HTTP/2. Faster than REST for internal calls. Uses Protocol Buffers for schema definition. Common for high-throughput service-to-service calls.
ASYNC — MESSAGE QUEUE
Service A publishes an event (e.g. Kafka, RabbitMQ). Service B consumes it when ready. Decoupled: Service A does not wait; Service B can be temporarily down without data loss.
CIRCUIT BREAKER PATTERN

When Service A depends on Service B via REST, a circuit breaker monitors failure rate. If B fails repeatedly, the circuit "opens" and A returns a fallback response immediately instead of waiting for timeout. This prevents cascading failures across the whole system. For QA: simulate Service B being unavailable and verify Service A returns the configured fallback — not a 500 timeout.

QA TEST ANGLES — MICROSERVICES
① Network isolation: attempt a direct TCP connection to a service's internal port from outside the VPC/private network → must get timeout or connection refused, not an HTTP response.
② Integration tests: service A calls service B → verify correct response, correct error handling when B returns 4xx or 5xx.
③ Circuit breaker: stop Service B while Service A is processing requests that depend on it → verify A returns the configured fallback within the open-circuit timeout, not a cascade of 500 errors.
④ Consumer-driven contract tests (Pact): Service A's expectations of Service B's API are encoded as a contract. Run the contract against Service B independently. Catches breaking API changes before integration.
⑤ Database isolation: verify Service A cannot query Service B's database directly (only via Service B's API).
⑥ Async flow: publish an event to the queue → verify the consuming service processes it and produces the expected side effect (within SLA time).

Test business logic within a single service in isolation. Mock all external dependencies. Fast, cheap, no infrastructure needed.

END-TO-END (few)
Full stack with real infrastructure. Test critical user journeys only — expensive, slow, brittle. Cover the complete path from client to database and back.

06 Common mistakes INTERVIEW
↑ diagram
These are the most common incorrect statements made in interviews about these components. Saying any of these is an immediate red flag for a senior QA or backend engineer role.
✗
Saying load balancer and reverse proxy are the same thing.
They solve different problems. The reverse proxy handles transport concerns (TLS, caching, static files, IP masking). The load balancer handles availability concerns (distribution, health checks, failover). Nginx can do both simultaneously, but that does not make them the same concept.
✗
Saying the API gateway "is just a router."
Routing is one of many functions. An API gateway also enforces authentication, authorization, rate limiting, request/response transformation, and centralised logging. Calling it "just a router" misses the architectural reason it exists.
✗
Saying TLS is terminated at the load balancer.
In the layered architecture, TLS is terminated at the reverse proxy — before the load balancer. The LB receives plain HTTP. (Exception: in some simplified cloud deployments where the managed LB also acts as the reverse proxy, it terminates TLS. The key point is that TLS termination happens at the first server-side component.)
✗
Saying microservices can be reached directly "in emergencies."
This voids the security model. If microservices have any direct-access path, that path will be used, misconfigured, and eventually exploited. The rule is absolute: no public route to internal services. Emergencies are handled through the gateway or through internal admin tooling within the private network.
✗
Saying "the gateway handles auth so services don't need any."
Services should still validate that the X-User-Id or equivalent header injected by the gateway is present and makes sense for the requested resource (ownership check). Never assume a request arrived through the gateway just because it's on the internal network. Defense in depth still applies.

The correct mental model — four layers, one problem each

LAYER 1: REVERSE PROXY
Solves transport concerns: TLS, compression, caching, static files. Problem it solves: "How does encrypted traffic from the internet become clean internal HTTP?"
LAYER 2: LOAD BALANCER
Solves availability concerns: distribution, failover, health checks. Problem it solves: "How does one URL serve traffic across many running instances?"
LAYER 3: API GATEWAY
Solves API-level policy: auth, rate limiting, routing, logging. Problem it solves: "How are cross-cutting API concerns enforced without duplicating code in every service?"
LAYER 4: MICROSERVICES
Solves business logic: domain-specific processing, data management. Problem it solves: "How is a complex application built as independently deployable, domain-focused units?"
✓
Reverse proxy terminates TLS — first server-side component, public IP, certificates live here.
✓
Load balancer distributes across gateway instances — the gateway runs as a cluster, the LB distributes to it.
✓
API gateway is the enforcer — every external request passes through exactly one enforced auth/rate-limit check before reaching business logic.
✓
Service-to-service calls bypass the gateway — they travel directly on the internal network. This is correct and intentional.
✓
Each layer is independently testable — test TLS at the proxy, distribution at the LB, auth at the gateway, and business logic at the service, without deploying the full stack for every test.

07 Request normalization COMPONENT
↑ diagram
Normalization is the process of transforming an incoming request into a clean, standardized form before passing it further down the chain. The reverse proxy does this first — before the request reaches the load balancer or any internal service.
WHY REQUESTS CAN BE "DIRTY"

Browsers send well-formed requests — but the browser is not the only client. curl, mobile apps, third-party integrations, and attackers craft requests by hand, with no guarantees of correctness. Normalization protects against every client that isn't a browser, not against the browser itself.

What gets normalized

WhatExampleWhy it matters
URLs and paths//api//orders → /api/orders; /api/./orders/../orders → /api/orders; double-encoding %252F is decoded hereAnomalous paths are a common filter-bypass technique — normalize before any routing decision
Client-supplied headersClient sends X-User-Id: admin → proxy strips itWithout stripping, any client can spoof an identity and trick a downstream service
Hop-by-hop headersConnection: keep-alive is removedApplies only to the current TCP connection; forwarding it is a protocol error
Protocol versionHTTP/1.0 without a Host header → normalized to HTTP/1.1Backend receives a well-formed request regardless of what the client sent
WHY THIS MATTERS FOR QA

If normalization is missing or broken, the backend receives a dirty or potentially dangerous request. The classic example is path traversal: GET /api/orders/../../etc/passwd. A browser won't send that — an attacker will. If the URL is not normalized before being passed to a service, the request can bypass routing and reach files or endpoints that were never meant to be accessible.

QA TEST ANGLES — REQUEST NORMALIZATION
① Path traversal: GET /api/orders/../../etc/passwd → expect 400 or 404, not file contents
② Double encoding: /api%2Forders and /api%252Forders → correctly handled or rejected
③ Spoofed header: request with X-User-Id: 999 → service receives the ID from the token, not from this header
④ Hop-by-hop: the Connection header does not appear in backend logs

08 Proxies and gateways — terminology TERMINOLOGY
↑ diagram
All four sit "in the middle" of a connection — that's why they feel the same. The difference is who they serve and in which direction.

Proxy (forward proxy)

Sits between the client and the internet. The client knows about it and routes traffic through it intentionally. The destination server sees the proxy's IP, not the client's.

Client → Proxy → Internet → Server

Used for: corporate internet filtering, anonymisation, bypassing geo-restrictions. The server has no idea a proxy is involved.

Reverse Proxy

Sits between the internet and your servers. The client has no idea it exists — it just sees one address. All traffic hits the reverse proxy first.

Client → Reverse Proxy → Your Server(s)

Used for: TLS termination, caching, compression, hiding internal IPs. The client has no idea there's anything behind it.

The word "reverse" just means the proxy is on the server side instead of the client side.

Gateway

A general networking term — any component that translates between two different systems or protocols. Not specific to HTTP. A gateway can bridge two different networks, protocols, or data formats.

Reverse proxy is technically a type of gateway — but the term "gateway" alone is too broad to mean anything specific without context.

API Gateway

A reverse proxy with API-specific features built in. Sits in front of microservices specifically.

Client → API Gateway → Microservice A
                     → Microservice B
                     → Microservice C

Added on top of what a plain reverse proxy does: authentication enforcement, rate limiting per client, request routing between multiple services, token validation, request/response transformation.

One-line summary

TermServesDirectionKey job
ProxyClientClient → InternetHides client from internet
Reverse ProxyServerInternet → ServerHides server from internet
GatewayEitherEitherTranslates between systems (broad term)
API GatewayServerInternet → MicroservicesReverse proxy + auth + rate limiting + routing
THE CONFUSION USUALLY COMES FROM

The fact that an API Gateway is a reverse proxy — it just does more. And vendors sometimes call their reverse proxy a "gateway" for marketing reasons (AWS API Gateway, Kong Gateway). The underlying concept is always the same: something sitting in the middle, intercepting and processing requests.

09 Multiple load balancers COMPONENT
↑ diagram
Yes — this is common practice. A load balancer is not fixed to any single place in the architecture. It goes in front of any layer that needs to scale horizontally.

What this looks like

Client

First load balancer — before the application

What we've already covered. Distributes HTTP traffic across API gateway or application server instances. Operates at L7, understands HTTP.

Second load balancer — before the database

Typically operates at L4 (TCP level) — it doesn't understand SQL, it just distributes TCP connections across cluster nodes.

① Route reads (SELECT) to replica nodes, writes (INSERT, UPDATE) to primary only
② Remove a node from rotation if it goes down
③ Reduce direct connections to the database (connection pooling)

Examples of tools for this: PgBouncer (PostgreSQL), ProxySQL (MySQL), HAProxy (universal L4/L7).

WHY READ/WRITE SPLIT MATTERS FOR QA

If writes go to primary and reads come from a replica, there is replication lag between them. A test can write data and immediately read it — and not find it, because the replica hasn't updated yet.

This is a common cause of flaky tests in integration environments. Solutions: read from primary in tests, or add a delay after writes.
