Functional testing — quality-characteristic driven
Functional testing
ISO 25010 — functional suitability
›
In plain words
Does the system do what the requirements say it should do? Not how fast, not how secure — just: does it actually work as specified?
Evaluates the functions a component or system should perform. Maps to ISO 25010 functional suitability with three sub-characteristics: completeness, correctness, appropriateness.
Real-world context
You are testing an e-commerce backend. Functional testing answers: does the checkout flow work? Does the discount calculation apply correctly? Does the order confirmation email send? These are all functional questions — they have nothing to do with how fast or how secure the system is.
Functional completeness completeness
›
Are all the features that were promised actually there? Nothing missing.
Formal definition: The degree to which the set of functions covers all the specified tasks and user objectives.

Key distinction from correctness: Completeness asks "does it exist?" — not "does it work correctly?"

How to test: Requirements traceability matrix — every requirement mapped to an implemented feature. Gaps = completeness defects.
Example — microservices API: Payment service contract specifies 5 operations: charge, refund, void, capture, status. Developer implements 4, skips void. Completeness defect — feature is absent, not broken.

Example — SaaS product: Requirements say the admin panel must have user management, role assignment, audit log, and billing overview. Billing overview tab is missing from the UI. Completeness defect.
Functional correctness correctness
›
The features exist and they give the right answer. Wrong calculation = correctness defect.
Formal definition: The degree to which a product or system provides the correct results with the needed degree of precision.

Key distinction: The function exists (completeness ✓) but returns wrong output (correctness ✗).
Example: Tax endpoint exists and responds, but returns 19% VAT instead of the required 20%. Completeness: pass. Correctness: fail.

Example — data transformation: ETL pipeline exists and runs, but rounds currency values to 2 decimal places instead of 4, causing calculation drift downstream.
Functional appropriateness appropriateness
›
The features exist, work correctly, but are they actually useful for what real users are trying to do?
Formal definition: The degree to which the functions facilitate the accomplishment of specified tasks and objectives.

Hardest to test — requires understanding real user goals, not just technical requirements.
Example: A product search feature exists (complete) and returns accurate results (correct), but requires users to enter an exact SKU code rather than a natural keyword. It technically works but is not appropriate for how users actually search.

Example — API design: An endpoint to fetch order history returns all fields including internal system metadata. It is complete and correct, but inappropriate for the client — it returns 50KB where 2KB would serve the actual use case.
Non-functional testing — quality-characteristic driven
Performance testing
ISO 25010 — performance efficiency
›
In plain words
Is the system fast enough? Does it use memory and CPU reasonably? Does it stay fast when lots of people use it at once? Umbrella term for six sub-subtypes — each answers a different performance question.
Verifies speed, resource consumption, and capacity relative to workload. Maps to ISO 25010 performance efficiency sub-characteristics: time behaviour, resource utilisation, capacity.
Load testing
›
Does the system meet its speed targets when the expected number of users are using it?
Key: Defined, expected load. Not trying to break it — verifying it handles normal and peak traffic within SLA.

Metric: Response time, throughput (requests/sec), error rate under defined user count.
Example: Black Friday peak load is 2,000 concurrent users. Load test verifies checkout API responds under 300ms at 2,000 concurrent users with error rate below 0.1%.
Stress testing
›
Where does the system break, and when it breaks — does it crash hard or slow down gracefully?
Key: Load is increased gradually beyond normal capacity until failure. Goal is to find the breaking point and characterize the failure mode — hard crash vs graceful degradation.
Example: Normal load is 1,000 users. Ramp up to 1,500 → 2,000 → 3,000. At 2,400 users, error rate exceeds 5%. Breaking point identified. System returns 503s (acceptable) rather than throwing unhandled exceptions (not acceptable).
Spike testing
›
What happens if 10x the normal traffic arrives in 5 seconds? Flash sale, viral tweet, DDoS-like burst.
Key difference from stress: Stress is gradual. Spike is abrupt — normal to extreme in seconds, then back down.
Example: Ticket sales for a popular concert go live. 200 users → 8,000 users in under 10 seconds. Does the system absorb the spike and recover, or does it stay degraded after the burst passes?
Soak / endurance testing
›
Does the system slowly get worse over hours or days — memory leaks, connection pool exhaustion, log files filling up?
Key: Problems that only appear over time. A system can pass load testing at hour 1 but degrade at hour 48 due to a memory leak.
Example: Run the system at 70% capacity for 72 hours. Memory usage grows from 2GB → 8GB over 3 days. Response time at hour 72 is 3x slower than at hour 1. Memory leak confirmed. Without soak testing, this would only appear in production after days of operation.
Volume testing
›
Can the system handle a lot of data — not a lot of users, but a lot of rows, files, messages?
Key distinction from load testing: Load = concurrent users. Volume = data size. You can have volume issues with one user and one huge file.
Example: An ETL pipeline processes daily transaction files. Works fine with 10,000 rows in dev. In production, the file has 50 million rows — the process runs out of memory and crashes. Volume defect.

Example: Message queue accumulates 5 million unprocessed events overnight. Consumer service slows to a crawl when queue depth exceeds 500,000.
Scalability testing
›
When we add more servers, does performance actually improve? If doubling machines only gives 20% more capacity, something is wrong.
Key: Validates that the architecture actually scales. Reveals bottlenecks — a database that can't scale, a shared resource that becomes a chokepoint.
Example: 2 pods: 1,000 req/s. Add 2 more pods → expect ~2,000 req/s. Actual result: 1,200 req/s. Bottleneck found — all pods share one database connection pool with max 50 connections. Scaling pods does not help because they all compete for the same 50 DB connections.
Security testing
ISO 25010 — security
›
In plain words
Can someone break in, steal data, or make the system do things it shouldn't? Security testing tries to find those holes before an attacker does.
Verifies confidentiality, integrity, non-repudiation, accountability, and authenticity. Who can access what, and can the system detect and resist attacks?
Penetration testing
›
A tester acts like an attacker and actually tries to break in — not just scan for holes, but exploit them.
Example: Tester finds an unsanitized input field and attempts SQL injection. Successfully extracts user table contents. Pen test confirms a real exploitable vulnerability, not just a theoretical one.
Vulnerability scanning
›
Automated tool scans for known weak spots — outdated libraries, misconfigured settings, known CVEs.
Key difference: Scanning finds vulnerabilities. Pen testing exploits them. Scanning is automated and wide — pen testing is manual and deep.
Example: OWASP dependency check finds that a service uses Log4j 2.14.1 — vulnerable to Log4Shell (CVE-2021-44228). Vulnerability flagged for patching without manual exploitation.
Authentication testing
›
Can the system correctly verify who you are? Can someone log in as someone else, or stay logged in after they should be kicked out?
Example: Expired JWT token is still accepted by the API — no token expiry validation. Session is not invalidated after logout — old session cookie still works. Brute force on login endpoint is not rate-limited.
Authorization testing
›
Even when logged in correctly, can you access things you should not be able to access?
Classic interview question: Authentication = who are you? Authorization = what are you allowed to do? Two completely separate concerns.
Example: User A is authenticated. They call GET /api/orders/12345 — order belongs to User B. System returns it without checking ownership. IDOR (Insecure Direct Object Reference) — authorization defect, not an authentication defect.
Reliability testing
ISO 25010 — reliability
›
In plain words
Does the system keep working correctly over time, under expected conditions, and does it recover when something goes wrong? Especially important in microservices — one service failing should not take down everything.
Availability testing
›
Is the system accessible when users need it? Measured as uptime percentage.
Example: 99.9% SLA = maximum 8.7 hours downtime per year. 99.99% = 52 minutes. Test verifies the system meets its stated SLA under normal operating conditions and planned maintenance windows.
Fault tolerance testing
›
If one part of the system dies, does the whole thing die — or does it keep going?
Example — microservices: Kill the recommendation-service pod. Does the product page still load (showing products without recommendations), or does it throw a 500 error? Fault tolerance means the failure is isolated, not propagated.

Chaos engineering (e.g. Netflix Chaos Monkey) is a practice built on fault tolerance testing.
Recoverability testing
›
After a crash or failure, how quickly and completely does the system get back to normal?
RTO (Recovery Time Objective) — how long to restore service.
RPO (Recovery Point Objective) — how much data can be lost (time since last backup).
Example: Database server crashes at 14:00. Last backup was 13:00. Recovery completes at 14:45. RTO = 45 minutes. RPO = 60 minutes (1 hour of transactions lost). Test verifies both values meet contractual obligations.
Maturity testing
›
Is the system stable in day-to-day operation? No random crashes, no unexpected behavior, defect rate within acceptable limits.
Example: System has been in production for 3 months. Defect rate is still 5 critical issues per week. Maturity criterion not met — system is not yet stable enough for a given reliability target.
Usability testing
ISO 25010 — usability
›
In plain words
Can real users actually use the system to get things done — without confusion, frustration, or needing a manual? Features can be complete and correct but completely unusable.
Learnability
›
Can a new user figure it out without training?
Example: Give 5 new users the task "place an order without help." Measure time-to-first-success and error count. If most users fail or take 15+ minutes, learnability is poor.
Accessibility (WCAG)
›
Can people with disabilities use it? Screen readers, keyboard-only navigation, sufficient color contrast.
Example: Image buttons have no alt text — screen reader says "button" with no context. Color contrast ratio is 2.5:1 — WCAG AA requires 4.5:1. Both are accessibility failures.
Operability
›
Is the system easy to operate and control? Consistent behavior, clear labels, predictable responses.
Example: "Save" button in one part of the app triggers immediately. "Save" in another part opens a confirmation dialog first. Inconsistent operability — users cannot predict what will happen.
User error protection
›
Does the system stop users from making mistakes, and help them recover when they do?
Example: Admin clicks "Delete all users" — no confirmation dialog. All users deleted instantly with no undo. Error protection failure. Good design: confirmation step + soft-delete with 30-day recovery window.
Compatibility testing
ISO 25010 — compatibility
›
In plain words
Does the system play nicely with other systems and environments — sharing resources without conflict, and exchanging data correctly?
Co-existence
›
Two services running on the same machine don't steal each other's resources or break each other.
Example: Service A and Service B both deployed on the same host. Service A's memory leak causes Service B to be killed by the OOM killer. Co-existence failure.
Interoperability
›
Services can actually talk to each other and understand each other's data formats.
Example — microservices: Order service sends dates as Unix timestamps. Notification service expects ISO 8601 strings. API contract mismatch — interoperability defect. Consumer-driven contract testing (Pact) is specifically designed to catch these.
Maintainability testing
ISO 25010 — maintainability
›
In plain words
Can developers change, fix, and extend the system without it becoming a nightmare? More developer-facing than user-facing — but poor maintainability is what turns a healthy system into legacy spaghetti over time.
Modularity
›
Changing one part doesn't break unrelated parts.
Example: Changing the pricing logic in the pricing service causes the order service to fail — they share a database table with undocumented coupling. Low modularity.
Testability
›
Can you actually write tests for it? Can you isolate a component to test it alone?
Example: A class has 12 constructor dependencies, all concrete (not injected). Impossible to unit test without spinning up the entire application. Low testability.
Analyzability
›
When something goes wrong, can you figure out why? Good logs, meaningful error messages, proper tracing.
Example: Production error log shows: "Error: null". No stack trace, no context, no request ID. Analyzability failure — impossible to diagnose without reproducing the issue.
Modifiability
›
Can you safely change the code without accidentally breaking something else?
Example: Changing a database column name requires manually finding and updating 47 hardcoded string references across 12 files. High risk of missing one. Low modifiability.
Portability testing
ISO 25010 — portability
›
In plain words
Can the system be moved to a different environment — different OS, different cloud, different server — without rewriting it?
Adaptability
›
Can it run in a different environment without code changes?
Example: Docker image built for AWS runs on GCP and Azure without modification. Passes adaptability. Contrast: application has AWS SDK calls hardcoded and fails outside AWS — fails adaptability.
Installability
›
Can you install and uninstall it cleanly on a target environment?
Example: Helm chart deploys successfully to a fresh Kubernetes cluster. Uninstall leaves no orphaned resources. Installability pass. Contrast: install script fails on Ubuntu 22.04 because it only supports 20.04 — installability failure.
Replaceability
›
Can this system replace an existing one for the same purpose, with the same data?
Example: Migrating from MySQL to PostgreSQL. Replaceability test: export all data, import to PostgreSQL, run full regression suite against the new database. All existing queries must produce identical results.
Black-box testing — test design driven
Black-box testing
test design techniques
›
In plain words
You test the system from the outside — you give it inputs and check outputs, without looking at the code inside. You only know what the system is supposed to do, not how it does it. Subtypes are techniques for designing those tests systematically.
Specification-based. Derives tests from requirements, specs, user stories, and other external documentation. Applies to both functional and non-functional testing.
Equivalence partitioning (EP)
›
Divide all possible inputs into groups where every value in a group should behave the same way. One test per group is enough — testing 5 values from the same group tells you nothing more than testing 1.
Example — age field, valid range 18–65:
Partition 1: below 18 (invalid) → test with 15
Partition 2: 18–65 (valid adult) → test with 35
Partition 3: above 65 (senior) → test with 70
3 partitions = 3 test cases minimum.
Boundary value analysis (BVA)
›
Most bugs hide at the edges of a valid range, not in the middle. Test right at the boundary — the first valid value, the last valid value, and the values just outside.
2-value BVA: Test at the boundary itself + just outside it.
3-value BVA: Test just below + at boundary + just above.
Example — valid age 18–65, 3-value BVA:
Lower boundary: 17 (invalid), 18 (valid), 19 (valid)
Upper boundary: 64 (valid), 65 (valid), 66 (invalid)
Decision table testing
›
When the system behaves differently depending on multiple conditions at once — build a table of every combination. Each column in the table is a test case.
Example — discount rules:
Conditions: member (Y/N) × large order (Y/N) = 4 combinations
Member + large = 20% | Member + small = 10% | Non-member + large = 5% | Non-member + small = 0%
4 columns = 4 test cases, covering all combinations.
State transition testing
›
The system has a set of states it can be in. Model the valid moves between states, then test both the moves that should work and the moves that should be rejected.
Example — order lifecycle:
States: pending → confirmed → shipped → delivered → cancelled
Valid: pending → confirmed ✓
Invalid: shipped → pending ✗ (should be rejected)
Test covers both valid transitions and attempts at invalid ones.
Use case testing
›
Test the system as a real user completing a real goal — not individual functions, but an end-to-end scenario.
Example — "place an order":
Happy path: search → add to cart → checkout → payment succeeds → confirmation
Alternative: item goes out of stock during checkout
Exception: payment fails → retry option presented
White-box testing — test design driven
White-box testing
test design techniques
›
In plain words
You test by looking inside the code. You know how it works and you design tests to make sure specific code paths, branches, and conditions have actually been executed. Subtypes are coverage criteria — measurable targets for how much of the code structure your tests have exercised.
Structure-based. Derives tests from internal code, architecture, workflows, and data flows. Coverage percentage is the key metric.
Statement coverage
›
Has every line of executable code been run at least once by your tests?
Formula: Exercised statements ÷ total executable statements × 100%
Weakness: Weakest criterion. 100% statement coverage does not mean you tested both true and false branches of an if statement.
Example: if (x > 0) { doA(); } — if tests only pass x=5, doA() is covered (statement coverage = 100%), but the false branch (x ≤ 0, doA not called) is never tested.
Branch coverage
›
Has every if/else, every decision point gone both ways — true and false?
Key fact: 100% branch coverage guarantees 100% statement coverage. The reverse is not true.
Most commonly required criterion in practice — standard for most commercial software.
Example: if (x > 0) { doA(); } else { doB(); }
Need at least 2 tests: one with x=5 (true branch → doA), one with x=-1 (false branch → doB).
Condition coverage
›
In a complex condition like (A AND B), has each individual part — A and B — been both true and false independently?
Example: if (isAdmin AND isActive) — condition coverage requires tests where isAdmin=true/false AND isActive=true/false independently, even if the overall decision doesn't change.
Path coverage
›
Has every possible route from start to end of the code been executed? The most thorough — and usually impractical for anything real.
Problem: Number of paths grows exponentially. 10 consecutive if/else statements = up to 1,024 paths. Achievable only in small, critical units.
MC/DC coverage
›
Prove that each condition in a complex decision can independently change the final outcome — no condition is being masked or ignored by others.
Full name: Modified Condition/Decision Coverage
Used in: Safety-critical systems — aviation software (DO-178C Level A), medical devices, automotive (ISO 26262 ASIL D).
FL 4.0 exam note: Know what it is and where it is used. Deep knowledge is not required at foundation level.
Example: if (A OR B OR C) — MC/DC requires showing that changing A alone (while B and C are fixed) changes the outcome, and the same independently for B and for C. Eliminates redundant conditions that never actually affect the result.
ISO/IEC 25010:2023 — Software Product Quality Model
Defines nine quality characteristics and their sub-characteristics — properties a software product must have, independent of how they are tested. The 2023 revision added Safety as a new top-level characteristic, renamed Usability to Capability and Portability to Flexibility, and introduced new sub-characteristics within several existing ones. Old names shown in parentheses where applicable.

Mnemonic: Fried Potatoes Catch Unicorns, Running Snails Meet Purple Snake → Functional Suitability · Performance Efficiency · Compatibility · Usability (Capability) · Reliability · Security · Maintainability · Portability (Flexibility) · Safety
Functional Suitability
ISO 25010
›
In plain words
Does the system do what its specification says? Not how fast, not how securely — just: is the stated functionality present, correct, and actually useful for what users are trying to accomplish?
Functional Completeness
›
The set of functions covers all specified tasks and user objectives. Nothing is missing from what was promised.
Example: Payment API contract specifies 5 operations. Developer implements 4, skips void. Completeness defect — the function is absent, not broken.
Functional Correctness
›
Functions provide the right results with the required degree of precision. A function can exist without being correct.
Example: Tax endpoint exists and responds, but returns 19% VAT instead of the required 20%. Completeness: pass. Correctness: fail.
Functional Appropriateness
›
Functions actually facilitate the user's goals. A feature can be present and correct but still not appropriate for the real use case.
Example: Product search exists and returns accurate results, but requires an exact SKU code rather than a natural keyword. Present ✓ Correct ✓ Appropriate ✗
QA angle
Requirements traceability matrix → completeness. Test cases with expected outputs → correctness. User goal analysis and task modelling → appropriateness. This characteristic is the "why" behind functional testing — it defines what "working correctly" means at the model level.
Performance Efficiency
ISO 25010
›
In plain words
Does the system perform within acceptable time and resource limits under defined conditions? How fast it responds, how much CPU/memory it consumes, and how much load it can handle.
Time Behaviour
›
Response times, processing times, and throughput rates under defined conditions.
Example: "95th percentile response under 200ms at 500 rps" is a time behaviour requirement. Verified by load testing under that exact traffic profile.
Resource Utilization
›
CPU, memory, disk, and network bandwidth consumed relative to workload.
Example: A service responds in 50ms but pegs CPU at 100% under normal load, starving co-deployed services. Fast response ✓ Resource utilization ✗
Capacity
›
Maximum limits the system can reach — concurrent users, file sizes, queue depth, connection pool — before degrading.
Example: Message queue handles up to 500,000 events before consumer throughput degrades. Capacity requirement: sustain 1M events without degradation. One user uploading one huge file can hit capacity while concurrent-user load is near zero.
QA angle
Load/stress/spike testing → time behaviour + capacity. Soak testing → resource utilization over time. Note: Scalability is now its own sub-characteristic under Flexibility (characteristic 8), not under Performance Efficiency.
Compatibility
ISO 25010
›
In plain words
Does the system work alongside other systems without interference, and exchange data with them correctly?
Co-existence
›
Can operate in a shared environment — same host, network, or cluster — without negatively affecting other products and without being affected by them.
Example: Service A's memory leak causes the OOM killer to terminate Service B on the same host. Co-existence failure — one product's defect damages another product with no shared code between them.
Interoperability
›
Can exchange information with other systems and use that information correctly. Covers API contracts, data formats, and protocol conformance.
Example: Order service sends dates as Unix timestamps. Notification service expects ISO 8601 strings. API contract mismatch — interoperability defect. Consumer-driven contract testing (Pact) is designed to catch exactly this class of failure.
QA angle
Co-existence: deploy multiple services, monitor for resource interference and unexpected side effects. Interoperability: contract testing (Pact), integration tests, API schema validation. In microservices architectures this is one of the most frequently violated characteristics.
Capability Usability
ISO 25010
›
In plain words
Can users actually achieve their goals with the system? Covers everything from first contact ("does this do what I need?") through to ongoing use for people with different abilities, languages, and levels of expertise.
Appropriateness Recognizability
›
Within first contact, users can recognise whether the system suits their needs.
Example: A user lands on a SaaS product page. Within 10 seconds they cannot tell what the product actually does. Appropriateness recognizability failure — regardless of how capable the product actually is.
Learnability
›
How quickly can a new user become proficient? Measured by time-to-first-success and error rate during initial use.
Example: Give 5 new users the task "place an order without help." If most fail or take 15+ minutes, learnability is poor — regardless of whether experienced users find the system fast and efficient.
Operability
›
The system is easy to operate and control: consistent behaviour, predictable interactions, low cognitive load during ongoing use.
Example: "Save" in one module triggers immediately; "Save" in another opens a confirmation dialog. Inconsistent operability — users cannot build a reliable mental model of how the system behaves.
User Error Protection
›
Prevents users from making mistakes and helps them recover when they do. Confirmations before destructive actions, clear error messages, undo capability.
Example: Admin clicks "Delete all users" — no confirmation dialog. All users deleted instantly with no undo. Error protection failure. Correct design: confirmation step + soft-delete with 30-day recovery window.
User Engagement User Interface Aesthetics
›
The system presents itself in a way that motivates users to continue engaging — responsiveness, perceived performance, appropriate feedback, interaction quality. Goes beyond visual aesthetics.
Example: A visually polished app that freezes for 2 seconds on every tap and gives no loading feedback has poor user engagement despite attractive design. Contrast: plain UI with instant feedback and smooth transitions scores higher on this sub-characteristic.
Inclusivity Accessibility
›
The system is usable by the widest possible range of users — including those with disabilities, different languages, cognitive styles, devices, and contexts. Broader than WCAG compliance alone.
Example: WCAG covers disability accessibility. Inclusivity also covers: right-to-left language support, low-bandwidth contexts, varying literacy levels, older devices. A product can pass WCAG AA and still fail inclusivity on these other dimensions.
User Assistance
›
The system provides effective in-product help: tooltips, inline documentation, contextual hints, tutorials. Users can answer their own questions without leaving the product.
Example: A complex form has a "?" icon next to each field. Clicking it shows a short explanation of what the field expects and why it is needed. User assistance — no external documentation required to complete the task.
Self-Descriptiveness
›
Labels, icons, status indicators, and feedback make the system's current state and available actions clear without external reference material. The UI documents itself.
Example: Button shows a spinner while processing, then a green tick on success, then a red ✕ with a one-line reason on failure. The user always knows what state the system is in. Contrast: button goes grey after clicking and nothing else happens — user has no idea if their action was received.
QA angle
Usability testing sessions, accessibility audits (WCAG 2.2), first-use studies with real users, heuristic evaluation (Nielsen's 10 heuristics map directly to several sub-characteristics here), assistive technology testing (screen readers, switch access, voice control).
Reliability
ISO 25010
›
In plain words
Does the system keep working correctly over time, under expected conditions, and recover when something goes wrong? Especially critical in distributed systems where partial failure is the norm, not the exception.
Faultlessness Maturity
›
The system meets its reliability requirements under normal operation. Low defect rate in production, stable long-term behaviour, no random crashes.
The rename from "Maturity" reflects that a new system can be faultless while an old one can be full of faults — the concept is about defect rate and stability, not age of the product.
Example: System has been in production for 3 months. Defect rate is still 5 critical issues per week. Faultlessness criterion not met — regardless of how long the system has been deployed.
Availability
›
The system is accessible and operational when required. Expressed as uptime percentage.
Example: 99.9% SLA = maximum 8.7 hours downtime per year. 99.99% = 52 minutes. 99.999% = 5.2 minutes. Each additional "nine" reduces acceptable downtime by roughly 10×.
Fault Tolerance
›
The system continues operating correctly even when components fail or invalid inputs are encountered. Failures are isolated, not propagated.
Example: Kill the recommendation-service pod. Does the product page still load (without recommendations), or does it throw a 500? Fault tolerance = the failure is isolated. Circuit breakers, fallbacks, and graceful degradation are implementation patterns for this sub-characteristic.
Recoverability
›
After a failure, the system restores data and re-establishes normal operation within defined time (RTO) and data loss (RPO) limits.
Example: Database crashes at 14:00. Last backup at 13:00. Recovery completes at 14:45. RTO = 45 min, RPO = 60 min. Both values must meet contractual obligations.
QA angle
Long-run stability testing → faultlessness. SLA monitoring → availability. Chaos engineering / fault injection → fault tolerance. Disaster recovery drills → recoverability.
Security
ISO 25010
›
In plain words
Can the system protect information and resources from unauthorized access, disclosure, or manipulation — and hold up under active hostile behaviour?
Confidentiality
›
Data is accessible only to those authorized. Encryption at rest and in transit, access control, data classification enforcement.
Example: User A calls GET /api/orders?userId=B and receives User B's full order history without any authorization check. Confidentiality breach — data exposed to an unauthorized party.
Integrity
›
Data is protected from unauthorized modification. Checksums, audit trails, write access controls, input validation.
Example: Attacker intercepts and modifies an order amount in transit (man-in-the-middle). No HTTPS + no request signing = integrity violation. The data arrived, but it was not the data that was sent.
Non-Repudiation
›
Actions can be proven to have occurred so neither party can deny them. Tamper-evident audit logs, digital signatures, timestamping.
Example: A financial transaction is disputed. Tamper-evident audit log with digital signatures proves the user initiated the transfer at a specific timestamp. Without this, either party can deny the transaction occurred.
Accountability
›
Actions by any user or system component can be traced back to the specific entity responsible. Structured logging with identity context, correlation IDs.
Example: Production data is deleted. Audit log shows which admin account triggered which API call at which timestamp with which request ID. Without accountability, a breach investigation cannot determine the responsible actor.
Authenticity
›
The identity of a user, system, or resource can be verified as what it claims to be. Authentication mechanisms: tokens, certificates, MFA.
Example: Expired JWT token still accepted — no expiry validation. Session not invalidated after logout. Brute force on login not rate-limited. All three are authenticity failures — the system cannot reliably verify who it is talking to.
Resistance
›
The system sustains correct operation under hostile conditions: DDoS attacks, malformed inputs, brute force, injection attempts.
Example: API receives 50,000 requests/second from a botnet. Without rate limiting and WAF rules, it falls over for legitimate users too. Resistance means staying up and correct under attack — not just detecting it.
QA angle
Penetration testing → exploiting vulnerabilities. Vulnerability scanning → finding them. Auth testing → authenticity + confidentiality. Authorization testing → integrity + accountability. Load testing under attack conditions → resistance.
Maintainability
ISO 25010
›
In plain words
How easy is it for developers to modify, fix, understand, and extend the system? Poor maintainability is the primary driver of technical debt — the reason systems become expensive and risky to change over time.
Modularity
›
Discrete components such that changes to one have minimal impact on others. High cohesion, low coupling.
Example: Changing pricing logic in the pricing service causes the order service to fail — they share a database table with undocumented coupling. One change, unintended side effect in an unrelated component. Low modularity.
Reusability
›
Components, modules, or libraries can be used to build other systems or other parts of the same system.
Example: Authentication logic extracted into a shared library consumed by 5 microservices — bug fixed once, all services benefit. Contrast: authentication duplicated in each service — 5 places to patch, 5 ways to drift out of sync. Low reusability multiplies maintenance cost.
Analysability
›
The impact of proposed changes can be assessed; causes of failures can be diagnosed. Good logging, meaningful error messages, distributed tracing, readable code.
Example: Production log shows: "Error: null". No stack trace, no context, no request ID. Analysability failure — diagnosing this requires reproducing from scratch. Contrast: structured log with correlation ID, user context, and full stack trace.
Modifiability
›
Changes can be implemented without introducing defects or degrading existing quality. Measured by regression rate — how often a routine change breaks something else.
Example: Renaming a database column requires manually updating 47 hardcoded string references across 12 files. High risk of missing one. Low modifiability — the cost and risk of routine changes is disproportionately high.
Testability
›
Test criteria can be established and tests can be executed to determine whether those criteria are met. Dependency injection, observable state, isolated components, deterministic behaviour.
Example: A class has 12 constructor dependencies, all concrete (not injected). Impossible to unit test without spinning up the entire application. The design actively resists verification. Low testability.
QA angle
Testability directly enables testing effectiveness — a system with low testability is harder and more expensive to test at every level. Analysability determines how fast QA can diagnose production issues. These are characteristics QA lives with daily, not just verifies once.
Flexibility Portability
ISO 25010
›
In plain words
Can the system be deployed in different environments, scaled to different workload levels, and moved or replaced without rewriting? The rename from Portability to Flexibility reflects that this characteristic covers more than just "can it run somewhere else."
Adaptability
›
Can operate in different or evolving hardware, software, or usage environments without code changes.
Example: Docker image built for AWS runs on GCP and Azure without modification. Adaptability pass. Contrast: application has AWS SDK calls hardcoded and fails outside AWS — adaptability failure.
Scalability
›
Can handle growing or varying workloads by adding resources — horizontally (more instances) or vertically (bigger instances). Whether adding resources actually translates to proportional capacity gain.
Example: 2 pods: 1,000 req/s. Add 2 more → expect ~2,000 req/s. Actual: 1,200 req/s. Bottleneck: all pods share one DB connection pool (max 50 connections). Adding pods does not help — scalability is constrained by the shared resource.
Installability
›
Can be successfully installed and uninstalled in a target environment without leaving orphaned resources or broken state.
Example: Helm chart deploys cleanly to a fresh Kubernetes cluster. Uninstall leaves no orphaned resources. Installability pass. Contrast: install script only works on Ubuntu 20.04, fails on 22.04 — installability failure.
Replaceability
›
Can replace another software product for the same purpose in the same environment, with the same data and producing the same outcomes.
Example: Migrating from MySQL to PostgreSQL. Replaceability test: export all data, import to PostgreSQL, run full regression suite. All queries must produce identical results. Any divergence is a replaceability failure.
QA angle
Cross-environment deployment tests → adaptability. Scalability testing (now a named sub-characteristic here, not under Performance Efficiency) → scalability. Install/uninstall automation → installability. Migration tests + full regression suite against the new system → replaceability.
Safety
ISO 25010
›
In plain words
Does the system avoid causing harm to people, property, or the environment? A system can be fully functional, performant, and secure and still create dangerous situations when it fails in a safety-critical context. This characteristic did not exist in ISO 25010:2011 — its addition reflects the growing role of software in medical devices, autonomous vehicles, and industrial control systems.
Operational Constraint
›
The system operates within defined safe limits and refuses to operate outside them.
Example: Medical device refuses to administer a dosage above the safe maximum — even if the controlling software instructs it to. Drone controller ignores a command that would exceed structural load limits. Operational constraint = hard boundary enforcement, not just a warning.
Risk Identification
›
The system identifies conditions that could create risk and surfaces them to the appropriate entity — user, operator, or external system — in time to act.
Example: Industrial control system detects that reactor temperature is trending toward the critical threshold — 15 minutes before it would be reached. Alert raised to operator with time to intervene. Risk identification is proactive, not a post-incident log entry.
Fail Safe
›
When a failure occurs, the system transitions to a safe state rather than an undefined or dangerous one.
Example: Vehicle ECU loses communication — brakes engage rather than releasing. Industrial actuator loses power signal — valve closes rather than opening. Access control service crashes — system defaults to deny rather than permit. The failure mode is designed, not accidental.
Hazard Warning
›
The system warns users and connected systems about conditions that could cause harm — before harm occurs.
Example: Patient monitoring system detects irregular heart rhythm. Alarm triggers at the nursing station before the patient deteriorates to a critical state. Hazard warning = actionable notice with time to respond.
Safe Integration
›
When integrated with other systems, the new component does not introduce failure modes that compromise the safety of the broader environment.
Example: New telemetry microservice added to an autonomous vehicle pipeline. Safe integration testing verifies: the service cannot block the control loop, its failure does not propagate to braking or steering, and its timing does not violate real-time safety constraints.
QA angle
Safety requirements testing, fault injection, failure mode and effects analysis (FMEA), compliance testing against domain safety standards: IEC 62304 (medical software), DO-178C (aviation), ISO 26262 (automotive), IEC 61508 (industrial). Safety testing requires domain expertise and regulatory audit. Beyond ISTQB Foundation scope — but important to know it exists and why.
Why these three concepts are often confused
Test types, quality characteristics, and test design techniques are three separate ideas that interact — but each answers a different question. Mixing them up is one of the most common interview mistakes.
ConceptQuestion answeredExamples
Test type What aspect of the system are you testing? Functional, Performance, Security, Usability, Reliability…
Quality characteristic By what standard do you measure quality? ISO 25010: Functional Suitability, Performance Efficiency, Reliability, Security…
Design technique How do you systematically design test cases? Equivalence Partitioning, BVA, Decision Table, Exploratory…
How they connect
A test type (e.g., functional testing) is motivated by a quality characteristic (e.g., ISO 25010 — Functional Suitability). A design technique is the tool you use to decide which test cases to write — for any test type. The same technique (e.g., Equivalence Partitioning) can be applied to functional, performance, or security tests. Techniques are orthogonal to test types: they describe how, not what.
ISTQB FL 4.0 — primary categorization
Black-box techniques specification-based
design techniques
›
In plain words
You design test cases from what the system should do — specifications, requirements, user stories — without looking at the code. You treat the system as a black box: input goes in, output comes out, you validate the output.
Applicable to any test level and type. Black-box techniques work wherever expected behavior can be defined from a specification — functional, API, UI, performance boundaries.
Equivalence Partitioning (EP)
›
Divide possible inputs into groups where every value in a group should behave identically. One representative test per group is enough.
When to use: Any input with a range or set of values — numbers, strings, dates, status codes.

Value: Reduces test case count without losing coverage of distinct behaviors.
Example — age field (valid 18–65):
Partition 1: <18 (invalid) → test with 15
Partition 2: 18–65 (valid) → test with 35
Partition 3: >65 (invalid) → test with 70
3 partitions = 3 test cases minimum.
Boundary Value Analysis (BVA)
›
Most defects hide at the edges of valid ranges. Test exactly at the boundary and just outside — not just the middle of a partition.
2-value BVA: boundary + one value just outside.
3-value BVA: one just below + boundary + one just above.

Used with EP: EP selects which partitions to test; BVA refines the values chosen at their boundaries.
Example — valid age 18–65, 3-value BVA:
Lower boundary: 17 (invalid) · 18 (valid) · 19 (valid)
Upper boundary: 64 (valid) · 65 (valid) · 66 (invalid)
Decision Table Testing
›
When behavior depends on multiple conditions simultaneously, build a table covering every meaningful combination. Each column is one test case.
When to use: Business rules with multiple interacting conditions — discount logic, eligibility checks, access control rules.

Alternative grouping: Rule-based (see section below).
Example — discount rules:
Conditions: member (Y/N) × order > $100 (Y/N) = 4 combinations
Member + large = 20% | Member + small = 10% | Non-member + large = 5% | Non-member + small = 0%
4 columns = 4 test cases, all rule combinations covered.
State Transition Testing
›
Model the system's valid states and the events that move between them. Test both valid transitions and attempts at invalid ones.
When to use: Anything with a lifecycle — orders, sessions, workflows, accounts, subscriptions.

Alternative grouping: Behavior-based.
Example — order lifecycle:
States: Pending → Confirmed → Shipped → Delivered | Cancelled
Valid: Pending → Confirmed ✓
Invalid: Shipped → Pending ✗ (must be rejected)
Test suite covers valid moves AND attempted invalid transitions.
Use Case Testing
›
Test a complete end-to-end scenario as a real user pursuing a real goal — not individual functions, but the full interaction flow.
Covers: Happy path + alternative flows + exception handling.

Alternative grouping: Behavior-based.
Example — "place an order":
Happy path: search → cart → checkout → payment succeeds → confirmation
Alternative: item goes out of stock during checkout
Exception: payment fails → retry offered, order not created
Applies to
Functional testing (primarily) · API contract testing · UI testing · System and acceptance testing. EP and BVA also apply to performance boundary testing, security input validation, and compatibility range checks.
White-box techniques structure-based
design techniques
›
In plain words
You design test cases based on the internal structure of the code — logic paths, branches, conditions. Coverage percentage is the key output. The goal: ensure no code path has been silently left untested.
Structure-based. Requires access to source code or architecture diagrams. Primarily used at component/unit level, but also applies to integration-level flow testing and API routing logic.
Statement Coverage
›
Has every executable line been run at least once?
Weakness: Weakest criterion. 100% statement coverage does not mean both branches of an if/else were tested.
Example: if (x > 0) { doA(); } — passing only x=5 gives 100% statement coverage. The false branch (x ≤ 0) is never exercised.
Branch Coverage
›
Has every decision point gone both true and false?
Key fact: 100% branch coverage guarantees 100% statement coverage. The reverse is not true.

Most commonly required criterion in commercial software practice.
Example: if (x > 0) { doA(); } else { doB(); }
Requires 2 tests: x=5 (true → doA) and x=-1 (false → doB).
Condition Coverage
›
In a compound condition (A AND B), has each individual boolean been independently true and false?
Example: if (isAdmin AND isActive) — condition coverage requires isAdmin=T/F and isActive=T/F independently, even when the overall decision outcome stays the same.
Multiple Condition Coverage (MCC)
›
Every possible combination of atomic condition truth values in a compound decision must be tested. More thorough than condition coverage — exhaustive within the decision.
For if (A AND B): MCC requires all 4 combinations: TT, TF, FT, FF. For 3 conditions: 8 combinations. Grows exponentially — impractical beyond 3–4 conditions, which is why MC/DC was invented as a more efficient alternative.
Example: if (isAdmin AND isActive AND isVerified) — MCC requires 8 test cases (2³). MC/DC requires only 4 — each condition independently changes the outcome, without exhausting all combinations.
Path Coverage
›
Has every possible route through the code from start to finish been executed?
Most thorough, usually impractical. 10 sequential if/else blocks = up to 1,024 paths. Achievable only in small, safety-critical units.
MC/DC Coverage
›
Each condition in a compound decision can independently change the final outcome — no condition is masked or irrelevant.
Used in: Safety-critical systems — aviation (DO-178C Level A), medical devices, automotive (ISO 26262 ASIL D).
Example: if (A OR B OR C) — MC/DC proves that changing A alone (B and C fixed) changes the result, and independently for B and for C. No condition is redundant.
Applies to
Unit testing · Component testing · Integration flow testing · CI coverage gates. Usually implemented by developers as part of writing code — QA sets coverage criteria and reviews gaps against risk.
Experience-based techniques
design techniques
›
In plain words
Tests designed from the tester's knowledge, intuition, and prior experience — not from a formal specification or code structure. Particularly valuable for finding defects that systematic techniques miss, and for testing when specifications are incomplete or absent.
Complements black-box and white-box techniques. Most effective in combination — structured techniques find what was specified; experience-based techniques find what no one thought to specify.
Exploratory Testing
›
Simultaneously design and execute tests, learning about the system as you go. Not random clicking — structured exploration guided by a charter and time-boxed sessions.
Key components: Charter (what to explore and what risks to target) · Time-box (typically 45–90 min) · Debrief notes.

When to use: New features, poorly documented areas, after spec-based tests find nothing obvious, legacy code under regression.
Example: Charter: "Explore checkout under poor network conditions." Session: throttle connection, interrupt payment mid-flow, submit with expired tokens, trigger back-button after order placement. Finds 3 defects no spec-based test would have identified — the spec didn't cover these scenarios.
Error Guessing
›
Based on experience, anticipate where bugs are likely to hide — empty fields, null values, zero, special characters, maximum lengths, concurrent actions, race conditions.
Technique: Build a fault/error list from prior experience and known common defect types, then write targeted tests for each entry.

Works best: When the tester has domain or product expertise.
Example error list for an API:
· Empty string where ID expected
· Negative quantity in order
· SQL injection in search field
· Simultaneous double-submit of the same form
· JWT with future issue date
· Unicode characters in name fields
Checklist-based Testing
›
Tests designed against a reusable checklist of things to always verify — derived from past defects, standards, or domain conventions. More structured than error guessing, less formal than specification-based.
Advantage: Captures accumulated team knowledge. Reusable across releases.

Maintenance: Checklists must be updated — unchecked items from resolved defects give false confidence.
Example — API testing checklist:
☐ Correct HTTP status codes for all outcomes
☐ Error responses contain a descriptive message
☐ Authorization checked on every endpoint
☐ PII masked in logs
☐ All inputs validated and sanitized
☐ Rate limiting present and tested
Applies to
Any test level and type — most effective at system and acceptance testing where full system behavior is visible. Exploratory testing is particularly valuable for security surface testing, UX edge cases, and newly integrated areas. Cannot replace systematic techniques for coverage tracking — but finds defects systematic approaches miss.
Alternative categorization — by technique mechanism
Note
A second way to classify the same techniques — grouped by what drives test case design, rather than by access to source code. The ISTQB categorization (black / white / experience-based) is primary for certification. This alternative view helps understand why a technique works the way it does.
Data-based
›
In plain words
Tests derived from the data inputs the system accepts — partitions, boundaries, combinations of values.
Equivalence Partitioning
›
Group inputs where all values should behave identically. One test per group.
Boundary Value Analysis
›
Focus on partition edges — that is where off-by-one errors concentrate.
Pairwise Testing
›
When there are many input parameters, test all pairs of values rather than all full combinations. Covers most bugs with far fewer test cases.
Rationale: Most defects are caused by the interaction of at most 2 parameters. Pairwise ensures every 2-way combination is covered at least once without testing the full Cartesian product.
Example: 3 parameters × 3 values each = 27 full-factorial combinations. Pairwise reduces this to ~9 test cases while still catching all 2-way interactions.
Classification Tree Method
›
Structure input parameters as a tree of classes and values, then derive test cases by selecting one leaf from each branch. Provides a visual map of the input space.
Example: Search feature tree: query type (keyword / phrase / empty) × filters (none / category / price range) × sort (relevance / price / date). Makes it explicit which combinations are worth testing and which are redundant.
Behavior-based
›
In plain words
Tests derived from the observable behavior of the system — state transitions, user actions, end-to-end flows.
State Transition Testing
›
Model valid states, triggering events, and expected transitions. Test valid moves and rejected invalid ones.
Use Case Testing
›
Test as a real user completing a real goal — happy path, alternatives, and exception flows.
Rule-based
›
In plain words
Tests derived from business rules or logical relationships — the system must implement a defined rule and the test verifies it is applied correctly in every combination.
Decision Table Testing
›
Enumerate all relevant combinations of business conditions and verify the correct outcome for each.
Metamorphic Testing
›
When the exact expected output is unknown, verify that changing an input in a predictable way produces a predictably changed output. Tests a relationship between outputs rather than a specific value.
Use case: Testing ML models, search engines, compilers, numerical libraries — anywhere the "correct" answer is expensive or impossible to pre-compute.

Metamorphic relation: A known property the function must satisfy regardless of the specific input.
Example — search engine: Search "car" returns 150 results. Search "car OR automobile" must return ≥ 150 results. If it returns fewer, there is a defect — without needing to know the correct result set in advance.
Combination of techniques
›
In plain words
In practice, techniques are rarely used in isolation. Effective test design combines multiple techniques to cover different risk dimensions of the same feature.
A typical feature test suite: EP + BVA for input validation → Decision Table for business rules → State Transition for lifecycle → Use Case for end-to-end flows → Exploratory for what the spec forgot → Checklist for cross-cutting concerns.
Example — e-commerce checkout
EP + BVA: Price inputs, quantity limits, discount code length
Decision Table: Discount eligibility (member × order value × promotion active)
State Transition: Order lifecycle (pending → confirmed → shipped → delivered)
Use Case: Happy path + payment failure recovery
Error Guessing: Double-submit · expired session mid-checkout · item going out of stock between cart and confirm
Checklist: Auth on all endpoints · PII masking in logs · correct HTTP status codes

Test levels — the hierarchy
Each level tests a larger scope than the one below it. Tests at lower levels are faster, more numerous, and cheaper to fix when they fail. Tests at higher levels are slower and fewer, but closer to real-world use. The levels do not replace each other — they are complementary layers. A defect caught at unit level costs a fraction of the same defect found at acceptance.

The levels — detail
Unit / Component / Module testing
smallest scope
›
In plain words
Test a single unit of code in complete isolation. Everything it depends on is replaced with a test double (mock, stub, fake). The only question: "Does this one piece of logic work correctly on its own?"
A unit is the smallest individually testable element — a function, method, class, or module. Dependencies are isolated: no real database, no real network. If a dependency is called, it is mocked. The test verifies the logic of the unit itself, not the behavior of its dependencies.
What it finds
›
Logic errors inside individual units — wrong calculations, missing conditions, unhandled edge cases, null pointer defects.
Finds: calculateTax(0, 0.2) throws NullPointerException ✗
Does NOT find: Whether the Tax service can connect to the Pricing database in staging — that is an integration-level concern.
Who runs it and when
›
Developer-owned. Runs on every commit as part of the CI pipeline. TDD (test-first) means tests are written before the implementation code.
Tools: Jest (JS/TS) · JUnit / TestNG (Java) · pytest (Python) · NUnit / xUnit (.NET) · go test (Go) · RSpec (Ruby)
Microservices context
›
In microservices, a "unit" is typically one service's internal logic — a domain model, a business rule, a data transformation. Each service has its own independent unit test suite.
Example: Order service — unit test for order validation: verifies that an order with negative quantity is rejected, zero items is rejected, a valid order passes. All calls to database and downstream services are stubbed — the test verifies the validation logic only.
Component integration testing
interfaces between components
›
In plain words
Individual components pass unit tests in isolation — but do they work correctly together when connected? Integration testing answers that. The focus is on the interfaces: what one component sends and what the other expects to receive.
Does not test the whole system — only specific component pairs or groups. Everything outside the scope of the integration under test is still mocked. The question: "When A calls B, do they agree on the contract?"
What it finds that unit testing misses
›
Interface mismatches — field names, data types, date formats, HTTP status codes — that unit tests can never catch because each unit is tested with its own mocked responses.
Classic example: Order service unit tests pass — they mock Inventory to return {"available": true}. Inventory unit tests pass. But real Inventory returns {"inStock": true}. Integration test catches the field name mismatch that both unit suites missed entirely.
Incremental vs big-bang integration
›
Incremental: integrate one component at a time (bottom-up from units, or top-down from the API surface). Big-bang: integrate all at once, then test — harder to isolate which interface caused a failure.
Bottom-up: Test utility/data layers first, build up gradually — real components replace mocks as they are verified.
Top-down: Test from the API facade downward, stub lower layers first — good when the top-level API contract is the primary risk.
Consumer-driven contract testing (Pact)
›
A technique specific to integration level: the consumer (calling service) defines the contract it expects. The provider (called service) verifies it meets that contract. Both sides test independently — no shared environment needed.
Example: Order service writes a Pact saying "I expect GET /inventory/{id} to return { id, inStock, quantity }." Inventory service runs Pact verification in its own CI. If Inventory removes the quantity field, the Pact test catches it before the two services are ever deployed together in staging.
QA angle
Integration tests are where unit tests' false confidence is exposed. A system can have 95% unit test coverage and still fail catastrophically at integration level if the mocks do not reflect reality. Contract testing (Pact) is the gold standard for catching this class of failure in microservices architectures.
System testing
full integrated system
›
In plain words
The complete system — all components integrated — is tested as a whole against system requirements. No mocks. Real services, real databases, real infrastructure. The question: "Does the system, taken together, behave as specified?"
QA-owned. The primary level for formal test execution. Tests derive from system requirements — functional AND non-functional. The environment should mirror production as closely as possible.
What it tests
›
Both functional and non-functional requirements at system scope: end-to-end user flows, performance under load, security, usability, reliability — everything the system specification covers.
Example: Full checkout — search → add to cart → apply discount → enter payment → confirmation email sent → inventory decremented → order record created. All real, all integrated, no stubs.
What it finds that lower levels miss
›
Emergent defects — behavior that only appears when ALL components interact under realistic conditions: race conditions, data consistency failures across services, configuration mismatches, environmental issues.
Example: Order service and Payment service both pass unit and integration tests. At system level, under concurrent load: two users simultaneously purchase the last item in stock — both orders succeed, inventory goes negative. The race condition only manifests when both services run against a shared database under real concurrency.
[System integration testing]
›
Testing the integrated system against external systems — third-party APIs, payment processors, legacy ERPs, external data feeds. Sometimes a separate formal level, sometimes folded into system testing depending on project context.
Example: Our order system integrated with Stripe (payment), SendGrid (email), and a legacy warehouse management system. System integration tests verify the full data flow across all three external integrations under realistic conditions — not mocked adapters.
Acceptance testing
validates business goals
›
In plain words
System testing asks "does it meet the spec?" — acceptance testing asks "does the spec actually satisfy the users and the business?" The system can pass system testing and still fail acceptance if the requirements were wrong or incomplete to begin with.
Performed by or with the intended users, business stakeholders, or product owners — not by QA alone. Validates against business requirements and user goals, not technical specifications. This is the formal gate before release.
UAT — User Acceptance Testing
›
Actual users or business representatives validate the system meets their needs under conditions resembling real use.
Example: Finance team uses the new reporting module on real (anonymized) production data for one week before go-live. Their sign-off confirms the feature meets real operational needs, not just documented requirements.
Contractual acceptance
›
Verifies the system meets acceptance criteria written into the contract between the development team and the client. Formal pass/fail against an agreed checklist.
Regulatory acceptance
›
Verifies compliance with laws, regulations, or industry standards before the system can be legally operated.
Example: Medical device software passes regulatory acceptance against IEC 62304 before deployment. Financial system demonstrates GDPR compliance before processing personal data.
Alpha / Beta testing
›
Pre-release validation with real users in conditions closer to actual deployment.
Alpha: Internal users or invited testers in a controlled environment, close QA oversight.
Beta: External users in their own environment, limited QA oversight — catches issues that only emerge at real-world scale and diversity of usage.
Key distinction from system testing
System testing: "Does the system match the specification?" Acceptance testing: "Does the specification match what users actually need?" A system can be defect-free at system level and still be rejected at acceptance if the wrong feature was built. This is why acceptance criteria must be agreed before development starts, not after.
Change-induced testing — not a level, not a type
Important distinction
Confirmation testing and regression testing are not test types or test levels — they are testing activities triggered by change. They can be performed at any test level using any technique. What makes them special is the trigger, not what they test or how.
Confirmation testing (re-testing)
›
In plain words
A defect was found. A fix was deployed. Confirmation testing re-runs the specific test(s) that detected the defect to verify the fix actually works.
Narrow focus: Re-run exactly the test cases that failed. Not a broad sweep — that is regression testing's job. Confirmation testing answers one question: "Is this specific defect now fixed?"
When and how
›
After a fix is deployed to the test environment, re-execute the failing test(s) with the same steps, same data, same environment. Pass → confirmed. Fail → defect re-opened.
Example: Bug #1234: checkout fails when cart has exactly 10 items (off-by-one in quantity validation). Fix deployed. Confirmation test: add exactly 10 items, proceed to checkout. Completes successfully → #1234 confirmed fixed. Then: trigger regression testing to check for side effects.
Regression testing
›
In plain words
After any change — a new feature, a bug fix, a refactor, a configuration update — verify that nothing that was working before is now broken. Changes have unintended side effects; regression testing finds them.
Broad scope: Covers any area of the system that could plausibly have been affected by the change. Scope expands with risk — a critical shared library change may trigger a full suite; a minor UI text change needs only a targeted sweep.
Risk-based scope selection
›
Running the full suite on every change is expensive. Prioritize: what changed, what it touches, what has failed historically, what is business-critical.
Prioritization factors: Changed code paths · Downstream dependencies · Historical defect concentration · Business impact of failure · Frequency of real user interaction
Why automation is essential
›
Regression suites grow with the product. Manual regression at scale is unsustainable — automation is required to run it fast enough to provide feedback after every change.
Example: 3-year-old product. Full manual regression = 2 weeks. Release cadence = every 2 weeks. Without automation, QA spends 100% of capacity on regression and has zero capacity for new feature testing.
Confirmation vs Regression
Confirmation: "Is this specific defect fixed?" — narrow, targets the known failure.
Regression: "Did fixing this break anything else?" — broad, targets unknown side effects.
Both are triggered by change. They ask different questions and use different scope. Both are typically run after a fix is applied — confirmation first, then regression.
Common misconceptions
Smoke = Sanity — and neither is a formal ISTQB test type
›
Reality
"Smoke test" and "sanity test" are informal industry terms for the same thing: a quick, shallow check that a build is stable enough to test. ISTQB does not list them as formal test types. In interviews, the correct answer is that these are informal practices — a form of lightweight confirmation/regression testing typically run at system level to verify a build is alive before the full test suite is executed.
Origin of "smoke test": Hardware engineering — power on a circuit board; if smoke appears, stop immediately. Applied to software: if the build cannot start or crashes on launch, there is no point running the full test suite. Smoke testing verifies the build is alive, not that it is correct.
Maintenance testing ≠ Maintainability
›
Reality
Maintenance testing — a test ACTIVITY. Testing triggered by a change to an existing system: a defect fix, a new feature added to a live product, a migration to a new environment, retirement of a legacy system. Something changed; you test to verify the change and catch side effects.

Maintainability — an ISO 25010 quality CHARACTERISTIC. How easy it is for developers to modify, analyze, test, and extend the system's code. A property of the product's architecture, not a testing activity.
Example to keep them separate
Maintenance testing: "We patched a security vulnerability in the auth service. We ran maintenance testing — confirmation + regression — to verify the patch works and has no side effects."

Maintainability: "The auth service has poor maintainability: low testability (concrete dependencies, no injection), poor analysability (no structured logging), risky modifiability (73 hardcoded string literals)."

One describes what you DO after a change. The other describes what the code IS.
e2e is not a test level — it is a scope descriptor
›
Reality
"End-to-end test" describes the scope of a test scenario — it covers the full flow from one end of the system to the other (UI → API → database → external services → back). It is not a separate test level in the ISTQB hierarchy. e2e tests are run at system level or acceptance level.
When a team says "our e2e suite," they mean "our suite of system-level tests that exercise complete user flows." The term describes what the tests cover, not where they sit in the level hierarchy.
Why this matters
Teams that treat e2e as a separate level tend to skip component integration testing ("we'll catch it in e2e") — then integration bugs are expensive to diagnose because they only surface in full-system runs. The correct approach: unit → integration → system (e2e) — not unit → e2e directly, skipping the integration level.
