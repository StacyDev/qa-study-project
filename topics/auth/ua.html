00 Що таке автентифікація і авторизація? КОНЦЕПЦІЯ

АВТЕНТИФІКАЦІЯ (authn)
"Хто ти?"
Перевірка того, що суб'єкт запиту є тим, за кого себе видає.

Приклади: перевірка логіна + пароля, валідація підпису JWT, верифікація сертифіката.

"Що тобі дозволено робити?"
Визначення того, до чого вже автентифікований суб'єкт має право доступу або що може виконувати.

Приклади: перевірка ролей, scope, прав, належності ресурсу.

Що вважається "методом автентифікації"?

Метод автентифікації — конкретний механізм, за допомогою якого клієнт підтверджує свою особу в запиті. Приклади: надсилання пароля, API-ключа, підписаного токена.

Фреймворк авторизації (наприклад, OAuth 2.0) — це протокол, що визначає правила отримання стороннім клієнтом обмеженого доступу до ресурсів. Він використовує методи автентифікації як складові, але сам методом автентифікації не є. Це розмежування критично важливе — дивіться розділ 13.

00b Кодування vs шифрування vs хешування КОНЦЕПЦІЯ
Три операції, які виглядають схоже, але є принципово різними. Плутанина між ними — серйозна помилка. Кожна тема в сфері автентифікації залежить від розуміння того, яка з трьох операцій застосовується.
КОДУВАННЯ
Мета: перетворення формату для сумісності під час передачі.
Зворотне? Так — ключ не потрібен.
Секретне? Ні — будь-хто може декодувати.

Приклади: Base64, Base64url, URL encoding, hex.
ШИФРУВАННЯ
Мета: приховати дані так, щоб лише авторизовані сторони могли їх прочитати.
Зворотне? Так — за наявності правильного ключа.
Секретне? Так — без ключа дані безглузді.

Приклади: AES-256, RSA (для обміну ключами).
ХЕШУВАННЯ
Мета: отримати відбиток даних фіксованої довжини.
Зворотне? Ні — за задумом.
Секретне? Н/З — інша мета.

Приклади: SHA-256, bcrypt, MD5 (слабкий), HMAC-SHA256.

КРИТИЧНО — НЕ ГОВОРІТЬ

"JWT зашифрований" — це не так (якщо спеціально не використовується JWE).
"Base64 — це шифрування" — це не так. Це кодування. Будь-хто може декодувати.
"Підпис JWT зашифровано" — підпис є криптографічним результатом (HMAC або цифровий підпис RSA), закодованим у base64url для передачі. Це не "зашифровані дані".

Підпис JWT — точне пояснення

ЩО ВІДБУВАЄТЬСЯ ПРИ ПІДПИСАННІ JWT
// Крок 1: кодуємо заголовок (JSON → base64url)
base64url({ "alg": "RS256", "typ": "JWT" })
→ "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9"

// Крок 2: кодуємо payload (JSON → base64url)
base64url({ "sub": "user123", "exp": 1745000000 })
→ "eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxNzQ1MDAwMDAwfQ"

// Крок 3: підписуємо конкатенацію закодованих частин
signing_input = "eyJhbGci..." + "." + "eyJzdWIi..."
signature_bytes = RS256_sign(signing_input, private_key)

// Крок 4: кодуємо байти підпису в base64url для передачі
base64url(signature_bytes) → "SflKxwRJSMe..."

// Готовий JWT = заголовок . payload . підпис (всі в base64url)
"eyJhbGci..." + "." + "eyJzdWIi..." + "." + "SflKxwRJSMe..."
ТОЧНЕ ФОРМУЛЮВАННЯ

Підпис JWT — результат алгоритму підпису, застосованого до закодованого заголовка + закодованого payload з використанням ключа. Цей результат (сирі байти) потім кодується в base64url для передачі. Заголовок і payload кодуються в base64url (читаються будь-ким). Підпис — криптографічний відбиток: декодувати до чогось значущого неможливо, підробити без ключа підпису — також.

01 Basic Authentication МЕТОД AUTHN RFC 7617
Найпростіший метод HTTP-автентифікації (RFC 7617). Клієнт надсилає логін та пароль з кожним запитом — у кодуванні base64 в заголовку Authorization. Без токенів. Без сесій. Без стану на сервері.
ЗАВЖДИ УТОЧНЮЙТЕ

Base64 — це кодування, не шифрування. Значення YWxpY2U6c2VjcmV0 миттєво декодується в alice:secret без будь-якого ключа. Basic Auth є безпечним лише тоді, коли HTTPS шифрує все з'єднання. Без HTTPS облікові дані передаються відкритим текстом.

Покроковий процес

ПРОЦЕС BASIC AUTH
1

Клієнт надсилає запит без облікових даних.
GET /api/orders HTTP/1.1

3

Клієнт об'єднує логін і пароль через двокрапку, потім кодує результат у base64.
"alice:secret123" → base64 → "YWxpY2U6c2VjcmV0MTIz"
4

GET /api/orders Authorization: Basic YWxpY2U6c2VjcmV0MTIz

Сервер декодує значення з base64, розділяє по двокрапці, хешує пароль і перевіряє хеш з хешем паролю що зберігається у базі даних. Повертає 200 (дійсний) або 401 (недійсний).
Сесія не створюється. Сервер не зберігає стан — перевірка виконується з нуля для кожного запиту.

02 Digest Authentication МЕТОД AUTHN RFC 7616
Digest Auth (RFC 7616) розроблено для усунення головної слабкості Basic Auth: пароль ніколи не передається мережею. Натомість клієнт надсилає хеш пароля, об'єднаного з випадковим значенням, згенерованим сервером (nonce). Навіть якщо перехопити — хеш не можна відновити до вихідного пароля.

Ключова концепція: nonce

Nonce (число, що використовується один раз) — випадковий рядок, який сервер генерує для кожного запиту автентифікації. Клієнт змішує пароль з цим nonce перед хешуванням. Оскільки nonce змінюється з кожним запитом, перехоплена відповідь не спрацює в іншому запиті.

ПРОЦЕС DIGEST AUTH
1
КЛІЄНТ → СЕРВЕР
Клієнт надсилає запит без облікових даних.
2
СЕРВЕР → КЛІЄНТ (виклик)
Сервер відповідає 401 і включає свіжий nonce в заголовок.
401 Unauthorized WWW-Authenticate: Digest realm="MyApp", nonce="abc123xyz"
3
КЛІЄНТ (внутрішньо)
Клієнт хешує облікові дані разом із nonce, використовуючи MD5 (або SHA-256 в новіших версіях).
HA1 = MD5("alice:MyApp:secret123") HA2 = MD5("GET:/api/orders") response = MD5(HA1 + ":" + nonce + ":" + HA2)
4
КЛІЄНТ → СЕРВЕР
Клієнт надсилає хеш (так звану "response") — але не пароль.
Authorization: Digest username="alice", nonce="abc123xyz", response="6f3a..."
5
СЕРВЕР
Сервер зберігає у себе захешований пароль. Він бере хеш паролю, застосовує до нього nonce. Результат сервер порівнює з захешованим паролем + nonce отриманим від клієнта. Якщо збігаються → 200.
Пароль ніколи не передається. Якщо канал перехоплено, хеш сам по собі не можна відновити.

03 API-ключі МЕТОД AUTHN Без RFC — вендорна конвенція
API-ключ — статичний рядок, згенерований сервером і наданий клієнту, який слугує обліковими даними для ідентифікації. На відміну від Basic Auth, клієнт не надсилає логін/пароль — він надсилає ключ. Сервер шукає ключ у базі даних для ідентифікації клієнта та отримання його прав.

GET /api/users Authorization: ApiKey abc123xyz456 — або — X-API-Key: abc123xyz456

API СЕРВЕР → БАЗА ДАНИХ
Сервер шукає хеш ключа в базі даних, щоб знайти, якому користувачу/клієнту він належить і які у нього права.
SELECT user_id, scopes, active FROM api_keys WHERE key_hash = hash(request_key)

API-КЛЮЧІ ЗБЕРІГАЮТЬ СТАН

На відміну від JWT, API-ключ не має вбудованого часу закінчення дії. Дійсність визначається через запит до бази даних при кожному зверненні. Це означає: API-ключі потребують серверного зберігання, їх можна миттєво відкликати (видалити з БД), але вони додають затримку (запит до БД при кожному зверненні).

КУТИ ТЕСТУВАННЯ QA
① Ключ у query-параметрі → перевірити логи сервера на наявність витоку ключа. ② Відкликати ключ через адмін-панель → одразу перевірити, чи він все ще працює (має повертати 401). ③ Тест rate limiting для ключа. ④ Тест з ключем, що належить іншому scope. ⑤ Перевірити, що відкритий ключ не зберігається в БД (лише хеш). ⑥ Перевірити, чи обов'язковий HTTPS — ключі в заголовках все одно є відкритим текстом на транспортному рівні без TLS.
04 Сесійна автентифікація МЕТОД AUTHN RFC 6265 (Cookie)
Сесійна автентифікація — класична модель веб-автентифікації. Після одноразового входу з обліковими даними сервер створює запис сесії у своїй базі даних і видає клієнту ідентифікатор сесії (зберігається у cookie). Кожен наступний запит надсилає цей ідентифікатор — сервер шукає його для ідентифікації користувача. Стан сесії зберігається на сервері.
ПРОЦЕС СЕСІЙНОЇ АВТЕНТИФІКАЦІЇ
1
КЛІЄНТ → СЕРВЕР
Користувач відправляє форму входу з обліковими даними.
POST /login Body: { username: "alice", password: "secret123" }
2
СЕРВЕР (внутрішньо)
Сервер перевіряє облікові дані. Якщо дійсні: створює запис сесії у сховищі (база даних/Redis), генерує унікальний випадковий ідентифікатор сесії.
3
СЕРВЕР → КЛІЄНТ
Сервер надсилає ідентифікатор сесії клієнту через заголовок Set-Cookie.

05 Bearer-токени та JWT ТОКЕН RFC 6750 (Bearer) RFC 7519 (JWT)
Bearer-токен — токен доступу, де сам факт його наявності надає доступ: "хто пред'являє цей токен — той входить". Найпоширеніший формат — JWT (JSON Web Token). На відміну від сесій, JWT є самодостатнім — всі дані для валідації містяться всередині токена. Для верифікації JWT запит до бази даних не потрібен.

Що означає "Bearer"

Bearer — назва схеми в заголовку Authorization. Вона означає: "пред'явник цього токена авторизований". Сервер надає доступ тому, хто пред'являє дійсний токен — не перевіряючи, чи це початковий отримувач. Саме тому крадіжка токена є серйозним ризиком.

GET /api/orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIn0.SflKxw...

Структура JWT — три частини

ВАЖЛИВА ТОЧНІСТЬ

Всі три частини кодуються в base64url для передачі. Але заголовок і payload — читабельний JSON (лише кодування). Підпис — криптографічний результат (алгоритму підпису), закодований у base64url. Декодувати до чогось значущого без ключа неможливо, підробити без ключа підпису — також.

{

// ЧАСТИНА 2: PAYLOAD — claim'и (дані про суб'єкт)
// (base64url-кодований JSON — читабельний для будь-кого — НЕ секретний)
{

HS256 vs RS256 — алгоритми підпису

HS256 — СИМЕТРИЧНИЙ (HMAC-SHA256)
Один спільний секретний ключ для підпису та верифікації. Будь-який сервіс, що верифікує токени, повинен знати секрет. Якщо будь-який верифікатор скомпрометовано — секрет підпису розкрито, зловмисник може підробляти токени.

Підходить для: односервісних застосунків, внутрішніх інструментів.
RS256 — АСИМЕТРИЧНИЙ (RSA-SHA256)
Приватний ключ підписує (лише auth-сервер, ніколи не передається). Публічний ключ верифікує (будь-який сервіс може його мати). Скомпрометований верифікатор не може підробляти токени.

Підходить для: мікросервісів, розподілених систем, мультикомандних архітектур.

Валідація JWT — що сервер перевіряє при кожному запиті

ПОСЛІДОВНІСТЬ ВАЛІДАЦІЇ JWT
1
Підпис — перерахувати очікуваний підпис з отриманого заголовка+payload. Порівняти з підписом у токені. Якщо не збігається → 401.
2
Час закінчення (exp) — чи поточний час до мітки exp? Якщо прострочено → 401.
3
Видавець (iss) — чи збігається видавець з очікуваним? Якщо невідповідність → 401.
4
Аудиторія (aud) — чи призначений цей токен для цього сервісу? Якщо невідповідність → 401.
5
Алгоритм (alg) — чи алгоритм очікуваний сервером? Відхилити "none". Якщо несподіваний → 401.
6
Всі перевірки пройдено → витягти claim'и з payload → перейти до авторизації.
КРИТИЧНА АТАКА — alg:none

Якщо JWT-бібліотека приймає "alg": "none", вона повністю пропускає верифікацію підпису. Зловмисник встановлює alg в none, змінює payload (наприклад, роль на admin), видаляє підпис і надсилає токен. Сервер приймає його без верифікації. Тест: надіслати токен з alg:none — має повертати 401.

Проблема відкликання

JWT не зберігає стан — після видачі жодного запису в базі даних немає. Якщо токен вкрадено або користувача заблоковано, токен залишається дійсним до закінчення exp. Заходи протидії:

  • Короткий TTL — access-токени мають закінчуватись через 5–15 хвилин.
  • Refresh-токени — довгострокові токени для отримання нових access-токенів без повторного входу.
  • Блокліст jti — зберігати відкликані jti у Redis із TTL рівним часу закінчення дії токена.
  • Rotation refresh-токенів — кожне використання скасовує старий і видає новий.
КУТИ ТЕСТУВАННЯ QA
① Змінити payload вручну (наприклад, sub або role) → збережений підпис більше не збігається → має повертати 401. ② Відправити прострочений токен → 401. ③ Відправити токен з alg:none → 401 (критичний тест). ④ Відправити токен з невідповідним aud → 401. ⑤ Відправити токен з невідповідним iss → 401. ⑥ Декодувати payload на jwt.io — чи містить він зайві чутливі дані?
06 Access та Refresh токени ПАРА ТОКЕНІВ RFC 6749 §1.4
Access та refresh токени вирішують протиріччя між безпекою і зручністю. Короткий access-токен обмежує вікно витоку. Довгий refresh-токен дозволяє отримувати нові access-токени без повторного входу.
ACCESS TOKEN
TTL: хвилини (зазвичай 5–15 хв)
Формат: зазвичай JWT (самодостатній)
Куди передається: до кожного захищеного API-ендпоінта
Зберігається: в пам'яті (SPA) або httpOnly cookie
При закінченні: клієнт використовує refresh-токен для отримання нового
REFRESH TOKEN
TTL: дні-тижні (або довше)
Формат: непрозорий рядок (випадковий, без структури) або JWE (зашифрований JWT — 5 частин)
Куди передається: ЛИШЕ до /token ендпоінта (refresh token endpoint)
Зберігається: httpOnly + Secure + SameSite cookie
При використанні: видається новий access-токен; при rotation — також новий refresh-токен

Чому refresh-токен не є JWT (зазвичай)

JWT самодостатній — будь-хто може його прочитати і перевірити без запиту до бази даних. Refresh-токен повинен бути відкличним: якщо він скомпрометований або користувач виходить — він має негайно стати недійсним. Непрозорий рядок вимагає пошуку в БД при кожному використанні, що уможливлює миттєве відкликання. JWE є альтернативою: зашифрований (лише auth-сервер може розшифрувати), але все одно потребує перевірки в БД для rotation та виявлення повторного використання.

ТИПОВА ЗНАХІДКА ПРИ ТЕСТУВАННІ

Якщо refresh-токен не декодується на jwt.io — це правильна поведінка, не баг. Непрозорий токен не має структури. JWE зашифрований — лише auth-сервер може його розшифрувати. Застосовуйте поведінкове тестування (що робить система при його використанні?), а не тестування вмісту.

КУТИ ТЕСТУВАННЯ QA
① Після виходу: POST refresh-токена до /token → має повертати 401 (тест зомбі-сесії). ② Rotation + повторне використання: зберегти R1 → використати → отримати R2 → використати R1 знову → і R1, і R2 мають бути недійсними. ③ Підміна типу: надіслати refresh-токен до /api/users/me як Bearer → має повертати 401. ④ TTL: тест через 7/14/30 днів — коли він закінчується? ⑤ Прив'язка client_id: використати refresh-токен з іншим client_id → має повертати 401. ⑥ Зберігання: у DevTools → перевірити, що refresh-токен у httpOnly+Secure+SameSite cookie, а не в localStorage. ⑦ Паралельні сесії: два входи → два refresh-токени → обидва мають працювати незалежно.
07 OAuth 1.0 ФРЕЙМВОРК AUTHZ RFC 5849
OAuth 1.0 (RFC 5849, 2010) — перший стандартизований протокол делегованого доступу: сторонній застосунок отримує доступ до ресурсів користувача, не отримуючи його облікових даних. Здебільшого витіснений OAuth 2.0, але ще трапляється у старих API (Twitter/X classic API, деякі платіжні шлюзи).
ЩО ОЗНАЧАЄ "ФРЕЙМВОРК АВТОРИЗАЦІЇ"

OAuth — це не метод автентифікації. Це фреймворк — набір правил про те, як сторонній застосунок може отримати обмежений доступ до ресурсів. Користувач автентифікується на сервері авторизації будь-яким методом, який той вимагає. OAuth визначає протокол, за яким сторонній застосунок отримує токен, що представляє наданий доступ.

Як працює OAuth 1.0

ПРОЦЕС OAUTH 1.0 — 3-СТОРОННЯ АВТЕНТИФІКАЦІЯ

Частина 2 — Абстрактний потік авторизації (RFC 6749 §1.2)

До будь-якого конкретного типу гранту RFC 6749 визначає загальний шестикроковий протокол, якому слідують усі типи грантів. Розуміння цього абстрактного потоку необхідне для розуміння того, чому конкретний тип гранту працює саме так.

АБСТРАКТНИЙ ПОТІК RFC 6749 — ВСІ ТИПИ ГРАНТІВ
A
КЛІЄНТ → ВЛАСНИК РЕСУРСУ
Запит авторизації. Клієнт просить власника ресурсу надати доступ. Може бути прямим (ROPC) або через AS (всі інші типи).
B
ВЛАСНИК РЕСУРСУ → КЛІЄНТ
Грант авторизації. Власник ресурсу надає дозвіл. Грант — обліковий запис, що представляє авторизацію власника. Тип залежить від використаного методу гранту.
C
КЛІЄНТ → СЕРВЕР АВТОРИЗАЦІЇ
Грант авторизації (пред'являється AS). Клієнт пред'являє грант до Ендпоінта токена разом зі своїми обліковими даними (client_id, client_secret або PKCE verifier).
D
СЕРВЕР АВТОРИЗАЦІЇ → КЛІЄНТ

E

F

Захищений ресурс. Resource сервер перевіряє access-токен (підпис, термін дії, scope, аудиторія) та повертає запитуваний ресурс.
КЛЮЧОВИЙ ВИСНОВОК — ДВОЕТАПНА СТРУКТУРА

Етап 1 (кроки A–B): Клієнт отримує грант авторизації від Власника ресурсу. Це частина, яку бачить користувач — вхід, екран згоди.
Етап 2 (кроки C–D): Клієнт обмінює грант на access-токен у Сервера авторизації. Це зворотньоканальний обмін — користувач не бере участі.

Тип гранту визначає, як виглядає грант авторизації на кроці B і як відбувається обмін на кроці C. Абстрактний потік A–F є однаковим незалежно від типу гранту.

Частина 3 — Потоки за типом гранту

② Повторне використання коду: надіслати той самий код двічі → другий виклик повинен повернути invalid_grant.

⑥ Валідація відповіді токена: перевірити наявність та коректність access_token, expires_in, refresh_token, scope.

3.2 Authorization Code + PKCE (RFC 7636)

КОЛИ ВИКОРИСТОВУВАТИ

Публічні клієнти — SPA, мобільні застосунки, CLI-інструменти — що не можуть зберігати client_secret. Також рекомендовано для конфіденційних клієнтів як додатковий рівень захисту. PKCE (Proof Key for Code Exchange, "pixie") розширює Authorization Code динамічно генерованим підтвердженням, що прив'язує код до клієнта, який його запросив. Клієнт генерує code_verifier, обчислює code_challenge = BASE64URL(SHA256(code_verifier)) та надсилає challenge наперед. При обміні коду надсилається verifier — AS перевіряє відповідність хешу.

3.3 Застарілі типи грантів

IMPLICIT GRANT — RFC 6749 §4.2 — ЗАСТАРІЛИЙ

Розроблено для браузерних SPA до появи PKCE. Повертав access_token безпосередньо у фрагменті URL redirect (#access_token=...). Токени потрапляли в історію браузера, заголовки Referer та будь-який JavaScript на сторінці (XSS). Refresh-токен не дозволявся. Автентифікація клієнта відсутня.

Замінений: Authorization Code + PKCE. Досягає тієї самої мети без витоку токенів.

RESOURCE OWNER PASSWORD CREDENTIALS (ROPC) — RFC 6749 §4.3 — ЗАСТАРІЛИЙ

Клієнт збирає логін і пароль користувача напряму та надсилає їх до Ендпоінта токена. Порушує основний принцип OAuth — облікові дані не повинні проходити через сторонній застосунок. Екран згоди відсутній. MFA неможливий. Ризик логування облікових даних.

Замінений: Будь-яким потоком на основі redirect. Якщо абсолютно неминучий (лише для першопартійних застосунків), розглядати як ціль міграції.

3.4 Client Credentials (RFC 6749 §4.4)

КОЛИ ВИКОРИСТОВУВАТИ

Машина-до-машини (M2M) — мікросервіси, що викликають один одного, фонові задачі, CI/CD-пайплайни. Взаємодія з власником ресурсу відсутня. Клієнт автентифікується у Сервера авторизації та отримує access-токен безпосередньо. У цьому потоці refresh-токен не видається — після закінчення терміну дії клієнт просто запитує новий токен з тими самими обліковими даними.

Аспекти безпеки — Client Credentials

  • client_secret потрібно захищати як пароль. Зберігати у змінних середовища або менеджері секретів (Vault, AWS Secrets Manager). Ніколи — у коді або конфіг-файлах у системі контролю версій.
  • Принцип мінімальних привілеїв для scope. Запитуйте лише ті scope, які дійсно потрібні сервісу. Скомпрометований токен не повинен надавати доступ до всього.
  • Термін дії та ротація токенів. Короткий термін дії обмежує збитки від витоку. Оскільки refresh-токен не використовується, закінчення терміну є природним механізмом анулювання.
  • Немає контексту власника ресурсу. Claim sub у JWT — це client_id, а не ID користувача. Resource сервер не повинен плутати M2M-токени з користувацькими.

① Невірний client_secret → invalid_client.
② Scope перевищує надані дозволи → invalid_scope.

⑤ Примусове застосування scope токена: запросити токен зі scope A. Перевірити, що він не може отримати доступ до ендпоінта, що вимагає scope B.
⑥ Ротація client_secret: змінити секрет у конфігурації AS. Перевірити, що старий секрет негайно відхиляється. Перевірити роботу нового секрету.

3.6 Refresh-токен (RFC 6749 §6)

Потік refresh-токена — не тип гранту, а механізм, доступний у типах грантів, що видають refresh-токен (Authorization Code, Device Authorization). Коли access-токен закінчується, клієнт використовує refresh-токен для отримання нового access-токена без повторної автентифікації користувача.

Без ротації: вкрадений refresh-токен дає зловмиснику постійний доступ до ручного відкликання.

КОЛИ REFRESH-ТОКЕН НЕ ВИДАЄТЬСЯ

• Грант Client Credentials: без refresh-токена. Сервіс просто повторно автентифікується з client_id + client_secret.
• Implicit grant (застарілий): специфікація явно забороняє refresh-токени.
• Короткострокові сесії лише з access-токеном, де повторна автентифікація є навмисною.

QA — REFRESH-ТОКЕН
① Використаний refresh-токен (ротація активна): повторно надіслати старий refresh_token → invalid_grant.
② Прострочений refresh-токен: використати після TTL → invalid_grant. Користувач повинен пройти повторну автентифікацію.
③ Відкликаний refresh-токен: відкликати через /revoke, потім спроба використання → invalid_grant.
④ Refresh-токен надіслано до Resource сервера: перевірити відхилення. Refresh-токен дійсний лише на Ендпоінті токена.
⑤ Новий access-токен після refresh: перевірити, що новий токен приймається Resource сервером.

4.2 Валідація access-токена (Resource сервер)

Resource сервер повинен незалежно перевіряти кожен access-токен відповідно до RFC 6750. Для JWT access-токенів:

  • Підпис: Перевірити з використанням публічного ключа AS (RS256) або спільного секрету (HS256). Отримати JWKS з well-known ендпоінта AS.
  • Claim exp: Поточний час повинен бути до закінчення терміну. Враховувати відхилення годинника (≤60 секунд).
  • Claim aud: Повинен містити ідентифікатор цього Resource сервера. Запобігає прийняттю токенів, виданих для Сервісу A, Сервісом B.
  • Claim iss: Повинен збігатися з відомою URL Сервера авторизації.
  • Claim scope: Повинен включати необхідний дозвіл для запитуваного ендпоінта.
  • Not before (nbf): Якщо присутній, поточний час повинен бути на або після цього значення.

5.4 Наскрізні тести потоку

  • Happy path для кожного типу гранту: Повний потік від початку до доступу до захищеного ресурсу повертає 200 з правильними даними.
  • Оновлення токена: Дочекатися закінчення access-токена. Перевірити, що клієнт автоматично оновлює та повторює запит. Користувача не запитують про повторний вхід.
  • Вихід: Після виходу refresh-токен відкликається. Спроба використання → invalid_grant. Access-токен закінчується у межах свого TTL.
  • Примусове застосування scope: Токен зі scope A не може отримати доступ до ендпоінта, що вимагає scope B.
  • Відкликання: Відкликати токен через /revoke. Подальше використання повертає 401.
  • PKCE наскрізний: Повний потік без client_secret успішний. Спроба з перехопленим кодом але невірним verifier провалюється.

5.5 Типові помилки на співбесіді

НЕПРАВИЛЬНО: "OAUTH — ЦЕ АВТЕНТИФІКАЦІЯ"

OAuth 2.0 — фреймворк авторизації. Він не автентифікує користувачів — він надає дозволи. Автентифікацію забезпечує OpenID Connect, побудований поверх OAuth 2.0.

НЕПРАВИЛЬНО: "IMPLICIT GRANT ДЛЯ SPA"

Implicit grant застарілий в OAuth 2.1. Сучасні SPA використовують Authorization Code + PKCE. Implicit grant розкривав токени у фрагментах URL.

НЕПРАВИЛЬНО: "CLIENT_SECRET У JAVASCRIPT-КОДІ SPA"

SPA — публічні клієнти. client_secret у браузерному JavaScript видний кожному, хто читає вихідний код. Публічні клієнти використовують PKCE замість цього.

НЕПРАВИЛЬНО: "REFRESH-ТОКЕН НАДІСЛАНО ДО API"

Refresh-токени дійсні лише на Ендпоінті токена. Надсилання refresh-токена до Resource сервера (API) є помилкою — API повинен відхилити його з 401.

НЕПРАВИЛЬНО: "STATE НЕОБОВ'ЯЗКОВИЙ — ПРОПУСКАЄМО"

Хоча RFC 6749 позначає state як РЕКОМЕНДОВАНИЙ, його відсутність є CSRF-вразливістю. На практиці state є обов'язковим для безпечних реалізацій.

09 OpenID Connect (OIDC) ПРОТОКОЛ AUTHN OIDC Core 1.0
Згідно зі специфікацією OpenID Connect Core 1.0: "OpenID Connect 1.0 — простий рівень ідентичності поверх протоколу OAuth 2.0." Точніше — це протокол автентифікації, який визначає, як клієнт верифікує особу кінцевого користувача на основі автентифікації, виконаної сервером авторизації. OAuth 2.0 відповідає на "що може цей клієнт?" OIDC відповідає на "хто цей користувач?" Він додає id_token (JWT з claim'ами ідентичності) та ендпоінт UserInfo до фреймворку OAuth 2.0. Це не фреймворк авторизації — це протокол, побудований поверх нього.
ПОШИРЕНА ПОМИЛКА

OIDC часто групують з OAuth 2.0 під "фреймворками авторизації", оскільки вони спільно використовують потоки та ендпоінти. Це неправильно. OAuth 2.0 — фреймворк авторизації. OIDC — протокол автентифікації, що використовує OAuth 2.0 як транспортний рівень.

Claim nonce — захист від replay-атак

Клієнт генерує випадковий nonce, надсилає його в запиті авторизації, а auth-сервер вбудовує його в id_token. Клієнт перевіряє, що nonce в отриманому id_token збігається з надісланим. Без nonce: перехоплений id_token може бути використаний повторно для автентифікації жертви протягом усього її TTL.

10 Single Sign-On (SSO) UX-ПАТЕРН / СХЕМА Wikipedia
SSO — це схема автентифікації та UX-патерн, а не протокол. Wikipedia визначає його як "схему автентифікації, що дозволяє користувачу входити з одним ID для доступу до кількох пов'язаних, але незалежних програмних систем." Він описує досвід користувача та архітектуру централізованої автентифікації. Базовими механізмами є реальні протоколи: SAML (корпоративний), OIDC (сучасний веб/мобайл), або Kerberos (мережевий). SSO знаходиться вище протокольного рівня — він визначає мету; протоколи визначають, як її досягти.
SSO — НЕ МЕТОД АВТЕНТИФІКАЦІЇ

SSO описує досвід користувача та архітектуру централізованої автентифікації. Базовими механізмами є протоколи: SAML, OIDC або власні реалізації. SSO знаходиться вище рівня методу автентифікації — він визначає, як сесії спільно використовуються між застосунками.

12 Типи автентифікації у Postman — що це таке ІНСТРУМЕНТ ТЕСТУВАННЯ Postman Docs
Postman групує типи автентифікації за категоріями. Розуміння категорії кожного варіанта запобігає поширеній помилці — ставленню до всіх опцій автентифікації Postman як рівнозначних.
МЕТОДИ АВТЕНТИФІКАЦІЇ — клієнт підтверджує особу при кожному запиті
Basic AuthКодує username:password у Base64, надсилає з кожним запитом. Облікові дані передаються з кожним викликом.
Bearer TokenВи вставляєте попередньо згенерований токен. Postman надсилає його як Authorization: Bearer <token>. Без підпису.
JWT BearerPostman локально конструює та підписує JWT, використовуючи вказані алгоритм, ключ і claim'и. Корисно для тестування конкретних комбінацій claim'ів у dev-середовищах, де відомий ключ підпису.
Digest AuthРеалізує Digest challenge-response обмін. Надсилає хеш, а не пароль.
NTLM AuthenticationПротокол автентифікації Windows. Базується на challenge-response. Використовується для корпоративних мережевих ресурсів.
API KeyНадсилає статичний ключ у заголовку або query-параметрі. Ви вказуєте назву та значення ключа.
ФРЕЙМВОРКИ АВТОРИЗАЦІЇ — протокольні потоки для обмеженого доступу до ресурсів
OAuth 1.0Реалізує 3-сторонній потік OAuth 1.0 з підписом запитів. Для застарілих API.
OAuth 2.0Реалізує потоки OAuth 2.0 (Auth Code, Client Credentials тощо). Postman обробляє redirect і обмін токенів. Зберігає отриманий access-токен для використання в запитах.
ВЕНДОРНІ РЕАЛІЗАЦІЇ
AWS SignatureРеалізує AWS SigV4 підпис для прямих викликів до AWS-сервісів (DynamoDB, SQS, SNS, S3). Ви вказуєте Access Key ID, Secret Access Key, регіон і сервіс. Кожен запит підписується хешем вмісту запиту + часова мітка. Використовуйте для тестування AWS-сервісів безпосередньо — оминаючи рівень застосунку.
Hawk AuthenticationMAC-базований підпис запитів, схожий на OAuth 1.0. Кожен запит підписується. Використовується деякими Mozilla та застарілими API.
Akamai EdgeGridВласний підпис запитів Akamai для їхніх API управління CDN.
ASAP (Atlassian)Внутрішня сервіс-до-сервісу автентифікація Atlassian. JWT-базована з асиметричними ключами. Використовується для інтеграцій Jira, Confluence.
КОЛИ ЩО ВИКОРИСТОВУВАТИ В QA-РОБОТІ

Тестування REST API з JWT: Bearer Token (вставити токен) або JWT Bearer (якщо є ключ).
Тестування DynamoDB/SQS/SNS напряму: AWS Signature (SigV4).
Тестування повного OAuth2 потоку входу наскрізно: OAuth 2.0 helper.
Тестування застарілого внутрішнього API: Basic Auth або Digest Auth.
Тестування IoT sensor API: API Key (зазвичай у кастомному заголовку).

13 Типові помилки — що НЕ слід говорити КРИТИЧНО ВАЖЛИВО OWASP Top 10
Поширені помилки при описі концепцій автентифікації та авторизації.
✗
Називати OAuth 2.0 методом автентифікації.
OAuth 2.0 — фреймворк авторизації, а не метод автентифікації. Він обробляє отримання обмеженого доступу до ресурсів. OIDC, побудований поверх OAuth 2.0, обробляє автентифікацію.
✗
Групувати SSO разом з методами автентифікації.
SSO — архітектурний патерн, а не метод. Він реалізується за допомогою протоколів — OIDC, SAML або Kerberos. Патерн описує мету; протокол описує, як її досягти.
✗
Використовувати JWT і Bearer Token як взаємозамінні поняття.
Bearer — назва HTTP-схеми в заголовку Authorization. JWT — формат токена. Bearer-токен може бути непрозорим рядком. JWT може використовуватися як Bearer-токен. Це різні концепції на різних рівнях.
✗
Називати JWT типом автентифікації.
JWT — формат токена, визначений у RFC 7519: структура даних із конкретним кодуванням і підписом. Він використовується в межах схем автентифікації та фреймворків авторизації, але сам по собі не є ні тим, ні іншим.
✗
Плутати автентифікацію і авторизацію.
Автентифікація відповідає на "хто ти?" — перевірка особи. Авторизація відповідає на "що тобі дозволено?" — перевірка прав. Це окремі кроки з окремими кодами помилок (401 vs 403), що діють на різних рівнях. Автентифікація завжди передує авторизації.
✗
Стверджувати, що JWT зашифрований.
Стандартний JWT (JWS) не зашифрований — payload кодується в base64url і читабельний для будь-кого. Підпис забезпечує виявлення підробки, а не конфіденційність. JWE — зашифрований варіант з 5 частинами замість 3.
✗
Вважати, що облікові дані Basic Auth захищені через base64-кодування.
Base64 — схема кодування, а не шифрування: повністю зворотна без ключа. Єдиний захист в Basic Auth — шифрування транспортного рівня через HTTPS.
