00 What is authentication vs authorization? CONCEPT
Before anything else, two terms that are always confused — and always asked in interviews. They are not the same thing and are never interchangeable.
AUTHENTICATION (authn)
"Who are you?"
Verifying that the entity making the request is who they claim to be.

Examples: checking username + password, validating a JWT signature, verifying a certificate.
AUTHORIZATION (authz)
"What are you allowed to do?"
Deciding what an already-authenticated entity is permitted to access or perform.

Examples: checking roles, scopes, permissions, ownership of a resource.
HTTP STATUS CODES — THE SHORTCUT

401 Unauthorized = authentication failed (the name is misleading — it means "not authenticated").
403 Forbidden = authenticated but not authorized (you are known, but not permitted).

The order is always fixed

EVERY PROTECTED REQUEST GOES THROUGH THIS SEQUENCE
1
AUTHENTICATION
Verify identity. Is this token valid? Is the signature correct? Is it expired? Does the issuer match?
Failure → 401
2
AUTHORIZATION
Verify permissions. Does this user's role allow this action? Does this token have the required scope? Does the user own this resource?
Failure → 403
3
ACCESS GRANTED
Both checks passed. Process the request and return 200.

What counts as an "authentication method"?

An authentication method is a specific mechanism by which a client proves its identity on a request. Examples: sending a password, sending an API key, sending a signed token.

An authorization framework (like OAuth 2.0) is a protocol that defines rules for how a third-party client obtains limited access to resources — it uses authentication methods as building blocks but is not itself an authentication method. This distinction is critical — see section 13 (common mistakes).

00b Encoding vs encryption vs hashing CONCEPT
Three words that look similar but are fundamentally different. Getting these wrong in an interview is an immediate red flag. Every auth topic depends on understanding which of these three operations is happening.
ENCODING
Purpose: format transformation for transport compatibility.
Reversible? Yes — no key needed.
Secret? No — anyone can decode.

Examples: Base64, Base64url, URL encoding, hex.
ENCRYPTION
Purpose: hide data so only authorized parties can read it.
Reversible? Yes — with the correct key.
Secret? Yes — meaningless without the key.

Examples: AES-256, RSA (used for key exchange).
HASHING
Purpose: produce a fixed-length fingerprint of data.
Reversible? No — by design.
Secret? N/A — different purpose.

Examples: SHA-256, bcrypt, MD5 (weak), HMAC-SHA256.

How each is used in auth

OperationWhere it appearsWhat it does
Base64 encodingBasic Auth, JWT header & payloadMakes binary/JSON safe for HTTP headers and URLs. Does NOT hide anything.
Base64url encodingJWT all three parts for transportSame as Base64 but URL-safe (uses - and _ instead of + and /). Still not secret.
Hashing (SHA-256)Digest Auth, password storage, JWT signature (as part of HMAC)Produces a fixed fingerprint. Cannot be reversed to original value.
HMAC (hash + secret key)JWT signature (HS256)Hash of data combined with a secret key. Proves both integrity and authenticity to anyone who knows the key.
RSA signingJWT signature (RS256)Private key produces signature; public key verifies. Not "encryption" in the hiding sense — it's used for signing.
Encryption (AES, RSA)JWE (encrypted JWT), HTTPS transportActually hides the payload. JWE is rare — JWS (signed JWT) is the default.
CRITICAL — DO NOT SAY IN AN INTERVIEW

"JWT is encrypted" — it is not (unless JWE is specifically used).
"Base64 is encrypted" — it is not. It is encoding. Anyone can decode it.
"The JWT signature is encrypted" — the signature is a cryptographic output (HMAC or RSA digital signature) that is then base64url-encoded for transport. It is not "encrypted data".

The JWT signature precisely explained

WHAT ACTUALLY HAPPENS WHEN A JWT IS SIGNED
// Step 1: encode the header (JSON → base64url)
base64url({ "alg": "RS256", "typ": "JWT" })
→ "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9"

// Step 2: encode the payload (JSON → base64url)
base64url({ "sub": "user123", "exp": 1745000000 })
→ "eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxNzQ1MDAwMDAwfQ"

// Step 3: sign the concatenated encoded parts
signing_input = "eyJhbGci..." + "." + "eyJzdWIi..."
signature_bytes = RS256_sign(signing_input, private_key)
// → produces raw bytes (cryptographic output)

// Step 4: base64url-encode the signature bytes for transport
base64url(signature_bytes) → "SflKxwRJSMe..."

// Final JWT = header . payload . signature (all base64url-encoded)
"eyJhbGci..." + "." + "eyJzdWIi..." + "." + "SflKxwRJSMe..."
PRECISE TERMINOLOGY

The JWT signature is the output of a signing algorithm applied to the encoded header + encoded payload using a key. That output (raw bytes) is then base64url-encoded for transport. The header and payload are base64url-encoded (readable by anyone). The signature is a cryptographic fingerprint — it cannot be "decoded" to anything meaningful, and it cannot be forged without the signing key.

01 Basic Authentication AUTHN METHOD RFC 7617
The simplest HTTP authentication method (RFC 7617). The client sends the username and password with every request — base64-encoded in the Authorization header. No tokens. No sessions. No state on the server.
ALWAYS CLARIFY IN INTERVIEWS

Base64 is encoding, not encryption. The value YWxpY2U6c2VjcmV0 decodes instantly to alice:secret with no key. Basic Auth is only safe when HTTPS encrypts the entire connection. Without HTTPS, credentials are plaintext on the wire.

Step-by-step flow

BASIC AUTH FLOW
1
CLIENT → SERVER
Client sends a request with no credentials.
GET /api/orders HTTP/1.1
2
SERVER → CLIENT
Server responds with 401 and tells the client which scheme to use.
401 Unauthorized WWW-Authenticate: Basic realm="MyApp"
3
CLIENT (internal)
Client concatenates username and password with a colon, then base64-encodes the result.
"alice:secret123" → base64 → "YWxpY2U6c2VjcmV0MTIz"
4
CLIENT → SERVER (every request)
Client includes the Authorization header on every single subsequent request. No caching, no token, no session — the credentials travel with every call.
GET /api/orders Authorization: Basic YWxpY2U6c2VjcmV0MTIz
5
SERVER
Server base64-decodes the value, splits on the colon, verifies the password against its database. Returns 200 (valid) or 401 (invalid).
No session is created. The server is stateless — it verifies from scratch on every request.

Properties

PropertyDetail
Stateless?Yes — server holds no session. Credentials sent every request.
Credential encodingBase64 (reversible, no key). NOT encryption, NOT a hash.
Safe without HTTPS?No — base64 decodes instantly on interception.
Logout possible?No standard mechanism. The browser may cache credentials until the tab/session closes.
Use todayInternal tooling, scripts, legacy APIs, CI/CD service accounts. Never for user-facing applications.
QA TEST ANGLES
① Valid credentials → 200. ② Wrong password → 401. ③ Missing Authorization header → 401. ④ Capture the header in Burp Suite → decode the base64 → you see plaintext credentials (document this). ⑤ Test over plain HTTP if available — confirm HTTPS is enforced. ⑥ Test special characters in passwords (colon in password breaks the format — server must handle this).
02 Digest Authentication AUTHN METHOD RFC 7616
Digest Auth (RFC 7616) was designed to fix Basic Auth's main weakness: the password is never sent over the wire. Instead, the client sends a hash of the password combined with a server-generated random value (a nonce). Even if intercepted, the hash cannot be reversed to get the original password.

Key concept: the nonce

A nonce (number used once) is a random string generated fresh by the server for each authentication challenge. The client mixes the password with this nonce before hashing. Because the nonce changes every challenge, capturing a valid response and replaying it against a different request won't work — the nonce won't match.

DIGEST AUTH FLOW
1
CLIENT → SERVER
Client sends request with no credentials.
2
SERVER → CLIENT (challenge)
Server responds with 401 and includes a fresh nonce in the header.
401 Unauthorized WWW-Authenticate: Digest realm="MyApp", nonce="abc123xyz"
3
CLIENT (internal)
Client hashes the credentials combined with the nonce using MD5 (or SHA-256 in newer versions).
HA1 = MD5("alice:MyApp:secret123") HA2 = MD5("GET:/api/orders") response = MD5(HA1 + ":" + nonce + ":" + HA2)
4
CLIENT → SERVER
Client sends the hash (called "response") — never the password.
Authorization: Digest username="alice", nonce="abc123xyz", response="6f3a..."
5
SERVER
Server performs the same hash calculation with its stored password and the nonce it issued. Compares result. If they match → 200.
The password is never transmitted. If the channel is intercepted, the hash alone cannot be reversed.

Digest vs Basic — comparison

PropertyBasic AuthDigest Auth
Password sent?Yes (base64-encoded)No — only a hash is sent
Replay protection?NoneYes — nonce changes per request
Safe without HTTPS?NoBetter (password not sent), but still weak (hash can be brute-forced)
Hash algorithmNone (base64)MD5 or SHA-256
Status todayLegacy but still usedLargely obsolete — replaced by token-based auth over HTTPS
QA TEST ANGLES
① Verify the nonce is unique per challenge (nonce reuse enables replay attacks). ② Verify HTTPS is still enforced — Digest Auth does not replace transport security. ③ If encountered: document as an outdated mechanism and recommend migration to Bearer Token over HTTPS. ④ Test with valid credentials → 200; wrong password → 401; missing nonce → 400/401.
03 API Keys AUTHN METHOD No RFC — vendor convention
An API Key is a static string — generated by the server and given to the client — that acts as an identity credential. Unlike Basic Auth, the client does not send a username/password. It sends the key. The server looks the key up in a database to identify the client and retrieve its permissions.

How API key auth works

API KEY FLOW (from Image 4 in your screenshots)
1
CLIENT → API SERVER
Client sends request with the API key — either in a custom header or as a query parameter.
GET /api/users Authorization: ApiKey abc123xyz456 — or — X-API-Key: abc123xyz456
2
API SERVER → DATABASE
Server looks up the key hash in the database to find which user/client it belongs to and what permissions it has.
SELECT user_id, scopes, active FROM api_keys WHERE key_hash = hash(request_key)
The key is stored as a hash — the plain key is never stored on the server.
2a — key valid
SERVER
Key exists, is active, and has the required scope → authorize the request → return 200 with data.
2b — key invalid
SERVER
Key not found or marked inactive.
401 Unauthorized
2c — key missing
SERVER
No API key in the request at all.
400 Bad Request (API key required)

Where API keys are sent

LocationExampleRisk
Custom headerX-API-Key: abc123Low — doesn't appear in URLs or browser history
Authorization headerAuthorization: ApiKey abc123Low
Query parameterGET /data?api_key=abc123High — appears in server logs, browser history, Referer headers
Request body{"api_key": "abc123"}Medium — only for POST requests
API KEYS ARE STATEFUL

Unlike JWT, an API key has no expiry embedded in itself. Validity is determined by a database lookup on every request. This means: API keys require server-side storage, they can be instantly revoked (delete from DB), but they also add latency (DB call per request).

QA TEST ANGLES
① Key in query parameter → check server logs for key exposure. ② Revoke a key via admin panel → immediately test if it still works (must return 401). ③ Test rate limiting per key. ④ Test with a key that belongs to a different user's scope. ⑤ Verify the plain key is not stored in the database (only a hash should be stored). ⑥ Check whether HTTPS is enforced — keys in headers are still plaintext at the transport layer without TLS.
04 Session-Based Authentication AUTHN METHOD RFC 6265 (Cookies)
Session-based auth is the classic web authentication model. After the user logs in once with credentials, the server creates a session record in its database and gives the client a session ID (stored in a cookie). Every subsequent request sends that session ID — the server looks it up to identify the user. The session state lives on the server.
SESSION AUTH FLOW
1
CLIENT → SERVER
User submits login form with credentials.
POST /login Body: { username: "alice", password: "secret123" }
2
SERVER (internal)
Server verifies credentials. If valid: creates a session record in the session store (database/Redis), generates a unique random session ID.
3
SERVER → CLIENT
Server sends the session ID to the client in a Set-Cookie header.
Set-Cookie: session_id=xK9mR3...; HttpOnly; Secure; SameSite=Strict
4
CLIENT → SERVER (every request)
Browser automatically sends the cookie on every matching request.
GET /api/orders Cookie: session_id=xK9mR3...
5
SERVER
Server looks up the session ID in the session store. Retrieves user data and permissions. Processes the request.
Requires a database lookup on every request. Stateful — the server must store sessions.
6 — logout
SERVER
On logout: server deletes the session record from the store. The session ID cookie becomes useless — even if captured, it will not match any session.

Session vs JWT — key difference

PropertySession-basedJWT-based
State locationServer (session store)Client (the token itself)
Server DB lookup?Yes — every requestNo — validates cryptographically
ScalabilityHarder (sessions must be shared across servers)Easier (stateless — any server can verify)
RevocationInstant — delete session recordHard — token valid until exp
Logout works?Yes — server deletes sessionOnly if blacklist or short TTL used
QA TEST ANGLES
① Log out → immediately use old session cookie → must return 401 (session deleted server-side). ② Check cookie attributes: HttpOnly (no JS access), Secure (HTTPS only), SameSite=Strict (CSRF protection). ③ Test session fixation: can you set your own session ID before login? ④ Test concurrent sessions: two logins for the same user — are both sessions valid or does login invalidate previous? ⑤ Test session timeout — does the server expire idle sessions?
05 Bearer Tokens & JWT TOKEN RFC 6750 (Bearer) RFC 7519 (JWT)
A Bearer Token is an access token where possession alone grants access — "whoever bears this token gets in." The most common format is JWT (JSON Web Token). Unlike sessions, JWTs are self-contained — all validation data is inside the token. No database lookup needed to verify a JWT.

What "Bearer" means

Bearer is the scheme name in the Authorization header. It means: "the holder of this token is authorized." The server grants access to whoever presents a valid token — it does not verify that the presenter is the original recipient. This is why token theft is a serious risk.

HOW THE TOKEN IS SENT
GET /api/orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIn0.SflKxw...

JWT structure — three parts

IMPORTANT PRECISION

All three parts are base64url-encoded for transport. But the header and payload are readable JSON (encoding only). The signature is a cryptographic output (produced by a signing algorithm) that is then base64url-encoded — it cannot be decoded to anything meaningful without the key, and it cannot be forged without the signing key.

JWT DECODED — ALL THREE PARTS
// PART 1: HEADER — identifies algorithm and token type
// (base64url-encoded JSON — readable by anyone)
{
  "alg": "RS256",  // signing algorithm
  "typ": "JWT"
}

// PART 2: PAYLOAD — the claims (data about the subject)
// (base64url-encoded JSON — readable by anyone — NOT secret)
{
  "sub": "user-123",         // subject: who this is about
  "iss": "https://auth.co.com",// issuer: who created the token
  "aud": "api.co.com",        // audience: who should accept it
  "iat": 1744996400,          // issued at (Unix timestamp)
  "exp": 1745000000,          // expiry (Unix timestamp)
  "jti": "uuid-abc-123",      // unique token ID (for revocation)
  "scope": "orders:read"      // what this token is allowed to do
}

// PART 3: SIGNATURE — proves the token was not tampered with
// Formula: base64url( sign(base64url(header)+"."+base64url(payload), key) )
// The signing algorithm output (raw bytes) is base64url-encoded for transport.
// It is NOT readable — it is a cryptographic fingerprint.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

HS256 vs RS256 — signing algorithms

HS256 — SYMMETRIC (HMAC-SHA256)
One shared secret key for both signing and verification. Any service that needs to verify tokens must know the secret. If any verifier is compromised, the signing secret is exposed — attacker can forge tokens.

Good for: single-service setups, internal tools.
RS256 — ASYMMETRIC (RSA-SHA256)
Private key signs (auth server only, never shared). Public key verifies (any service can have it). A compromised verifier cannot forge tokens — it only knows the public key.

Good for: microservices, distributed systems, multi-team architectures.

JWT validation — what the server checks on every request

JWT VALIDATION SEQUENCE
1
Signature — recalculate the expected signature from the received header+payload using the key. Compare to the signature in the token. If they don't match → 401.
2
Expiry (exp) — is the current time before the exp timestamp? If expired → 401.
3
Issuer (iss) — does the issuer match what this service expects? Prevents tokens from other systems. If mismatch → 401.
4
Audience (aud) — is this token intended for this service? Prevents token replay across services. If mismatch → 401.
5
Algorithm (alg) — is the algorithm what the server expects? Reject "none". Reject unexpected algorithms. If unexpected → 401.
6
All checks pass → extract claims from payload → proceed to authorization.
CRITICAL ATTACK — alg:none

If a JWT library accepts "alg": "none", it skips signature verification entirely. An attacker sets alg to none, modifies the payload (e.g. changes role to admin), removes the signature, and sends it. The server accepts it with no verification. Test: send a token with alg:none — must return 401.

The revocation problem

JWT is stateless — once issued, there is no database record to delete. If a token is stolen or a user is suspended, the token remains valid until exp passes. Mitigations:

  • Short TTL — access tokens should expire in 5–15 minutes.
  • jti blocklist — store revoked token IDs in Redis. Check on every request.
  • Refresh token rotation — see section 06.
QA TEST ANGLES
① Corrupt the signature (change last 5 chars) → must return 401. ② Use an expired token (exp in the past) → must return 401. ③ Send alg:none → must return 401. ④ Decode the payload at jwt.io — audit for PII, internal infrastructure details, unnecessary claims. ⑤ Send a token for Service A to Service B → must return 401 (aud mismatch). ⑥ Send a token from a different issuer → must return 401.
06 Access & Refresh Tokens TOKEN PAIR RFC 6749 §1.4
Most modern auth systems issue two tokens together: a short-lived access token for API calls, and a long-lived refresh token to get a new access token when the old one expires. This balances security (short window if stolen) with user experience (no re-login every 15 minutes).
ACCESS TOKEN
TTL: 5–60 minutes
Format: usually JWT
Sent to: every API endpoint
Validated by: API server (cryptographically)
Stolen? Attacker has a short window only.
REFRESH TOKEN
TTL: days to weeks (or longer)
Format: opaque string (random, no structure) or JWE (encrypted JWT — 5 parts)
Sent to: ONLY the /token endpoint (refresh token endpoint)
Validated by: auth server (via database lookup)
Stolen? Attacker has long-term access — high risk.
07 OAuth 1.0 AUTHZ FRAMEWORK RFC 5849
OAuth 1.0 (RFC 5849, 2010) was the first standardized protocol for delegated access — per RFC 5849, it provides "a method for clients to access server resources on behalf of a resource owner… without sharing their credentials." It is largely replaced by OAuth 2.0 but still appears in some older APIs (Twitter/X classic API, some payment systems).
WHAT "AUTHORIZATION FRAMEWORK" MEANS

OAuth is not an authentication method. It is a framework — a set of rules for how a third-party application can obtain limited access to resources. The user authenticates to the authorization server (using whatever auth method that server requires). OAuth then defines the protocol by which the third-party receives a token representing that granted access.

How OAuth 1.0 works

OAUTH 1.0 FLOW — 3-LEGGED AUTH
1
CLIENT → AUTH SERVER
Client requests a temporary "Request Token" using its Consumer Key and Consumer Secret.
2
AUTH SERVER → CLIENT
Returns a Request Token (temporary, not yet authorized).
3
CLIENT redirects USER → AUTH SERVER
User is sent to the auth server to log in and approve the access request.
4
USER approves → AUTH SERVER redirects back
Auth server redirects user back to client's callback URL with a verifier code.
5
CLIENT → AUTH SERVER
Client exchanges: Request Token + Verifier + Consumer Secret → Access Token.
6
CLIENT → RESOURCE SERVER
Client uses Access Token to make signed requests. Every request is signed using HMAC-SHA1 with both the Consumer Secret and Token Secret.
Request signing is the key complexity of OAuth 1.0 — every request body is part of the signature. This is why OAuth 2.0 dropped it in favor of HTTPS.

OAuth 1.0 vs OAuth 2.0 — key differences

PropertyOAuth 1.0OAuth 2.0
Request signingYes — every request signed with HMACNo — relies on HTTPS for transport security
Token typeOpaque tokens onlyJWT (or opaque), refresh tokens
ComplexityHigh — signature implementation error-proneLower — standardized flows
Mobile/SPA supportPoorGood — PKCE extension
StatusLegacy — mostly replacedCurrent standard
08 OAuth 2.0 AUTHZ FRAMEWORK RFC 6749
Per RFC 6749, OAuth 2.0 is an authorization framework that "enables a third-party application to obtain limited access to an HTTP service, either on behalf of a resource owner… or by allowing the third-party application to obtain access on its own behalf." OAuth 2.0 itself handles authorization only. It does not define authentication (that is what OIDC adds on top — see section 09). Note: when a client acts on its own behalf (Client Credentials grant), there is no user or delegation involved — just direct token issuance to the client.
OAUTH 2.0 IS NOT AN AUTHENTICATION METHOD

OAuth 2.0 tells you what a user has permitted a client to do. It does not tell you who the user is. When you "log in with Google," OAuth 2.0 grants the app access to your Google data. OpenID Connect (built on top of OAuth 2.0) provides the identity — who you are.

The four roles in OAuth 2.0

RESOURCE OWNER
The user who owns the protected data and grants access.
CLIENT
The third-party application that wants access to the user's resources.
AUTHORIZATION SERVER
Issues tokens after authenticating the user and getting consent. (e.g. Google Auth, AWS Cognito)
RESOURCE SERVER
The API that holds the protected data. Accepts and validates access tokens.

Flow 1: Authorization Code (user-facing apps)

Used when a user must be present to authenticate and grant consent.

AUTHORIZATION CODE FLOW
1
CLIENT → AUTH SERVER
Client redirects user to auth server's /authorize endpoint.
GET /authorize?response_type=code &client_id=myapp &redirect_uri=https://app.com/callback &scope=orders:read &state=random_csrf_token
2
USER (at auth server)
User logs in and approves the requested scopes.
3
AUTH SERVER → CLIENT (redirect)
Auth server redirects to the redirect_uri with a short-lived authorization code and the same state value.
GET https://app.com/callback?code=AUTH_CODE&state=random_csrf_token
4
CLIENT (internal)
Client verifies the state matches what it sent (CSRF protection).
5
CLIENT → AUTH SERVER (back channel)
Client exchanges code + client_secret for tokens. This is server-to-server — tokens never touch the browser URL.
POST /token grant_type=authorization_code&code=AUTH_CODE &client_id=myapp&client_secret=SECRET &redirect_uri=https://app.com/callback
6
AUTH SERVER → CLIENT
Returns access_token and refresh_token.

Flow 2: Authorization Code + PKCE (mobile/SPA)

PKCE (Proof Key for Code Exchange) extends Auth Code flow for public clients that cannot safely store a client_secret (mobile apps, SPAs). Without PKCE, a malicious app on the same device can intercept the authorization code and exchange it for tokens.

PKCE ADDITIONS TO AUTH CODE FLOW
A
CLIENT (before step 1)
Client generates a random code_verifier string, then hashes it to produce a code_challenge.
code_verifier = random_string(64 chars) code_challenge = base64url(SHA256(code_verifier))
B
CLIENT → AUTH SERVER (step 1 modified)
Client includes code_challenge in the authorization request.
GET /authorize?...&code_challenge=HASH&code_challenge_method=S256
C
CLIENT → AUTH SERVER (step 5 modified)
At token exchange, client sends the original code_verifier (not the hash). Auth server hashes the verifier and compares to the stored challenge. Only the original requester has the verifier.
POST /token ...&code_verifier=ORIGINAL_RANDOM_STRING

Flow 3: Client Credentials (machine-to-machine)

Used when there is no user involved — a service authenticates as itself.

CLIENT CREDENTIALS FLOW
1
SERVICE → AUTH SERVER
Service sends its own client_id and client_secret directly to the /token endpoint. No user redirect, no consent.
POST /token grant_type=client_credentials &client_id=my-service&client_secret=SERVICE_SECRET &scope=data:ingest
2
AUTH SERVER → SERVICE
Returns an access_token representing the service (not any user). No refresh token — the service can re-authenticate at any time.
The token's sub claim is the service's client_id — not a user ID.

QA TEST ANGLES
① Modify redirect_uri → auth server must reject (code interception risk). ② Remove state param → server must still validate state on callback (CSRF test). ③ Auth Code: try to reuse the authorization code a second time → must return error. ④ PKCE: send token exchange without code_verifier → must be rejected. ⑤ Client Credentials token → send to user-specific endpoint → must return 403 (wrong subject type). ⑥ Verify code_challenge_method=S256, not plain.
09 OpenID Connect (OIDC) AUTHN PROTOCOL OIDC Core 1.0
Per the OpenID Connect Core 1.0 specification: "OpenID Connect 1.0 is a simple identity layer on top of the OAuth 2.0 protocol." More precisely, it is an authentication protocol — it defines how a client verifies the identity of an end-user based on authentication performed by an Authorization Server. OAuth 2.0 answers "what can this client do?" OIDC answers "who is this user?" It adds the id_token (a JWT containing identity claims) and the UserInfo endpoint to the OAuth 2.0 framework. It is not an authorization framework — it is a protocol built on top of one.
COMMON MISTAKE

OIDC is often grouped with OAuth 2.0 under "authorization frameworks" because they share flows and endpoints. This is incorrect. OAuth 2.0 is an authorization framework. OIDC is an authentication protocol that uses OAuth 2.0 as its transport layer. Confusing these two is a frequent interview error.

id_token vs access_token — critical distinction

ID_TOKEN
Who it's for: the client application.
Contains: identity claims — name, email, profile.
Purpose: tells the client who the user is.
Send to API? No — it is NOT for API authorization.
Audience: the client_id.
ACCESS_TOKEN
Who it's for: the resource server (API).
Contains: authorization claims — scopes, subject.
Purpose: tells the API what the user is allowed to do.
Send to API? Yes — in Authorization: Bearer header.
Audience: the API resource server.

The nonce claim — replay attack prevention

The client generates a random nonce, sends it in the authorization request, and the auth server embeds it in the id_token. The client verifies that the nonce in the received id_token matches what it sent. Without nonce: a captured id_token can be replayed to authenticate as the victim for its entire TTL.

QA TEST ANGLES
① Decode id_token → check for PII beyond what the application needs. ② Send id_token to a resource API endpoint (instead of access_token) → must return 401/403. ③ Call /userinfo with expired access_token → must return 401. ④ Test nonce: replay a captured id_token in a second login → must be rejected. ⑤ AWS Cognito finding: iss claim contains the full user pool URL — infrastructure disclosure, medium severity.
10 Single Sign-On (SSO) UX PATTERN / SCHEME Wikipedia
SSO is an authentication scheme and UX pattern — not a protocol. Wikipedia defines it as "an authentication scheme that allows a user to log in with a single ID to access several related, yet independent, software systems." It describes the user experience and architecture of centralised authentication. The underlying mechanisms are actual protocols: SAML (enterprise), OIDC (modern web/mobile), or Kerberos (network). SSO sits above the protocol layer — it defines the goal; the protocols define how it is achieved.
SSO IS NOT AN AUTHENTICATION METHOD

SSO describes the user experience and architecture of centralized authentication. The underlying mechanisms are protocols: SAML, OIDC, or proprietary implementations. SSO sits above the auth method layer — it determines how sessions are shared across applications.

SSO FLOW
1
USER → APP A
User tries to access App A. App A has no session for this user.
2
APP A → IDENTITY PROVIDER
App A redirects user to the central IdP (e.g. Okta, Google Workspace, ADFS).
3
USER authenticates at IdP
User logs in once with their corporate credentials. IdP establishes a session for this user.
4
IDP → APP A
IdP sends an assertion (SAML) or token (OIDC) back to App A. App A establishes its own local session.
5
USER → APP B (later)
User tries to access App B. App B redirects to IdP. IdP checks its session — user is already authenticated. Sends assertion to App B immediately — no login prompt.

12 Postman auth types — what each one is TESTING TOOL Postman Docs
Postman groups auth types into categories. Understanding which category each option belongs to prevents the common mistake of treating all Postman auth options as equivalent. This directly maps to Image 3 in your screenshots.
AUTHENTICATION METHODS — the client proves its identity on each request
Basic AuthEncodes username:password as Base64, sends in every request. Credentials travel with every call.
Bearer TokenYou paste a pre-generated token. Postman sends it as Authorization: Bearer <token>. No signing.
JWT BearerPostman constructs and signs the JWT locally using your provided algorithm, key, and claims. Useful for testing specific claim combinations in dev environments where you know the signing key.
Digest AuthImplements the Digest challenge-response handshake. Sends a hash, not the password.
NTLM AuthenticationWindows authentication protocol. Challenge-response based. Used for corporate network resources.
API KeySends a static key in a header or query parameter. You specify the key name and value.
AUTHORIZATION FRAMEWORKS — protocol flows for limited resource access
OAuth 1.0Implements the OAuth 1.0 3-legged flow with request signing. For legacy APIs.
OAuth 2.0Implements OAuth 2.0 flows (Auth Code, Client Credentials, etc.). Postman handles the redirect and token exchange. Stores the resulting access token for use in requests.
VENDOR-SPECIFIC IMPLEMENTATIONS
AWS SignatureImplements AWS SigV4 signing for direct calls to AWS services (DynamoDB, SQS, SNS, S3). You provide your Access Key ID, Secret Access Key, region, and service. Every request is signed with a hash of the request content + timestamp. Use for testing AWS services directly — bypassing the application layer.
Hawk AuthenticationMAC-based request signing similar to OAuth 1.0. Each request is signed. Used by some Mozilla and legacy APIs.
Akamai EdgeGridAkamai's proprietary request signing for their CDN management APIs.
ASAP (Atlassian)Atlassian's internal service-to-service auth. JWT-based with asymmetric keys. Used for Jira, Confluence integrations.
WHEN TO USE WHICH IN QA WORK

Testing a REST API with JWT: Bearer Token (paste the token) or JWT Bearer (if you have the key).
Testing DynamoDB/SQS/SNS directly: AWS Signature (SigV4).
Testing a full OAuth2 login flow end-to-end: OAuth 2.0 helper.
Testing a legacy internal API: Basic Auth or Digest Auth.
Testing an IoT sensor API: API Key (usually in custom header).

13 Common mistakes — what NOT to say in an interview INTERVIEW CRITICAL OWASP Top 10
Common mistakes when describing authentication and authorization concepts.
✗
Calling OAuth 2.0 an authentication method.
OAuth 2.0 is an authorization framework, not an authentication method. It handles obtaining limited access to resources. OIDC, built on top of OAuth 2.0, handles authentication.
✗
Grouping SSO alongside authentication methods.
SSO is an architectural pattern, not a method. It is implemented using protocols — OIDC, SAML, or Kerberos. The pattern describes the goal; the protocol describes how it is achieved.
✗
Using JWT and Bearer Token as interchangeable terms.
Bearer is the HTTP scheme name in the Authorization header. JWT is a token format. A bearer token can be an opaque string. A JWT can be used as a bearer token. They are different concepts at different layers.
✗
Referring to JWT as an authentication type.
JWT is a token format defined in RFC 7519 — a data structure with specific encoding and signing. It is used within authentication schemes and authorization frameworks, but is not itself either.
✗
Confusing authentication and authorization.
Authentication answers "who are you?" — verifying identity. Authorization answers "what are you allowed to do?" — verifying permissions. They are separate steps, have separate failure codes (401 vs 403), and operate at different layers. Authentication must succeed before authorization is checked.
✗
Saying JWT is encrypted.
Standard JWT (JWS) is not encrypted — the payload is base64url-encoded and readable by anyone. The signature provides tamper detection, not confidentiality. JWE is the encrypted variant and has 5 parts instead of 3.
✗
Assuming Basic Auth credentials are protected because they are base64-encoded.
Base64 is an encoding scheme, not encryption — it is fully reversible with no key. The only protection in Basic Auth comes from HTTPS encrypting the transport layer.
